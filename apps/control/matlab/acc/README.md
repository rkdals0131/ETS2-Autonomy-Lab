# 고속도로 ACC 종방향 제어기 (MPC + Stateflow + Embedded Coder)

레퍼런스 트럭(Scania S 6x2, DC16 520, G33CM-R 리타더, 빈 박스 트레일러 연결 약 20.3 t, [docs/31](../../../../docs/31_plant_parameters.md))의 ACC입니다. 게임의 리얼 오토매틱이 변속하고, 제어기는 스로틀·서비스 브레이크·리타더 단만 냅니다. 상위는 선형 MPC(MPC Toolbox, 비교용 두 제어기를 Multiple MPC 블록으로 전환), 하위는 측정 맵으로 만든 액추에이터 배분기, 모드는 Stateflow이고, `ACC_Controller` 하나를 Embedded Coder로 C++ 클래스(`ets2::AccController`)로 만듭니다. 폐루프 검증용 플랜트는 [종방향 플랜트](../../../sysid/matlab/longitudinal/README.md)에 자동 변속 모델을 붙인 것입니다. 질량은 고정값이 아닙니다. `MassEstimator`가 식별된 구동력 모델로 질량을 온라인 추정하고(재귀 최소제곱, 정보 구간에서만 갱신), 배분기 맵과 MPC의 도달 가능 범위가 그 질량을 씁니다.

## 실행

MATLAB에서 이 폴더로 이동한 뒤:

```matlab
build_acc_plant();        % acc_plant.slx: 종방향 플랜트 + 자동 변속(Stateflow)
validate_acc_plant();     % acc-20261020-192243 구간 재생 → results/plant_validation.json, plant_*.png (약 1분)
build_acc_controller();   % ACC_Controller.slx
build_acc_closed_loop();  % acc_closed_loop.slx (제어기·플랜트 Model 블록 + 선행차)
run_acc_scenarios();      % 시나리오 12개 → results/scenario_*.json/png, scenarios_summary.json (약 3분)
replay_mass_estimate();   % 게임 기록 9개를 질량 추정기로 재생 → results/mass_replay.json, mass_replay_*.png (약 4분)
validate_acc_mass();      % 플랜트 12/20.3/30/40 t × 제어기 설정 3개 × 시나리오 12개 + 변형 → results/mass_validation.json (약 20분)
generate_acc_code();      % C++ 생성·컴파일(codegen/, git 제외) → generated/에 소스 복사 (약 3.5분)
verify_acc_codegen();     % 생성 코드 SIL 대 모델 비교 → results/codegen_verification.json (약 10분)
compile_generated();      % generated/만으로 MSVC 컴파일 + example/acc_smoke_main.cpp 실행
```

`run_acc_scenarios(Rebuild=true)`는 세 .slx를 모두 다시 만들고 돌립니다. `run_acc_scenarios(PlantMass=40000, MassPrior=0, Adaptive=false, Grade=[t g], PitchKnown=false, ActuationValid=false)`처럼 플랜트 질량, 질량 사전값, 고정 맵(예전 제어기), 경사, 피치 입력 유무, 추정기 입력원을 바꿉니다(`acc_scenario_input.m`; 15 t 미만 플랜트는 트레일러 브레이크가 없는 트럭 단독). `.slx`는 모두 build 스크립트로 다시 만들어지므로 모델을 직접 고치지 않습니다. 맞춤과 식별은 `fit_auto_shift()`(변속 사건 표, 발진 클러치 맞춤), `identify_actuator_lag()`(게임 기록에서 경로별 지연), `identify_closed_loop_lag()`(시나리오 결과에서 a_des → 가속도 지연)입니다.

- MPC 블록은 제어기 객체를 기본 작업공간에서만 찾습니다. 그래서 `ACC_Controller.slx`의 InitFcn이 `acc_controller_init`를 불러 `mpcComfort`, `mpcEmergency`를 기본 작업공간에 만듭니다. 나머지 파라미터(`C`, `MODE_*`)는 모델 작업공간에 있고 `acc_controller_params.m`에서 옵니다.
- 플랜트 파라미터는 `acc_plant.slx` 모델 작업공간의 `P = acc_plant_params()`와 차트용 `AT_*`입니다. `acc_plant_params`가 `apps/sysid/matlab/longitudinal`을 경로에 넣고 `longitudinal_params("trailer")`를 읽습니다(그 폴더는 고치지 않음).
- 기록은 `acc_load_recording("<run>")`가 읽어 `cache/<run>.mat`에 둡니다(git 제외).

## 구조

### 플랜트: `acc_plant.slx`

입력 `thr_cmd`, `brk_cmd`, `ret_step`(0–5), `eb_cmd`, `brake_temp`, `grade`, 출력 `v`, `a`, `rpm`, `gear`(SDK, 0 중립), `Te`, `clutch`, `thr_app`, `F_brake`입니다. ode3 5 ms(20 ms 차트, 50 ms 제어기의 정수배).

- `Longitudinal`: [종방향 플랜트](../../../sysid/matlab/longitudinal/README.md)를 그대로 복사한 것에 두 가지를 더했습니다. 서비스 브레이크 힘에 (입력, 속도) 보정표를 곱하고(저속 경제동, 아래), 정지 중 가속도 출력을 0으로 둡니다(모델의 지연된 힘/질량이 정지 후에도 음수로 남는 것을 게임처럼 0으로).
- `AutoGearbox`(Stateflow, 20 ms): NEUTRAL → LAUNCH_ENGAGE → LAUNCH_SLIP → LAUNCH_CLOSE → DRIVE ↔ SHIFT_OPEN → SHIFT_CLOSE → THR_RETURN. 기록에서 읽은 규칙입니다(`acc_plant_params.m`에 근거 수치).
  - 올림: 현재 단 회전수 > up_rpm(스로틀, 단). 스로틀 1.0에서 약 1,900, 0.2에서 약 1,460–1,500 rpm. 목표 단은 변속 뒤 회전수가 899(목표 ≤ 6) / 910(7–9) / 935 rpm(10 이상) 이상인 가장 높은 단이라 4 → 6 → 8 → 10처럼 건너뜁니다. 기록의 올림 69개 중 66개에서 같은 단을 고르고, 나머지 3개는 리타더 5단을 푼 직후의 7 → 8을 모델이 7 → 9로 고릅니다.
  - 내림: 예측 회전수(속도 + 감속 × 0.75 s)가 955 − 24·(12 − 단) rpm(스로틀 0) 아래, 킥다운 쪽은 스로틀³로 올림. 리타더 5단·엔진브레이크 중에는 1,505 rpm 아래에서 2,500 rpm 이하가 되는 가장 낮은 단으로 내림(12 → 9 → 7, 11 → 8 → 6 → 4 재현).
  - 변속 시간: 클러치가 열리기 시작해 0.50 s 뒤 SDK 단 변경, 0.233 s 뒤 클러치 닫힘, 0.80–0.82 s 뒤 스로틀 복귀(기록의 모든 변속이 같음). 내림 중에는 적용 스로틀 0.2(회전수 맞춤).
  - 중립: 스로틀 0에서 600 rpm 아래, 또는 브레이크 0.5 이상에서 예측 900 rpm 아래.
  - 발진: SDK 단 0 → 4(기록 17번 중 11번, 나머지는 2), 클러치 용량을 스로틀별로 램프(용량 최대 200/651/647/1,557/2,113 Nm, 시간 2.31/2.31/0.44/0.69/0.50 s, 스로틀 0/0.2/0.4/0.7/1.0). 종방향 모델의 클러치 식에 게임 클러치 값을 그대로 넣으면 게임보다 훨씬 많이 전달되므로, 재생 속도로 맞춘 값입니다(`fit_auto_shift.m`).
- 엔진브레이크(5단·B) 토크는 0.82배로 씁니다. 엔진 토크 채널은 −3,000 Nm인데 감속은 그만큼 나오지 않습니다(9단 63–40 km/h에서 게임 2.45, 보정 전 2.62, 보정 뒤 2.43 m/s²; docs/31의 "엔진브레이크 8단 약 12 % 작음"과 같은 방향).
- 아이들 크리프(`IdleCreep`, MATLAB Function, 2026-10-21 추가): 기어가 물린 채 0.3 m/s 넘게 굴러가던 중 적용 스로틀이 0이면 고정 힘(0.8 m/s까지 14 kN, 2.5 m/s에서 0)이 밀고, 0.05 m/s 아래(정지)에서는 클러치가 열려 사라집니다. 경사 입력에 −F/(m·g)로 더합니다. 근거는 게임 관찰 하나입니다(2026-10-21, 트럭 단독, 운전자 개입 뒤 스로틀 0·브레이크 0.085로 1.08 m/s를 유지; 브레이크 0.2는 정지를 유지; 정지 상태에서는 기어가 풀려 기어가지 않음, docs/31). 14 kN은 플랜트의 트럭 단독에서 브레이크 0.085(10.8 kN) + 구름 저항과 1.08 m/s에서 평형이 되는 값이고, 수정 전 제어기를 이 플랜트에 넣으면 0.99 m/s로 계속 기어갑니다(게임 1.08). 엔진 쪽으로 약 175 Nm(SDK 2단)이고 크리프 힘-속도 곡선의 모양은 가정입니다.
- 서비스 브레이크 보정: 원래 모델은 70 km/h 표와 50 km/h 강제동을 잘 맞추지만 저속 경제동이 셉니다(20 km/h 0.1 → 모델 2.44, 게임 1.81 m/s²). 0.02–0.2 입력만 측정값/모델 비율(저속 0.67–0.85)을 곱하고, 큰 입력은 모델 그대로 둡니다. 0.3–1.0 정지 시험(`acc-20261020-185529`)은 브레이크 94–188 °C에서 쟀으므로 쓰지 않았습니다.

### 제어기: `ACC_Controller.slx` (서브시스템 `ACC_Controller`, 0.05 s, 원자 서브시스템)

`InputConditioning` → `ModeLogic`(Stateflow) → `MPC_Prep` → `MPC`(Multiple MPC Controllers) → `MPC_Post` → `Allocator`, 마지막 적용 요청은 Unit Delay로 MPC의 `ext.mv`에 돌아갑니다. `MassEstimator`는 입력과 한 스텝 전의 자기 명령(또는 하네스가 주는 적용값)으로 질량을 내고, `MPC_Prep`과 `Allocator`가 그 질량을 씁니다(아래 "질량 추정").

**MPC 예측 모델**(`acc_design_mpc.m`): 상태 [간격 d, 상대속도 v_lead − v, 자차 속도 v, a1, a2], a = a1 + a2. 조작변수는 둘입니다. u1은 구동 경로(스로틀·리타더 1–4, 1차 지연 0.5 s), u2는 브레이크 경로(1차 지연 0.33 s, u2 ≤ 0)이고, 선행차 가속도는 측정 외란으로 지평선 동안 일정합니다(선행차가 2 s 안에 서는 만큼까지만 감속으로 봄). 출력은 y1 = d − 2.0·v, y2 = 상대속도, y3 = v. Ts 0.05 s, 예측 80 스텝(4 s), 이동 블로킹 [2 3 5 10 20 40](경로당 6개 이동), 상태는 측정값을 그대로 넣는 custom 추정입니다(외란 모델 없음). 출력 a_des = u1 + u2입니다.

- **브레이크를 아끼는 비용**: 선형 MPC는 음의 가속에만 다른 가중을 줄 수 없습니다. 그래서 감속을 경로 둘로 나눴습니다. u1은 타력 + 리타더 4단까지(브레이크 없이 낼 수 있는 감속, 속도별 온라인 하한)만 내려갈 수 있고 가중 0.05, u2(서비스 브레이크)는 가중 1.0으로 20배 비쌉니다. 그래서 최적해는 타력·리타더를 먼저 쓰고 그 범위를 넘을 때만 브레이크 경로를 씁니다. 변화율 가중(2.0 / 3.0)과 경로별 변화율 제약이 매끄러움을 맡습니다.
- **제약**: 총 하한 a_min − u1_min이 u2 하한(평상 −3.0, 비상 −6.0 m/s²), u1 상한은 min(0.8, 0.85·전부하 가속(v)), 선행차를 따라잡는 중(선행차가 가속하지 않음)에는 0.4. 저크: u1 −1.0/+1.5, u2 −2.0/+2.5 m/s³(평상), −3/+3, −12/+6(비상). 온라인 경계는 마지막 이동에서 저크 제약으로 닿을 수 있는 값보다 좁히지 않습니다(그렇지 않으면 QP가 불능이 되어 마지막 값을 붙잡는 것을 시나리오에서 봤음). QP가 실패하면 가속하지 않고 마지막 제동을 유지합니다.
- **간격 정책**: 목표 간격 d0 + th·v(d0 5 m, th 기본 2.0 s, 범퍼-범퍼)를 직접 추종하지 않고, 상대속도 기준을 만듭니다. 선행차 속도에서의 간격 오차 e = d − (d0 + th·v_lead)에 대해 e > 0이면 접근 속도 기준 −(√(2·a·e + c²) − c), c = a/k(a = 2.0 m/s², k = 0.4 /s, STOP에서 0.8 /s)로, 최대 a의 감속으로 목표 간격에 닿는 속도이고 목표 근처에서는 선형(시정수 2.5 s)입니다. 지금 접근 속도보다 빠르게 다가가라고는 하지 않습니다(따라잡기 1.5 m/s까지). e < 0이면 0.05 /s·|e|(최대 0.5 m/s)로 천천히 벌립니다. 이 기준은 지평선을 따라 앞으로 굴려(간격 오차가 기준 속도만큼 줄고 선행차 감속으로 목표 간격이 줄어듦) 미리보기로 넣습니다. y1은 약한 가중(0.05)으로 시간 간격을 유지합니다.
- **최소 간격(soft)**: d ≥ 3 + 0.5·th·v입니다. 과제 문구의 "d0 + th·v"를 하한으로 그대로 두면 30 m 끼어들기(80 km/h, 목표 49 m)에서 하한을 19 m 어긴 상태가 되어 가혹하게 제동합니다. 그래서 d0 + th·v는 추종 목표로, 그 절반 시간 간격을 soft 하한(ECR 1, 가중 1e5)으로 두었습니다.
- **설정 속도**: CRUISE는 y3를 설정 속도로 추종(가중 0.6), 다른 모드에서는 v ≤ 설정 + 0.3 m/s soft 상한. 설정 속도를 낮추면 현재 속도에서 시작하는 램프(최대 0.5 m/s², 그 속도·질량에서 타력 + 리타더 4단 감속의 80 %)로 내리고, 램프를 지평선에 미리 보여 주며 램프 동안 상한에 1 m/s 여유를 둡니다. 예전에는 계단 기준을 soft 상한이 브레이크로 지켜 80 → 60 km/h에서 −2.6 m/s²까지 감속했습니다(이제 −0.6, 브레이크 입력 0.02 이하). 추종 모드의 상대속도 기준은 v_lead − v_set 아래로 내려가지 않습니다. 선행차가 설정 속도보다 빠르면 예전 기준(1.5 m/s까지 따라잡기)이 설정 속도 상한과 다투어 스로틀이 약 1 s 주기로 0 ↔ 0.6을 오갔습니다(`mass_mixed` 112–125 s, 12–40 t 모두, 고정 질량 제어기도 같음). 두 가지 모두 질량 검증 시나리오에서 찾아 고쳤고, 이 두 수정만으로는 기존 시나리오 지표가 바뀌지 않았습니다(아래 표의 작은 차이는 크리프와 브레이크 효율 학습 때문).

**배분기**(`acc_allocate.m`, 측정 맵):
- 타력 감속(속도·단·rpm에서 구름 + 공기 + 엔진 마찰, 70 km/h 12단 0.21 m/s²)보다 0.08 m/s² 이상 큰 요청이면 구동: 리타더 즉시 해제, 스로틀 = 현재 단의 역엔진맵(부분 부하 1 − (1 − thr)^1.33) + 가속도 PI(kp 0.2, ki 0.6 /s, 오차는 max(a, 타력) 기준, 중립·클러치 미끄럼·변속 뒤 1 s 동안 적분 정지, 포화 시 적분 정지). 타력 아래로 내려가면 구동을 끝냅니다(히스테리시스 0.08 / 0, 리타더가 아직 걸려 있으면 0.25 넘어야 구동으로 가고 그 전에는 리타더를 한 단씩 내림).
- 그 아래는 스로틀 0, 리타더 1–4단 양자화: 필요 감속이 다음 단 몫의 70 %를 넘으면 한 단 올림(0.4 s 간격), 아래 단 쪽으로 70 % 내려가면 한 단 내림(1.0 s 간격), 방향을 바꿀 때는 2.5 s를 기다림. 단 몫 = 기울기(4.33/9.04/14.69/21.03 Nm/(rad/s))·v·(fd/r)²/m, 타력 포함 2·3·4단 0.43/0.53/0.61 m/s²(게임 0.42/0.52/0.60).
- 남는 감속이 0.12 m/s²(급할 때 0.02)를 넘으면 서비스 브레이크: 측정 표를 이 속도에서 역보간(연속값, 70 km/h에서 0.01당 약 0.23 m/s²)하고 추정기의 브레이크 효율 `k_brake`로 나눔(아래), 브레이크 중 리타더 몫은 0.75로 셈(3단 + 0.05/0.1에서 1.61/2.79 대 합 1.70/2.82).
- 리타더 5단은 4 s 지평선 평균 요청 ≤ −2.2, 지금 요청 ≤ −2.0이 2 s 계속, 30 km/h 이상, 운동학적 필요 감속 ≤ 2.5(선행차에 다가가는 중이 아님)일 때만 씁니다. 3.1 s 동안 브레이크가 다리를 놓고, 그 뒤 5단 + 0.6보다 더 필요하면 4단 + 브레이크로 돌아갑니다. 비상에서는 쓰지 않습니다. `engine_brake`는 `C.alc.use_engine_brake = true`일 때만(리타더가 없는 트럭에서 5단 대신) 켭니다.
- HOLD: 브레이크 0.2, 리타더 0. 정지 요청(STOP, 또는 CRUISE·FOLLOW·GO에서 설정 속도 < 0.5 m/s) 중 0.5 m/s 아래는 브레이크 최소 0.05.
- 정지 보조(2026-10-21 게임 관찰 대응): 정지 요청 중 2 m/s 아래에서 요청보다 덜 감속하면 그 부족분(a − a_des)을 적분해 브레이크를 더합니다(0.15 /(m/s²·s), 최대 HOLD 브레이크 0.2). 리얼 오토매틱의 아이들 크리프가 배분기 모델에 없어, 예전에는 a_des −1.5를 내도 브레이크 0.085에서 크리프와 비겨 1.08 m/s로 계속 기어갔습니다. 정상 정지에서는 a가 a_des를 따라가므로 적분이 거의 쌓이지 않습니다.

**모드**(`ModeLogic`, `mode` 출력): 0 OFF(enable false, 모든 출력 0), 1 CRUISE, 2 FOLLOW(선행차가 d0 + th·v + (v − v_lead)²/(2·2.0) + 20 m 안, 해제는 +30 m 또는 0.5 s 동안 선행차 없음), 3 STOP(선행차 < 0.5 m/s), 4 HOLD(정지 < 0.15 m/s), 5 GO(정지 뒤 3 s 안에 선행차가 2 m 이상 떠나면 자동, 아니면 resume 입력; 2 m/s에서 FOLLOW/CRUISE), 6 EMERGENCY(필요 감속 > 3.2 m/s² 또는 3 m/s 넘게 다가가며 TTC < 2 s; 4 s·2.0 m/s² 아래가 1 s 계속되면 해제). 필요 감속은 선행차가 속도를 유지하면 상대 정지거리, 선행차가 제동 중이면 둘 다 정지할 때의 값입니다(상수 감속 접근에서 TTC는 v/(2a)로 작아지므로 TTC만으로는 비상을 켜지 않음). enable 직후 첫 스텝은 `mode 0`, 다음 스텝부터 판정합니다. 정지 상태에서 켜면 HOLD에서 resume을 기다립니다. 설정 속도 < 0.5 m/s(`C.mode.vset_stop`)는 정지 요청입니다. CRUISE·FOLLOW·GO에서 0.15 m/s 아래가 되면 HOLD로 가고(선행차 없이도), HOLD에서 GO로 가지 않으며(resume 무시), 운전자가 밀어 1 m/s를 넘으면 CRUISE로 돌아가 다시 세웁니다. 예전에는 선행차 없는 CRUISE에서 HOLD로 가는 길이 없었습니다(게임 2026-10-21: 설정 속도 0, 운전자 스로틀 → resume → GO → CRUISE, 그 뒤 1.08 m/s 크리프).

**질량 추정**(`MassEstimator`, `acc_mass_estimate.m`, 파라미터 `C.est`):
- 모델: 클러치가 붙어 있을 때의 힘 균형을 기준 질량 m_ref = 20.3 t로 나눈 꼴입니다. y = a + g·(c + sin θ), φ = (lag(F_구동 − 3.0·v²) − J·(기어비·2.59/0.506)²·a)/m_ref, y = θ·φ, θ = m_ref/m. F_구동 = η·기어비·2.59/0.506·Te이고, Te는 적용 스로틀에서 부분 부하 맵(1 − (1 − thr)^1.33)·전부하 곡선·마찰선으로 구한 뒤 터보 지연 표(토크·rpm별 상승률, 종방향 맞춤)로 오름만 제한합니다. 배분기가 뒤집는 맵과 같은 맵이라, 추정값은 "이 스로틀 맵이 맞는 질량"입니다. lag는 차체 지연 0.2 s, J 4.6 kg·m², c 0.0072, 양변에 같은 0.4 s 1차 필터. 힘 수지가 닫히지 않는 출력 토크·바퀴 브레이크 토크 채널은 쓰지 않습니다(docs/31). 기록에서 이 맵 기반 힘으로 얻은 질량은 기록된 엔진 토크(Tier 1)로 같은 회귀를 한 값과 0.1–0.5 % 안에서 같았습니다(`acc-20261020-192243` 19,561 대 19,528, `gear-20261020-151650` 19,693 대 19,669, `acc-20261020-190844` 19,720 대 19,637 kg).
- 정보 구간: 적용 스로틀 ≥ 0.1, 서비스 브레이크 < 0.002, 리타더 0, 엔진브레이크 꺼짐, 1–14단에 클러치 붙음(|rpm − 차속에서 본 rpm| ≤ 4 % + 30 rpm), 같은 단, 5 m/s 이상, 850–2,250 rpm, 토크 모델이 요구보다 500 Nm 넘게 뒤처지지 않음, φ ≥ 0.25 m/s², |피치| ≤ 0.1 rad. 이 조건이 표본 앞 1.5 s(필터·차체 지연·토크 상승)와 뒤 1.0 s 동안 계속 참일 때만 그 표본을 씁니다(1.0 s 지연선). SDK 단 번호는 클러치가 열리기 시작하고 0.5 s 뒤에 바뀌므로, 뒤쪽 1 s가 변속 시작과 브레이크 직전을 걸러 냅니다. 정속 주행(φ 0.07–0.14)은 쓰지 않습니다. 구름 저항(0.0069–0.0082)과 경사 오차가 그대로 질량 오차가 되기 때문입니다.
- 추정: θ의 스칼라 RLS, 망각은 정보 구간 40 s, 표본 잡음 0.15 m/s²(20 Hz 표본의 상관을 셈), 잔차는 예측 σ의 3배에서 자릅니다. 정보 구간이 아니면 θ와 P를 그대로 둡니다. 범위 10–44 t.
- 사전값: `mass_prior_kg` > 0이면 그 값(상대 σ 10 %), 0이나 NaN이면 20.3 t(σ 40 %)에서 시작합니다. 사전값이 1 t 넘게 바뀌면 다시 시작합니다.
- 변화 감지: 정규화 잔차의 평균(정보 구간 2 s)이 2.5를 넘으면 공분산을 사전값 수준으로 다시 엽니다. 사전값 없이 트레일러를 달거나 떼도 몇 초 안에 따라갑니다(수렴 뒤의 RLS는 잔차 자르기 때문에 1분 넘게 걸림). 기록 9개에서 잘못 다시 연 적은 없습니다.
- 출력: `mass_est_kg`(추정), `mass_sigma_kg`(1σ, P와 max(가정, 관측) 잔차 σ), `mass_valid`(정보 구간 8 s 이상이고 σ/m ≤ 5 %, 즉 주행 자료로 확인됨). 제어기는 추정값을 1.5 t/s로 제한해서 씁니다. `C.est.adaptive = false`면 제어기는 20.3 t 고정이고 추정기는 계속 돕니다(예전 제어기와 비교용).
- 입력원: `actuation_valid`가 true면 `throttle_applied`·`brake_applied`·`retarder_applied`(SDK 적용값; NaN이나 음수인 항목은 자기 명령), false면 한 스텝 전의 자기 명령을 씁니다. 적용 스로틀은 변속 중 스로틀 차단을 보여 주므로 더 낫고, ACC가 꺼져 있을 때(운전자 주행)도 배웁니다. 자기 명령만 쓰면 ACC가 켜져 있을 때만 배웁니다.
- 브레이크 효율 `k_brake`(측정 표 대비 단위 입력당 감속): 처음에는 추정 질량에서 정한 배율(`acc_brake_scale`)이고, 브레이크가 0.4 s 넘게 걸려 있고 3 m/s 이상·리타더 5단과 엔진브레이크가 아니면 측정 감속(타력과 리타더 몫을 뺀 것)을 같은 0.3 s 지연을 건 표 감속과 비교해 0.5 s 시정수로 배웁니다. 표보다 센 쪽으로는 배우지 않습니다(표가 큰 입력에서 일부러 약하게 잡혀 있음). 사전값 없이 가속 한 번 없이 바로 제동하는 무거운 트럭은 질량 추정이 20.3 t에 머무는데, 이 학습이 없으면 40 t에서 브레이크가 절반만 들어 `lead_emergency_stop`과 `stopped_vehicle`에서 충돌했습니다(학습 뒤 최소 간격 4.6 / 4.5 m). 학습값은 질량을 이미 담고 있으므로 그 뒤 질량 추정이 바뀌어도 곱하지 않고, 추정기를 다시 시작하거나 공분산을 다시 열면 잊습니다. 게임 기록 재생에서 브레이크 중 학습값은 트레일러 연결 0.95–0.98(측정 표가 게임과 맞음), 트럭 단독 0.60(가벼운 쪽 배율 그대로)이었습니다.

**질량이 들어가는 곳**:
- 배분기: 타력 감속(구름 저항은 m에 비례, 공기·엔진 마찰은 힘이라 1/m), 리타더 1–4단(1/m), 5단(2.3 × 20.3/m), 역스로틀 맵(m + 엔진 쪽 관성, 구름 저항), 역브레이크 표(`acc_brake_scale`): 20.3 t보다 무거우면 단위 입력당 감속 × 20.3/m(브레이크 토크 고정), 가벼우면 12 t에서 0.6까지 보간. 트럭 단독은 트레일러 브레이크가 없어 단위 입력당 덜 섭니다(0.1 → 1.35 대 2.38, 0.3 → 3.57 대 4.72 m/s², docs/31 서비스 브레이크, 비율 0.57 / 0.76).
- MPC: 예측 모델은 가속도 단위이고 배분기가 그 질량으로 페달을 맞추므로 모델의 동역학은 바꾸지 않고, 경로별 도달 범위를 질량으로 다시 냅니다. u1 하한(타력 + 리타더 4단), u1 상한(0.85 × 전부하 가속, 측정값에서 구름 저항을 뺀 몫 × 20.3/m), 총 하한(타력 + 리타더 4단 + 브레이크 1.0 감속 × `k_brake`의 95 %, 40 t면 비상 −6.0 대신 약 −5.1). 이 선택의 근거는 아래 "질량별 폐루프"의 지연 식별입니다. 질량을 맞게 주면 a_des → 가속도 응답이 질량과 거의 무관하므로 Adaptive MPC(매 스텝 모델 갱신, 평상·비상 두 블록)를 쓰지 않았고, 코드 크기와 스텝 시간이 거의 그대로입니다.

### 폐루프: `acc_closed_loop.slx`

제어기(0.05 s)와 플랜트(5 ms)를 Model 블록으로 잇고, 명령에 35 ms 지연(게임 1 프레임 + 표본 하나, docs/31 "제어 루프 지연")을 둡니다. 선행차와 운전자 입력은 `scn_lead`, `scn_disc`(시나리오에서 생성)이고, `Controller` 블록을 SIL 모드로 바꾸면 생성 코드로 돕니다. 브레이크 온도는 80 °C로 고정입니다. 질량 쪽 입력은 `scn_grade`(플랜트 경사 [t sin θ], 제어기에는 asin으로 `pitch_rad`), `scn_mass_prior`, `scn_pitch_known`, `scn_act_valid`이고, `actuation_valid`일 때 플랜트의 적용 스로틀(변속 중 차단 포함)과 지연된 브레이크·리타더 명령을 추정기에 줍니다. 플랜트 질량은 플랜트 모델 작업공간의 `P.veh.m`이고, 구동·리타더·브레이크는 힘으로 그대로 두므로 단위 입력당 감속은 1/m로 변합니다(15 t 미만은 `P.veh.trailer = 0`인 트럭 단독).

- 예전 고정 맵은 무거울수록 브레이크·리타더가 기대의 20.3/m만 들어 30 t에서 정지 간격이 0.8–2.6 m, 40 t에서 충돌 2건입니다. 적응 제어기는 12–40 t 모든 시나리오에서 정지 간격 3.8 m 이상(목표 5 m, 크리프 포함 플랜트)입니다.

- 맞는 사전값에서 30–40 t의 저크가 4.0–4.3 m/s³로 사전값 없음(3.3–3.5)보다 큰 것은 리타더 단이 무거울수록 약해져 단 변경이 늘고(68 → 72회) 그 사이를 브레이크가 메우기 때문입니다. 12 t 맞는 사전값의 5.2 m/s²·5.4 m/s³는 위 한계 절의 가벼운 쪽 브레이크 배율 때문입니다.
- 추정기 변형(`mass_mixed`): 경사 +2 % / −1 % 구간에 피치를 주면 20.3 / 40 t가 +1.2 / +0.3 %, 피치를 0으로 주면 +50.6 / +4.9 %(첫 가속이 오르막). 적용값 대신 자기 명령으로 배우면 +3.8 / +1.2 %(변속 중 스로틀 차단을 못 봄).
- `stop_no_lead`(크리프): 수정 전 제어기는 12 t에서 0.99 m/s로 계속 기어가고 CRUISE에 머뭅니다. 수정 뒤 12 / 20.3 / 40 t에서 7.05 / 4.70 / 5.15 s에 HOLD(30 t도 HOLD), 최대 브레이크 0.26 / 0.20 / 0.45, 20 s의 resume은 무시합니다.

## 코드 생성 (`generate_acc_code`, `verify_acc_codegen`, `compile_generated`)

- ERT, C++ 클래스 `ets2::AccController`, 고정 스텝 0.05 s 단일 레이트, 동적 메모리 없음, 파라미터 인라인, SIMD 확장 없음, 하드웨어 x86-64(Windows64, SIL 호스트와 같게; 코드는 `<stdint.h>` 고정폭 형을 써서 Linux x86-64 g++에서도 그대로 빌드되도록 함).
- `generated/`(packNGo 결과): `ACC_Controller.h/.cpp`, `ACC_Controller_data.cpp`, `ACC_Controller_private.h`, `ACC_Controller_types.h`, `rtGetInf.*`, `rtGetNaN.*`, `rt_nonfinite.*`, `complex_types.h`, `coder_posix_time.c/.h`(QP 해법기의 시간 함수, MathWorks 런타임 파일), `ert_main.cpp`(예제 main, 노드에는 넣지 않음).
- 검증: 폐루프 4개(선행 −4, 15 s 스톱앤고, 비상 정지, 40 t 플랜트의 `mass_mixed` 180 s: 질량 추정이 20.3 → 40 t로 움직임)에서 제어기 입력 18개를 기록해 `ACC_Controller.slx`를 Normal과 SIL로 다시 돌림. 출력 9개 최대 차이 6.4e-13(질량 출력은 0, 판정 |차이| ≤ 1e-9 × max(1, |y|)), 폐루프 기록 대 Normal 재생 1.1e-11 이하. SIL 스텝 시간(/Od 디버그 빌드, 이 PC) 평균 3.4–4.0 ms(질량 적응 전 3.5 ms), 최대 5.4–21.6 ms(다른 MATLAB 작업이 같이 돌 때 잰 값이라 최대는 OS 지연이 섞임; 이전 측정 5.3 ms). 질량 추정기는 스칼라 RLS와 표 보간 몇 개라 스텝 시간에 거의 영향이 없습니다.
- 생성 코드 `ACC_Controller.cpp` 2.32 MB, 33,328줄(이전 2.30 MB). 클래스 밖 유틸리티 함수는 모델 이름을 붙여(`CustomSymbolStrUtil = '$R$N$C'`) `ACC_Controller_rt_powd_snf`, `ACC_Controller_rt_hypotd_snf`, `ACC_Controller_div_nde_7h8hU5qm`입니다(LCC 생성 코드의 `rt_powd_snf` 등과 겹치지 않음). 그 밖의 외부 심볼은 MathWorks 런타임 파일(`rtGetInf`, `rtGetNaN`, `rt_nonfinite`의 `rtInf`·`rtNaN` 등, `coder_posix_time`)로 예전과 같습니다.
- Embedded Coder 빌드가 `ert_main.cpp`까지 MSVC 2022로 링크하고(`codegen/ACC_Controller.exe`), `compile_generated()`가 `generated/`만으로 `example/acc_smoke_main.cpp`를 다시 컴파일해 돌립니다.

ROS 2 노드에서 쓰는 법(50 ms마다 `step()`):

```cpp
#include "ACC_Controller.h"
ets2::AccController acc;
acc.initialize();
ets2::AccController::ExtU_ACC_Controller_T in{};   // enable, set_speed_mps, time_gap_s, ego_speed_mps,
in.enable = true; /* ... */                          // ego_accel_mps2, lead_valid, lead_gap_m, lead_speed_mps,
                                                     // lead_accel_mps2, resume, engine_rpm, gear(int32_t),
                                                     // pitch_rad, mass_prior_kg, actuation_valid(bool),
                                                     // throttle_applied, brake_applied, retarder_applied(int32_t)
acc.setExternalInputs(&in);
acc.step();
const auto &out = acc.getExternalOutputs();         // throttle, brake, retarder_step(int32_t),
                                                     // engine_brake(bool), a_des_mps2, mode(uint8_t),
                                                     // mass_est_kg, mass_sigma_kg, mass_valid(bool)
ets2::AccController::terminate();
```

컴파일할 소스는 `ACC_Controller.cpp`, `ACC_Controller_data.cpp`, `rtGetInf.cpp`, `rtGetNaN.cpp`, `rt_nonfinite.cpp`, `coder_posix_time.c`입니다. 입력 규약: `lead_gap_m`은 범퍼-범퍼, `gear`는 SDK 엔진 단(0 중립), `ego_accel_mps2`는 정지 중 0이어야 하고 안에서 0.1 s 1차 필터를 거칩니다. `resume`은 누르는 동안 true(한 스텝 이상). `retarder_step`은 정상 동작에서 0.4 s에 한 단씩 바뀌고, 하네스가 레버 키로 그 단까지 움직여야 합니다.

질량 추정 입력(뒤에 붙인 6개, 모두 0으로 두면 예전과 같이 돌고 추정기는 자기 명령으로 배움):
- `pitch_rad`: 도로 경사각, 오르막(기수 들림) 양수. 월드 위치에서 atan(Δ높이/Δ수평거리)를 지난 약 20 m(또는 ±10 m)로 구한 값을 권합니다. SDK 차체 피치(`rot[1]`는 회전 단위, × 2π, 기수 들림 양수, 기록에서 위치 경사와 같은 부호 확인)는 서스펜션 성분(가속 1 m/s²당 0.003–0.006 rad 들림, 잡음 rms 0.003 rad)이 섞여 질량을 3–4 % 더 작게 봅니다. 모르면 0이나 NaN.
- `mass_prior_kg`: 트럭 + 트레일러 + 화물 질량(SDK 잡 화물 등). 0이나 NaN이면 20.3 t에서 시작. 1 t 넘게 바뀌면 추정기를 다시 시작합니다(트레일러 연결·분리, 화물 적재 때 보내면 됨).
- `actuation_valid`, `throttle_applied`, `brake_applied`, `retarder_applied`: true면 SDK 적용값(`ActuationState.throttle_applied`, `brake_applied`, SDK `truck.brake.retarder`)을 씁니다. NaN(스로틀·브레이크)이나 음수(리타더)인 항목은 제어기의 한 스텝 전 명령으로 대신합니다. 로더 0.42 미만에서 리타더를 브레이크로 접어 보내면 `brake_applied`에 그 몫이 들어가 정보 구간에서 빠지므로 그대로 두면 됩니다.
- `ego_accel_mps2`는 운동학적 가속도(dv/dt, 중력 미포함)여야 합니다. 기록에서 −`a_lin[2]`(SDK 로컬 z는 뒤쪽)가 dv/dt와 계수 1.01–1.03으로 맞고 g·sin(피치) 성분은 0.04–0.07배로 없다고 봐도 됩니다.
- 출력 `mass_est_kg`·`mass_sigma_kg`·`mass_valid`는 HUD·기록용입니다. 제어기는 안에서 같은 추정을 1.5 t/s로 제한해 씁니다. 추정 상태는 객체 수명 동안 유지됩니다(`initialize()`가 처음으로 돌림).

제품 노드 연결: `drive_speed`(`ros2/src/ets2_autonomy`)가 `longitudinal:=mpc`(기본)에서 이 코드를 씁니다. CMake가 `generated/`를 `acc_controller` 정적 라이브러리로 묶고, `src/control/acc_mpc.hpp`가 50 Hz 루프 안에서 50 ms 일정으로 `step()`을 부릅니다. 2026-10-21부터 노드는 `pitch_rad`를 GT 자세 높이의 최근 약 20 m 기울기(`src/control/road_grade.hpp`, 처음 10 m 전에는 NaN)로, `actuation_valid`·`throttle_applied`·`brake_applied`를 `/ets2/vehicle/actuation`에서, `retarder_applied`를 `/ets2/vehicle/powertrain`의 리타더 단에서 넣고, `mass_prior_kg`는 0(모름)으로 둡니다. 1 Hz 상태 줄에 `mass_t`와 `grade`가 나옵니다. `longitudinal_test`의 `AccMpc.StopsAndHoldsWithoutLead`는 설정 속도 0·선행차 없음에서 크리프 플랜트(브레이크 0.085와 균형)로 HOLD까지 가는지 봅니다.
- 입력: 선행차는 GT 교통의 가장 가까운 차(`LeadTracker`가 가속도 추정), 간격은 앞범퍼 기준(앞 오버행 `front_overhang_m` 1.5 m, 미측정 추정). `gear`는 `/ets2/vehicle/actuation`의 엔진 단, `ego_accel_mps2`는 `VehicleState.acceleration_base_mps2[0]`, `resume`은 운전자가 가속 페달을 0.2 넘게 밟을 때입니다.
- 차로 끝: LCC 경로가 끝나는 곳에 정지한 가상 선행차를 두어 MPC가 세우고, HOLD가 되면 제어를 놓습니다.
- 리타더: 로더 0.42+이면 axes 4로 단과 엔진브레이크를 직접 냅니다(semantical `retarderN`). 아니면 단별 같은 감속의 브레이크 입력으로 접습니다(`AccMpc::folded_brake`).
- `longitudinal:=pid`는 예전 속도 PID와 간격 규칙입니다.

## 알려진 한계 / 남은 일

- 게임 주행(2026-10-21, 질량 적응 이전 코드): 트레일러 없이 실제 도로에서 `engage:=cruise`로 77–95 km/h 순항·선행차 추종을 했고 사용자는 "엄청 스무스"라고 했습니다. 같은 날 오버라이드 뒤 설정 속도 0에서 1.08 m/s로 기어가는 결함이 나왔고, 이 판에서 고쳤습니다(게임 미확인). 질량 추정·크리프 수정은 게임에서 아직 돌려 보지 않았습니다.
- 그 이전 기록: 게임에서 주행해 보지 않았습니다. 플랜트와 시나리오 결과는 모두 시뮬레이션입니다. 게임에서 확인한 것은 정지 상태 하나뿐입니다(2026-10-20 밤, 실제 도로·트레일러·리얼 오토매틱, 릴레이 + `drive_speed` 기본 MPC, 목표 0, LCC 끔, 로더 0.31이라 리타더는 브레이크로 접음). 결과: arm → 첫 스텝 OFF → HOLD, 브레이크 0.2, 속도 |v| < 2e-4 m/s 유지. 명령 50 Hz 전달, 거부 0, 명령 나이 p99 2.4 ms. 정지 이벤트로 해제(종료 코드 0).
- 2026-10-21 게임 시험(로더 0.44, 트럭 단독, 설정 속도 0, 선행차 없음)에서 운전자 스로틀 개입 뒤 HOLD → GO → CRUISE로 가서 1.08 m/s로 계속 기어간 문제는 위 정지 요청 모드 전이·정지 보조로 고쳤고 `stop_no_lead` 시나리오로 확인했지만, 게임에서 다시 돌려 보지는 않았습니다. 플랜트의 크리프 힘은 이 관찰 하나로 맞춘 가정이고(힘-속도 곡선 모양, 트레일러 연결 시 값 모름), 그 실행의 기록 파일이 저장소에 없습니다.
- 자동 변속: 게임은 발진 단을 2와 4 중에서 고르는데 규칙을 모릅니다(모델은 4). 스로틀을 갑자기 밟을 때의 킥다운(9 → 8, 1,126 rpm)은 재현하지 않습니다(정상 상태 규칙을 거기 맞추면 8 → 10 직후 바로 내림). 강제동 중 10 → 8 한 번 내림도 없습니다.
- 리타더 5단: 사다리 2.10 대 게임 2.46 m/s², 5단 + 브레이크 0.05/0.1은 2.90/3.51 대 2.47/3.07로 과대. 5단 해제 직후 저속(9 km/h) 감속 0.08 대 0.39. 배분기는 5단을 거의 쓰지 않으므로(시나리오에서 0회) 폐루프 영향은 작지만, 5단 경로는 폐루프로 검증되지 않았습니다. 평지 ACC에서 5단 감속(2.3–2.5 m/s²)은 대부분의 상황에 너무 크고, 쓸모는 내리막(플랜트 `grade` 입력은 있으나 미시험)에 있습니다.
- 브레이크: 0.02/0.05의 저속 값, 저속 ↔ 고속 전환 속도(20 → 43 km/h)는 측정이 없어 가정했습니다. 온도 페이드는 폐루프에서 80 °C 고정입니다. 9 km/h 아래 제동 곡선 1.6배(docs/31)는 넣지 않았습니다.
- 질량 추정은 게임에서 돌려 보지 않았고 기록 재생만 했습니다. 재생 결과는 트레일러 연결 19.5–19.8 t(공칭 20.3 t 대비 −1…−5 %), 트럭 단독 11.0–11.1 t입니다(docs/31의 11.97 t는 출력 토크 채널 회귀로 기준이 다름). 추정값은 "식별된 스로틀 맵이 맞는 질량"이라 배분기에는 이 값이 맞지만, HUD에 실제 질량으로 보이면 3–8 % 작게 보입니다. 맞추려면 `C.est`에 보정 배율을 둘 수 있지만 그러면 시뮬레이션 플랜트에서 3 % 크게 나와 넣지 않았습니다.
- 화물을 실은 트레일러 기록이 없어 30–40 t는 시뮬레이션뿐입니다. 무거울 때 브레이크가 20.3/m으로 약해진다는 가정(브레이크 토크 고정)도 확인하지 않았습니다. 게임의 트레일러 브레이크가 화물에 따라 세지면 실제로는 더 세게 서고(안전한 쪽), 반대면 `k_brake` 학습이 1–1.5 s 안에 따라갑니다.
- 경사: 피치 입력 없이 오르막에서 가속하면 오르막 힘을 질량으로 봅니다. `mass_mixed`에 +2 % / −1 % 경사를 넣고 피치를 주지 않으면 20.3 t가 30.6 t(+51 %), 40 t가 42.0 t(+5 %)로 나옵니다(피치를 주면 +1.2 % / +0.3 %). 정보 구간이 가속 구간뿐이라 처음 가속이 오르막이면 크게 틀립니다. 위치 기반 경사(권장)나 차체 피치(질량 −3…−4 % 치우침)를 꼭 넣어야 합니다. 1 % 경사 = 0.1 m/s²입니다.
- 정속 주행만 하거나 가속 없이 제동만 하면 질량 추정은 움직이지 않습니다(사전값 그대로). 그 동안의 안전은 브레이크 효율 학습이 맡습니다(40 t·사전값 없음에서 비상 정지 최소 간격 4.6 m). 구동 쪽(스로틀 맵)은 추정 전까지 20.3 t 기준이라 무거운 트럭의 첫 가속은 PI 적분이 메울 때까지 느립니다.
- 12 t(트럭 단독)에서 사전값이 맞을 때 `lead_brake_4`의 최대 감속이 4.1 m/s²(평상 한계 3.0을 넘음), 저크 5.4 m/s³입니다. 가벼운 쪽 브레이크 배율 0.6이 큰 입력(게임 0.3에서 0.76)에서는 작고, 학습은 표보다 센 쪽으로 가지 않기 때문입니다(보수적 선택). `C.veh.brk_light_k`로 조정합니다.
- 변속 공백(0.73 s, 첫 변속은 터보 지연까지 1 s 남짓)은 MPC 모델에 없고 외란으로 보입니다. 설정 속도 가속 중 게임 변속기의 11 → 13 → 12 왕복(플랜트에서도 재현)이 가속을 2 s쯤 끊습니다.
- 선행차 가속도 입력의 잡음, 선행차 인식 끊김(0.5 s 뒤 CRUISE), 센서 지연은 시험하지 않았습니다.
- 생성 코드가 큽니다(`ACC_Controller.cpp` 2.32 MB, 약 33,300줄). 온라인 출력 가중(`y.wt`)과 예측 80 스텝 때문에 QP 행렬을 매 스텝 만들고, 두 MPC가 각각 코드를 가집니다. 고정 가중 제어기를 모드별로 따로 두거나 예측을 줄이면 작아지고 빨라집니다.
- 과제의 "최소 간격 soft = d0 + th·v"는 추종 목표로 쓰고 soft 하한은 3 m + 0.5·th·v로 두었습니다(위 설명). 하한을 바꾸려면 `C.fol.safe_frac`, `C.fol.d0_safe`입니다.
- `fit_auto_shift.m`의 발진 클러치 맞춤은 변속 규칙을 다듬기 전의 모델로 돌린 값이고, `acc_plant_params.m`에는 그 값을 옮겨 두었습니다.
