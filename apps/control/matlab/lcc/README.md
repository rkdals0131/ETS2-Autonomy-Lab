# 트럭 차로 유지(LCC) 횡방향 제어기 (Adaptive MPC + Embedded Coder)

레퍼런스 트럭(Scania S 6x2 태그리프트, 태그 올림, 빈 박스 트레일러 연결 약 20.3 t 또는 트럭 단독, [docs/31](../../../../docs/31_plant_parameters.md))의 차로 유지 제어기입니다. 상위는 속도마다 예측 모델을 바꾸는 Adaptive MPC(MPC Toolbox)이고, 2026-10-21부터 게임의 상대 조향 입력 u 자체를 계획합니다(아래 "게임 지연 반영 재설계"). 출력 계약은 그대로 앞바퀴각 목표와 각속도이고, 노드의 [VirtualEps](../../../../ros2/src/ets2_autonomy/src/control/virtual_eps.hpp)가 이것을 u로 바꿉니다. MPC가 조향하는 동안 목표는 측정 바퀴각이라 VirtualEps의 P항이 0이고, 각속도 피드포워드가 계획한 u를 그대로 만듭니다. `LCC_Controller` 하나를 Embedded Coder로 C++ 클래스 `ets2::LccController`로 만듭니다. 비교 기준(베이스라인)은 지금의 [lateral_controller.hpp](../../../../ros2/src/ets2_autonomy/src/control/lateral_controller.hpp)(곡률 피드포워드 + 선형화 pure pursuit)를 MATLAB으로 옮긴 `lcc_baseline.m`이고, 같은 플랜트에서 돌립니다. 폴더 구조와 코드 생성 방식은 [ACC](../acc/README.md)와 같습니다.

## 실행

MATLAB에서 이 폴더로 이동한 뒤:

```matlab
identify_lcc_plant();     % 게임 기록 재분석 → results/plant_identification.json (기록 캐시가 없으면 약 1분)
build_lcc_plant();        % lcc_plant.slx: 조향 액추에이터(VirtualEps + 게임 조향) + 트럭·트레일러 운동학 + 차로 센서
build_lcc_controller();   % LCC_Controller.slx
build_lcc_closed_loop();  % lcc_closed_loop.slx (플랜트 Model 블록 + 제어기 variant: 베이스라인 / MPC)
validate_lcc_plant();     % 게임 기록 재생·주파수 응답·폐루프 비교 → results/plant_validation.json, plant_*.png (약 3분)
run_lcc_scenarios();      % 17개 시나리오 × 트럭 단독·트레일러 × 베이스라인·MPC → results/scenario_*.json/png, scenarios_summary.json (약 12분)
run_lcc_scenarios(Wander=0.0013, Tag="_wander", Plot=false);   % 같은 것, 게임 직선 흔들림 외란 포함 → scenarios_summary_wander.json
generate_lcc_code();      % C++ 생성·컴파일(codegen/, git 제외) → generated/에 소스 복사 (약 1.5분)
verify_lcc_codegen();     % 생성 코드 SIL 대 모델 비교 → results/codegen_verification.json (약 8분)
compile_generated();      % generated/만으로 MSVC /O2 컴파일 + example/lcc_smoke_main.cpp 실행(스텝 시간 출력)
```

`run_lcc_scenarios(Rebuild=true)`는 세 .slx를 다시 만들고 돌립니다. `.slx`는 모두 build 스크립트로 다시 만들어지므로 모델을 직접 고치지 않습니다.

- MPC 블록은 제어기 객체를 기본 작업공간에서만 찾습니다. 그래서 `LCC_Controller.slx`의 InitFcn이 `lcc_controller_init`를 불러 `mpcLcc`를 기본 작업공간에 만듭니다. 나머지 파라미터 `C`는 모델 작업공간에 있고 `lcc_controller_params.m`에서 옵니다.
- 폐루프의 제어기 선택은 기본 작업공간 변수 `LCC_CTRL`(1 베이스라인, 2 MPC)입니다. 실행 스크립트가 `SimulationInput`으로 넣고 끝나면 지웁니다.
- 플랜트 파라미터는 `lcc_plant.slx` 모델 작업공간의 `P = lcc_plant_params(...)`와 차로 표 `LANE = lcc_lane(...).tab`이고, 시나리오가 `setVariable(..., "Workspace", "lcc_plant")`로 바꿉니다.
- 기록은 `lcc_load_recording("<run>")`가 읽어 `cache/<run>.mat`에 둡니다(git 제외).

## 측정 다시 보기: 트레일러 연결 시 "언더스티어"가 아님

표시: ✔ 기록에서 확인 / 맞춤 = 기록에 맞춘 값 / 추정 = 근거가 약하거나 가정.

docs/31의 트레일러 연결 유효 축간거리 3.18 → 3.30 m(언더스티어 K 0.0003–0.0006)는 SDK 국소 각속도 `v_ang[1]`에 2π를 곱해 요레이트로 쓴 값입니다(`apps/sysid/analyze_sysid.py`). 같은 기록에서 SDK 헤딩(`rot[0]`, 회전 단위)을 미분한 요레이트로 다시 계산하면 다릅니다(`identify_lcc_plant.m`).

- ✔ 헤딩 변화율 / `v_ang[1]` = 6.545(트레일러, `sysid-20261020-153130`), 차로 시험 곡선에서는 6.7–7.0입니다. 트럭 단독(`sysid-20261020-113045`)은 6.233으로 2π(6.283)에 가깝습니다. 트레일러가 붙으면 `v_ang`이 요레이트를 4–11 % 작게 보입니다(원인 모름).
- ✔ 헤딩 미분으로 본 트레일러 연결 유효 L은 기하값 3.158 m보다 **짧고** 속도에 따라 더 짧아집니다. 차로 시험 기록의 정상 곡선(폐루프)도 같은 값을 줍니다.

- ✔ 그래서 게임의 베이스라인 곡선 평균 오차 +12.5 ~ +20.8 mm는 **안쪽**입니다(lateral.jsonl에서 곡률이 양(왼쪽)인 곡선의 오프셋이 양(왼쪽)). docs/31·29는 "바깥쪽(언더스티어 방향)"이라고 적었지만 부호가 반대입니다. 제어기는 3.158 m로 각을 내는데 트럭은 3.04 m처럼 돌기 때문에 더 돌고, 안쪽으로 붙습니다. docs의 제안(피드포워드에 +K·a_y)을 넣으면 오히려 커집니다.
- ✔ 정상 곡선의 헤딩 오차 / 곡률(기준점 = 구동축의 옆미끄럼 위치): 트레일러 +0.042(25) ~ +0.090 m(97 km/h), 트럭 단독 −0.027 ~ −0.098 m. 곡선에서 구동축이 차로 접선에 대해 이만큼 비스듬히 갑니다.
- ✔ 트레일러: 히치가 구동축 뒤 a에 있는 운동학 트레일러 r_t/r = (v − a·s)/(L_t·s + v)를 사인 12개(트레일러/트럭 요레이트 이득·위상)에 맞추면 a = 0.478 m, L_t = 7.851 m입니다(구성값: 트럭 hook z 2.026 → 구동축 뒤 0.508 m, 트레일러 hook → 가운데 축 7.923 m). docs의 1차 지연(L_t/v, a = 0)으로는 1 Hz 위상이 20 km/h에서 −84°인데 게임은 −115°이고, 히치 오프셋을 넣으면 −114°입니다.
- ✔ 조향 정상 상태: 차로 시험 정상 곡선 10개(40–100 km/h)에서 명령/적용 비 u/eff가 LS c/a의 0.974배(0.966–0.989)입니다. 자동 복원이 LS 맞춤보다 2.6 % 약합니다. 플랜트는 c × 0.974를 씁니다.

## 플랜트: `lcc_plant.slx` (ode4 5 ms)

입력 `wheel_angle_target`(rad), `wheel_rate_ff`(rad/s), `speed`(m/s), 출력 `lateral_error`(m, 왼쪽 +), `heading_error`, `wheel_angle`(실제), `hitch_angle`, `curvature_preview`(61), `kappa_back`, `s`, `X`, `Y`, `psi`, `psi_trailer`, `yaw_rate`, `lat_accel`, `eff`, `u`(게임 조향 입력), `kappa`입니다. 기준점은 노드와 같은 구동축(태그 올림의 뒤 기준점)입니다. 속도는 시나리오가 주는 일정 속도이고(lane_test.py가 페달 PI로 속도를 유지) 5 ms Memory를 거칩니다(Model 블록에 직접 피드스루가 없어야 폐루프에 대수 루프가 생기지 않음).

- `SteeringActuator`: 노드의 VirtualEps(50 Hz, `lcc_virtual_eps.m`, 코드 그대로, 4x2 표·대역폭 6.5) → 게임 지연 `P.steer.delay`(플랜트 검증은 sysid 때의 1프레임 1/60 s, 시나리오는 `lcc_scenario_input`이 게임에서 잰 3프레임 `P.steer.delay_game` = 0.05 s를 넣음) → 측정 상대 조향 d(eff)/dt = a(v)·u − 0.974·c(v)·eff(6x2 LS 표, 트레일러/트럭 단독 각각, 88·97 km/h는 4x2 값으로 가정) → 바퀴각 = 0.70·eff(eff 한계 ±0.94, 가정).
- `Vehicle`: 운동학 bicycle r = v·tan δ / L_eff(v), L_eff = 3.158 + ΔL(v), 기준점 옆속도 −slip(v)·r(위 표의 맞춤값), 운동학 트레일러 r_t = (v·sin γ + (v_y − a·r)·cos γ)/L_t, 차로(Frenet: s, e_y, e_ψ)와 세계 좌표(X, Y, ψ)를 함께 적분합니다. 선택 외란: 느린 요레이트 흔들림 Σ A·sin(2πf·t + φ), f = 0.017/0.029/0.047 Hz(아래 "직선 흔들림").
- `LaneSensor`(50 Hz): 노드의 `LanePath::curvature(s + i, 6)`(창 6 m 평균 곡률)과 같은 미리보기. 차로 표는 0.5 m 격자의 헤딩 θ(s)이고 곡률은 그 기울기라서, 차로 좌표 오차와 세계 좌표가 어긋나지 않습니다.

**직선 흔들림(추정).** 게임의 직선 구간은 150 m 뒤에도 ±2–3 cm, 주기 20–40 s로 천천히 흔들립니다(RMS 7–19 mm). 플랜트는 외란이 없어 1 mm 아래입니다. 원인은 모르고(패드 경사, 위치 신호 등), 요레이트에 느린 사인 3개(진폭 각 0.0013 rad/s, `P.dist.amp_game`)를 넣으면 베이스라인 직선 RMS가 비슷해집니다(30 / 80 / 100 km/h 트레일러: 게임 7.1 / 15.8 / 18.8, 플랜트 12.8 / 14.5 / 17.1 mm). 같은 외란이 곡선에서는 게임보다 RMS를 크게 만들어서(트럭 R400 60: 게임 5.9, 플랜트 15.5 mm), 시간 함수 외란은 대략의 크기만 맞습니다. 주 비교는 외란 없이, 외란 비교는 따로 적었습니다.

**액추에이터 근사(옛 MPC용, 지금은 쓰지 않음).** 2026-10-21 재설계 전의 MPC는 VirtualEps + 프레임 지연 + 게임 조향을 "계획한 바퀴각을 1차 지연 τ로 따르는 것"으로 봤습니다. 1프레임 지연 플랜트에서 맞춘 τ는 0.001(20) / 0.059(40) / 0.071(60) / 0.059(80) / 0.073 s(100 km/h), 적합 95.5–99 %입니다(`validate_lcc_plant`의 4번이 아직 이 값을 냅니다). 게임 지연(3프레임)에서는 이 근사가 틀립니다: 계획 각 사인에 대한 실제 바퀴각의 이득이 1 Hz 1.28, 2 Hz 1.51(1프레임에서는 1.11, 1.19), 등가 지연이 2 Hz에서 47 ms(1프레임 11 ms)입니다. VirtualEps의 P항(대역폭 6.5)이 늦은 적용값에 대해 돌면서 2 Hz 근처에 공진을 만들기 때문입니다(스크래치 계산, 아래 재설계 참고). 지금 MPC는 이 내부 루프를 쓰지 않고 측정 조향 + 지연을 직접 모델로 씁니다.

## 제어기: `LCC_Controller.slx` (서브시스템 `LCC_Controller`, 0.02 s, 원자 서브시스템)

`MPC_Prep`(MATLAB Function → `lcc_mpc_prep.m`) → `model_bus`(A, B, C, D, X, U, Y, DX) → `MPC`(Adaptive MPC Controller, `mpcLcc`) → `MPC_Post`(→ `lcc_mpc_post.m`), 마지막 상태 `[예측 헤딩 오차; 곡률 바이어스; MPC 활성; u(k−1); u(k−2); u(k−3)]`은 Unit Delay `memory`로 돌아갑니다.

**왜 Adaptive MPC인가.** 예측 모델은 속도 v에 대해 거의 선형으로 바뀌고(v·e_ψ, v/L·δ, v²·κ), 한 지평선(1.5 s) 안에서는 속도가 거의 일정합니다. 그래서 매 스텝 현재 속도·축간거리·트레일러 여부로 모델 하나를 만들어 넣는 Adaptive MPC가 맞습니다. LTV(지평선의 스텝마다 다른 모델)는 속도 변화가 없으면 같은 결과에 계산만 늘고, 게인 스케줄 MPC는 속도 구간마다 제어기를 따로 둬서 생성 코드가 커지고 축간거리(태그 상태)와 트레일러 조합까지 나눠야 합니다.

**예측 모델**(`lcc_mpc_model.m`, 연속식 → expm으로 ZOH 이산화):

- 상태 x = [e_y, e_ψ, δ, γ, m_1, m_2, m_3]: 횡오차(구동축, 왼쪽 +), 헤딩 오차, 실제 바퀴각(= 0.70·적용 조향), 히치각(트레일러 없으면 출력에 쓰지 않음), 아직 게임에 닿지 않은 지난 입력 m_i = u(k−i).
- MV u = 게임의 상대 조향 입력(정규화, VirtualEps가 보내는 값 그대로), MD w = 차로 곡률 + 바이어스(미리보기, 지평선 각 스텝 가운데 지점 v·Ts·(k+0.5) 앞의 값).
- ė_y = v·e_ψ − slip(v)·(v/L_e)·δ, ė_ψ = (v/L_e)·δ − v·w, δ̇ = 0.70·a(v)·u(t − D) − 0.974·c(v)·δ(측정 조향, virtual_eps.hpp 표, c는 폐루프 정상 곡선 보정), γ̇ = (v/L_e)(1 + (a + slip)/L_t)·δ − (v/L_t)·γ. L_e = wheelbase_m + ΔL(v)(트레일러/트럭 단독 표), slip·a·L_t는 위 식별값입니다.
- 지연 D = 0.05 s(상태 프레임 → 명령이 작용하는 프레임, 게임 3프레임) = 2.5 스텝: 한 스텝 동안 u(k−3)이 앞 10 ms, u(k−2)가 뒤 10 ms에 작용하도록 나눠서 정확히 이산화합니다(`C.act.delay_s`, `nd` 2, `frac` 0.5).
- 출력 y = [e_y, e_ψ, δ, a_y,corr, e_t, j]. a_y,corr = v·ė_ψ(차로가 요구하는 v²·κ 위에 제어기가 더하는 횡가속도), e_t = e_y − (a + L_t)·e_ψ + L_t·γ − (a + L_t)²/2·w(트레일러 유효 축의 횡오차, 선형화, 트레일러일 때만), j = v·(v/L_e)·δ̇(트럭의 횡 저크, m/s³, 이번 스텝에 작용하는 입력으로).
- e_ψ의 기준은 0이 아니라 slip(v)·κ(곡선에서 정상 헤딩 오차)입니다.
- 초기 상태: e_y, e_ψ, γ는 측정값, δ는 측정 바퀴각을 측정 나이 `C.act.age_s`(지금 0)만큼 그 사이 작용한 입력으로 앞으로 민 값, m_i는 메모리(처음이나 폴백 뒤에는 측정 각을 유지하는 입력 c·δ/(0.70·a))입니다.

**제약**: |u| ≤ 0.95(VirtualEps가 1에서 자름), |δ| ≤ 0.63 rad(eff 0.9, soft ECR 0.1), |a_y,corr| ≤ 3.0 m/s²(soft ECR 1).

**관측기(적분 동작) 둘**: (1) 곡률 바이어스: 지난 스텝의 모델 예측 헤딩 오차와 측정값의 차이로 곡률 바이어스 κ_b를 시정수 2 s로 추정하고(|κ_b| ≤ 1.5e-3 /m, 5 m/s 아래 정지) 미리보기 곡률에 더합니다. (2) 조향 입력 바이어스(2026-10-21): 지난 스텝의 모델 예측 바퀴각과 측정값의 차이로 u_b를 시정수 1 s로 추정하고(|u_b| ≤ 0.3) 게임에 u + u_b를 보냅니다(게임 조향이 VirtualEps 표와 다를 때). 모델의 ΔL·slip이 틀리거나 요레이트 외란이 있어도 정상 오차가 남지 않게 합니다(적분 동작). 트레일러 플래그를 일부러 false로 준 R400 80 km/h(모델 불일치)에서 곡선 평균 −2.5 mm, 최대 9.2 mm였습니다(재설계 전).

**상태와 폴백**(`status`, uint8): 0 꺼짐(enable false: 측정 바퀴각을 그대로, 각속도 0), 1 MPC, 2 QP 실패(status < 0) → 내장 폴백, 3 저속(2 m/s 아래) → 내장 폴백, 4 입력 이상(NaN, 축간거리 1.5–8 m 밖) → 측정 바퀴각 유지·각속도 0. 내장 폴백은 lateral_controller.hpp와 같은 곡률 피드포워드 + 선형화 pure pursuit(전방 6 + 0.7·v m)에 트레일러 ΔL을 넣은 것입니다. 폴백 뒤 MPC로 돌아올 때는 지난 입력을 측정 각을 유지하는 입력으로 다시 시작합니다.

## 트레일러 쓸림(off-tracking) 검토

운동학 트레일러의 정상 쓸림은 기하적입니다: 유효 축이 (L_t² − a²)/(2R) 안쪽(R400 7.7 cm, R700 4.4 cm, R200 15 cm, R60 51 cm, R40 77 cm), 뒤축(히치 뒤 9.23 m)은 조금 더 안쪽입니다. 트럭이 차로 중심에 있으면 이것은 제어로 줄일 수 없고, 줄이려면 트럭이 바깥으로 그만큼 비켜야 합니다(트럭 1 mm 바깥 = 트레일러 약 1 mm 덜 안쪽).

- MPC 출력 e_t(트레일러 유효 축 횡오차)에 가중을 주는 항을 넣어 두었습니다(`C.w.trailer`, 기본 0). 튜닝 중 6(e_y 가중의 절반)으로 돌려 보니 R40 15 km/h에서 트럭이 87 mm 바깥으로 가고 트레일러 뒤축 안쪽 쏠림이 720 → 650 mm, R400 80 km/h에서 트럭 15 mm 바깥, 트레일러 74 → 59 mm입니다. 절반으로 줄이려면 트럭이 그 절반만큼(R40에서 약 36 cm) 바깥으로 가야 합니다.
- 고속도로 반경(R ≥ 400)에서는 쓸림이 8 cm 아래라 차로(3.5 m, 트레일러 폭 2.55 m 가정이면 한쪽 여유 0.47 m) 안이고, 트럭을 비키는 것이 손해입니다. 저속 급회전(교차로, R ≤ 60)에서는 트레일러 뒷바퀴가 안쪽 차선을 0.5–0.75 m 넘으므로 그때만 가중을 켜는 것(온라인 가중 또는 반경별 전환)이 맞습니다. 온라인 가중은 QP 행렬을 매 스텝 더 만들므로 지금은 넣지 않았습니다.
- 결과 표의 트레일러 뒤축 값이 MPC에서 줄어든 것(R400 80 km/h 95 → 74 mm)은 트럭이 안쪽으로 21 mm 붙던 것을 없앤 효과입니다.

### 게임 주행 1 (2026-10-21)

트럭 단독, 리얼 오토매틱, 크루즈 버튼 모드(provider `--follow`), 프랑스 고속도로 77–90 km/h, 약 3분. 기록은 `bridge/recordings/20261021-085242-39900571`(차량 상태 프로필, 이때는 노드 내부 신호·차로가 기록되지 않아 차로는 기록된 GT 자세를 provider에 `--snapshot -`로 다시 넣어 재구성). 사용자: "너무 과격", "직선에서 부들부들", "코너에서 덜 꺾음", "수동 차로 변경 뒤 LCC가 놓침".

- ✔ 직선 떨림: 조향 명령이 약 3–4 Hz로 ±0.3 흔들렸고(적용 조향 봉우리 3.1 Hz), 요레이트 잡음(1 s 이동평균과의 차 RMS)이 0.019 rad/s였습니다. 횡오차 자체는 ±0.5 cm로 작았습니다. 원인은 지도 차로 점이 float32라는 것입니다(원점에서 30 km면 2–4 mm 계단). 1.5 m 구간마다 헤딩이 ±3 mrad(구간 사이 표준편차 4.2 mrad) 튀고, MPC가 헤딩 오차·곡률 미리보기로 그것을 따라갔습니다. 재구성 차로 위 폐루프 시뮬레이션(`lateral_sim_test` `GameReplayExploration`)에 측정 지연(명령 → 적용 2–3프레임, 적용값 1프레임 늦게 읽음)을 넣으면 요레이트 잡음 0.021 rad/s로 게임과 같고, 지연 1프레임이면 0.008입니다. 같은 차로를 매끈하게 하면 0.004 rad/s, 조향 반전이 150 s에 1016 → 26회입니다.
- 수정: `LanePath`가 위치·헤딩·곡률을 ±8 m 국소 2차 맞춤(tricube 가중, `path_following.hpp` `local`)으로 냅니다. 횡오차도 맞춘 곡선 기준(`LanePath::offset`)입니다. 원 차로(`Float32MapLane`, 30 km 떨어진 float32 S자 곡선)에서 87 km/h·게임 지연 요레이트 잡음 0.0026(맞춤 없이 0.0092) rad/s, 차로 오차 최대 3.2 cm.
- ✔ 코너 "덜 꺾음": 160–163 s 곡선(곡률 8/km)에서 명령이 ±1로 떨면서 VirtualEps가 포화돼 요레이트가 차로보다 작았고 횡오차가 −1.1 m까지 갔습니다. 떨림을 없애면 같이 없어질 것으로 봅니다(△ 게임 미확인). 같은 곡선에 87 km/h로 들어가 횡가속도가 4.2 m/s²였는데, ACC 커브 속도 제한이 23 m 앞 pure pursuit 곡률 하나만 봐서입니다. 이제 차로 앞 700 m 곡률로 미리 감속합니다(`curve_speed.hpp`).
- △ 137–143 s에 운전자 입력 없이 재구성 차로에서 1.7 m 벗어났다 돌아왔습니다. 그 구간의 요레이트는 재구성 차로보다 더 돌았는데 오프셋은 반대쪽이라, 노드가 그때 쓴 차로가 재구성과 달랐던 것으로 봅니다(provider가 다른 시점에 시작해 다른 이음·분기를 냈을 가능성). 노드가 쓴 차로를 기록하지 않아 확인할 수 없었습니다. 이제 `/ets2/drive/lane`(1 Hz)과 `/ets2/drive/assist`(50 Hz)를 기록합니다.
- 진입 과격: MPC는 켜지는 순간 차로 중심으로 바로 갑니다(80 km/h, 1 m 오프셋에서 최대 횡가속 3.3 m/s²). 이제 노드는 켜질 때마다 지금 자세에서 차로 중심으로 가는 3차 Hermite 기준(`lane_merge.hpp`, 기준 횡가속 0.5 m/s², 최소 2 s)에 대한 오차와 그 곡률을 MPC에 넣습니다. 같은 경우 최대 횡가속 0.64 m/s², 넘침 3 mm(`SoftEngagement`).
- 수동 차로 변경: 예전에는 차로 폭 절반을 벗어나면 LCC를 그 세션 동안 끝냈습니다. 이제 조향 / 양보 / 차로 찾기 상태로 두고, provider가 새 차로를 내고 트럭이 그 안(차로 폭 1/4, 0.1 rad)에 들어오면 다시 잡아 합류합니다([브리지 문서](../../../../bridge/README.md#gt-도로-자동-주행)). △ 게임 미확인.

### 게임 지연 반영 재설계 (2026-10-21)

사용자: "더 스무스하고 더 정확하게 코너를 돌아야함", "가끔 막 오실레이션 있을 때도 있고"(트레일러 연결, 86 km/h, 기록 `bridge/recordings/20261021-163908-70c280d2`). 아래 시뮬레이션은 `lateral_sim_test`의 `CorneringWithGameDelay`·`CorneringReplayLane`·`CorneringRackMismatch`(레퍼런스 트럭 6x2 태그 올림, MPC에 축간거리 3.158 m, 플랜트는 측정 L_eff(v)·옆미끄럼·운동학 트레일러, 측정 조향 표, 60 Hz 게임 / 50 Hz 노드)입니다. **게임 지연 다시 재기.** ✔ 새 기록에서 `/ets2/drive/assist`의 상태 시각과 `/ets2/drive/state`의 명령 시퀀스를 맞추면, 명령은 그 상태 프레임 3프레임 뒤에 게임에 닿습니다(70 %, 2프레임 14 %, 4프레임 11 %). 닿은 프레임부터 작용하고(적용 조향 변화를 명령에 LS 맞춤하면 추가 지연 0프레임이 가장 잘 맞음, a 0.30·c 1.91 @ 82 km/h), 노드가 읽는 적용 조향은 자세와 같은 프레임입니다(나이 0, 4,136 중 4,125 샘플). 앞 기록에서 짐작한 "적용값 1프레임 늦음"은 이 기록에서는 보이지 않았습니다. 그래서 `C.act.delay_s` 0.05 s, `C.act.age_s` 0이고, 시험은 2–4프레임과 나이 0/1을 모두 돌립니다.

**원인 1: 옛 MPC는 게임 지연에서 안정 여유가 거의 없었습니다.** 옛 예측 모델은 VirtualEps + 1프레임 지연 + 조향을 "계획 각을 τ 0.06–0.07 s로 따르는 1차 지연"으로 봤습니다. 실제 지연이 3프레임이면 VirtualEps의 P항(6.5 rad/s)이 늦은 적용값에 대해 돌아 2 Hz 근처에 공진이 생기고(계획 각 → 실제 각 이득 1 Hz 1.28, 2 Hz 1.51), MPC가 그 대역까지 밀어서 루프가 거의 발진합니다. 옛 코드는 3프레임·나이 0에서는 버티지만, 4프레임(게임에서 11 %)이나 나이 1, 조향 표 속도 계수 ×1.4면 90 km/h에서 1.7 Hz 극한 순환으로 커집니다(VirtualEps 입력 ±1 포화, 요레이트 떨림 0.01–0.08 rad/s, 오프셋은 ±7 mm). "가끔 오실레이션"과 맞습니다(△ 게임에서 그 순간을 따로 확인하지는 않음).

**원인 2: 차로 자체가 흔들립니다.** ✔ 새 기록 16–21 s(provider 경로가 mod_ger_35 프리팹의 3 → 2 차로 감소를 지나는 내비 곡선)에서 차로 곡률이 +2.7 → −4.0 /km로 45 m에 걸쳐 내려가다 +4.1로 계단, 다시 −3.6까지 내려가다 0으로 계단입니다. 옛 MPC는 이것을 그대로 따라가서(오프셋 1–3 cm) 요레이트 ±0.08 rad/s(횡가속 약 ±2 m/s²), 조향 입력 ±0.4로 흔들었습니다. 비슷한 작은 일이 10–11, 38–39, 50, 64–73 s의 도로 이음(곡률 계단 2–4 /km)에도 있습니다. 보이는 도로 모양이 아니라 내비 경로의 모양이라, 정확히 따라가는 것이 오히려 흔들림입니다.

**바꾼 것.**

- MPC가 게임 조향 입력 u를 직접 계획합니다. 예측 모델의 조향부는 측정 조향 dδ/dt = 0.70·a(v)·u(t − 0.05 s) − 0.974·c(v)·δ 그대로이고, 아직 게임에 닿지 않은 입력 3개를 상태로 둡니다(2.5 스텝 지연, 반 스텝은 나눠서 정확히 이산화). 출력은 VirtualEps의 P항을 0으로 만들고(목표 = 측정 각) 피드포워드로 u를 그대로 보내게 합니다. 공진하는 내부 루프가 MPC 루프 밖으로 빠지고, 모델이 근사가 아니라 측정값이 됩니다. 입력 한계도 VirtualEps 포화(|u| ≤ 1)를 직접 씁니다(0.95).
- 조향 입력 바이어스 관측기를 더했습니다. 게임 조향이 VirtualEps 표(a, c)와 다르면 계획한 u로는 예측한 바퀴각이 안 나옵니다. 한 스텝 앞 바퀴각 예측과 측정값의 차이를 시정수 1 s로 적분해 입력 바이어스 u_b(|u_b| ≤ 0.3)를 추정하고 게임에는 u + u_b를 보냅니다. 이것이 없으면 표가 30 % 틀릴 때 곡선에서 3–5 cm 정상 오차가 남았습니다(옛 구조에서는 VirtualEps P항이 흡수). 시정수 0.5 s는 1 m 오프셋에서 바로 켤 때(합류 없음) 넘침이 69 → 82 mm로 커져 1 s로 뒀습니다(76–78 mm).
- 출력에 트럭 횡 저크 j = v·(v/L)·dδ/dt를 더하고 가중 0.2를 줬습니다. MPC가 1.5 s 미리보기 안에서 짧은 곡률 흔들림과 계단을 몇 cm 안쪽으로 가로질러 매끈하게 갑니다. 긴 곡선(완화 곡선)은 저크가 작아서 거의 그대로 따라갑니다.
- 노드 파라미터는 바꾸지 않았습니다. 미리보기 창만 넓히는 방법(`curvature_window_m` 20 m, 피드포워드만 저역 통과)은 MATLAB 복제 루프에서 오히려 나빴습니다(흔들림 곡선 최대 횡가속 1.6 → 3.0 m/s², R130 계단 오차 19 → 50 mm): 위치·헤딩 오차 피드백이 여전히 차로를 따라가면서 퍼진 피드포워드와 싸웁니다. 가중 e_y / e_ψ / Δu는 저크 가중과의 비만 바꾸고(파레토 한 줄), 예측 지평선 100 스텝도 결과가 같았습니다.

```cpp
#include "LCC_Controller.h"
auto lcc = std::make_unique<ets2::LccController>();   // ~1.4 MB: heap
lcc->initialize();
ets2::LccController::ExtU_LCC_Controller_T in{};
in.enable = lcc_enabled;
in.speed_mps = v;
in.lateral_error_m = p.offset;                 // LanePath::track at the rear (bicycle) reference point
in.heading_error_rad = std::remainder(yaw - lane.heading(p.s), 2 * M_PI);
for (int i = 0; i < 61; ++i) in.curvature_preview[i] = lane.curvature(p.s + i * 1.0, curvature_window_m);
in.wheel_angle_rad = 0.70 * applied_steering;  // SDK truck.effective.steering
in.wheelbase_m = axles.wheelbase();            // kinematic_axles: 3.158 tag up, 3.68 down
in.trailer_connected = trailer_connected;
in.hitch_angle_rad = trailer_connected ? hitch : 0.0;   // psi_truck - psi_trailer
lcc->setExternalInputs(&in);
lcc->step();                                   // every 20 ms (the node's 50 Hz loop)
const auto &out = lcc->getExternalOutputs();   // wheel_angle_cmd_rad, wheel_rate_cmd_rad_s, status (uint8_t)
u = eps.command(out.wheel_angle_cmd_rad / 0.70, out.wheel_rate_cmd_rad_s / 0.70, applied_steering, v, dt, eps_settings);
```

- 트레일러 쓸림 가중은 기본 꺼짐입니다. 저속 급회전에서 쓰려면 반경·속도에 따라 켜는 방법이 필요합니다.
- 관측기는 요레이트(헤딩) 바이어스와 조향 입력 바이어스를 봅니다. 기준점 옆미끄럼(slip) 오차는 작은 횡오차로 남습니다(smoke 예제의 단순 플랜트에서 1.5 mm, 재설계 전).
- MPC는 VirtualEps의 공식과 표(virtual_eps.hpp)를 알고 그 출력을 정합니다. VirtualEps 표나 `steering_angle_per_unit_rad`(0.70)를 바꾸면 `lcc_controller_params.m`의 `C.eps`·`C.angle_per_unit`도 같이 바꾸고 다시 생성해야 합니다(입력 바이어스 관측기가 작은 차이는 흡수).
- 차로 점 잡음은 위에서 다뤘습니다. SDK 위치 잡음은 시험하지 않았습니다.
