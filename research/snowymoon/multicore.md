# snowymoon 프록시(AA 켬)와 렌더 패스 동시 기록의 공존 설계 (B안)

2026-10-22. 대상은 [docs/28](../../docs/28_render_pass_parallel_prototype.md) §11의 M3c·M3d 동시 기록(`ot.cmd parallel_passes parallel --order concurrent`, core 0.54.3)과 snowymoon 프록시 `dxgi.dll`(sha256 `d819c168…`)을 같은 세션에서 쓰는 방법입니다. 정적 분석만 했습니다. 게임과 DLL은 실행하지 않았고, DLL 원본과 `ot/native/`는 건드리지 않았습니다. 표시는 ✔ 코드로 확인, △ 추정입니다.

주소: `dxgi+RVA`는 프록시(이미지 베이스 `0x180000000`), 나머지는 eurotrucks2.exe 1.61.1.9 RVA입니다. 괄호 안의 1.61.1.1 주소는 docs/28과 맞추려고 적었습니다. 배경은 [README](README.md) §4·§6·§9·§10, [sensor_coexistence](sensor_coexistence.md) §3·§9입니다.

## 결론 (3줄)

1. **B안은 가능합니다(정적 판정 ✔, 런타임 확인 항목 남음).** 동시 기록이 닿는 스노위문 상태는 장면 키 `c780e8`, uniform 합성 잎 `0x1A440`의 "프레임당 첫 카메라" 기록과 직전 객체 캐시, 카메라 링, 업로드 크기 `c735bc`, 리소스 `std::map` `c76810`과 생성 계수기뿐이고, 나머지(AA 상태 기계, 컨텍스트 바인드 전역, 히스토리 레코드)는 렌더 스레드에서만 움직입니다.
2. **필요한 것은 dxgi 코드 훅 2개, D3D11 장치 vtable 슬롯 포인터 교체, 합류점 재생입니다.** `0x1A890`(장면 키를 스레드 지역으로)과 `0x1A440`(실행자 스레드에서는 같은 계산을 하되 전역 대신 패스별 기록에 씀)에 훅을 걸고, 합류가 끝난 뒤 메인 스레드가 그 기록을 원래 큐 순서로 스노위문의 `0x84460`·`0x84670`에 넣습니다. 링을 사후에 정렬하는 방식으로는 모자랍니다(§5.2.4). `c76810`은 장치 vtable 슬롯 7·9·10을 감싸 실행자 스레드에서만 기존 풀 락을 잡게 하고, `c735bc`는 지금 풀 락으로 이미 지켜집니다.
3. **스노위문 때문에 다시 직렬화되는 몫은 정상 프레임에서 거의 0으로 봅니다(△).** 텍스처 뷰 생성(캐시 미스 때만)만 풀 락을 잡고, 재생은 프레임당 push 19회 이하·기록 1회입니다. 이득은 프록시 없는 M3d(주행+센서 −1.33 ms, 정차 −0.84 ms)와 같은 수준을 기대합니다. 가장 큰 위험은 스노위문 갱신(해시가 바뀌면 B안은 꺼짐)과, 런타임에 만들어지는 장면 스텁의 내용을 정적으로 못 본 것입니다(§12의 1번으로 닫음).

`d3d_sites.py`의 닫힘은 과대 근사입니다. 엔진 vtable 슬롯 간선은 "같은 오프셋 메서드를 가진 아무 객체"도 잇습니다. 반대로 엔진 장치 vtable이 아닌 함수 포인터(재질 composer 콜백 `call [rbx+0x10]` 등)는 따라가지 않아 빠뜨린 경로가 있을 수 있습니다(△). 그래서 §5.3의 vtable 감싸기에 슬롯별·스레드별 계수기를 두어 런타임에서 빠진 경로를 드러내게 합니다.

### 2.3 뷰 해제 경로

스노위문은 SRV·RTV·DSV를 객체별 vtable 사본으로 감싸고(`0x189E0`, ✔), `Release`가 0이 되면 소멸자 `0x15EC0`(SRV)·`0x15F80`(RTV)·`0x16000`(DSV)이 텍스처 레코드 참조 수 `+0xF0`을 원자 연산 없이 내린 뒤 0이면 `0x17E80`으로 `c76810`에서 지웁니다(✔). 기록 경로에서 뷰를 놓는 곳은 프레임 뷰 등록 `0x2AE6B0`(덮어쓸 때 Release)과 리소스 준비 `0x32E540`의 해제(`0x23BAE0`)이고 둘 다 풀 락 안입니다(✔ `pool_guard.cpp:23`·`:36`).

### 3.2 업로드 쪽

| 상태 | 쓰기 | 읽기 | 시점·스레드 | 도달 | 분류 |

`0x16100`은 `ByteWidth > 0xFFFF`인 동적 상수 버퍼(곧 2 MB uniform 세그먼트)에만 CPU 그림자를 붙이고, Map을 그림자로 돌린 뒤 Unmap에서 `min(c735bc, ByteWidth)`만큼 실제 매핑에 복사합니다(✔). `[0x158]`은 스테이징 가지에서 자기 자신을 vtable로 다시 부르므로 `0x1A8C0`이 중첩되고 바깥 호출이 돌아올 때 `c735bc`는 이미 0입니다(✔ `0x2B61D9`). 스노위문 자체의 동작이라 우리와 무관합니다.

## 4. 장면 키 `c780e8`은 패스 포인터가 아님 (✔)

- `0x1A890`이 저장하는 값은 들어올 때의 `rcx`입니다(✔ `0x1A89B mov [c780e8], rcx`). 이 핸들러는 `rcx`·`rdx`·`r8`·`r9`를 건드리지 않고 `[c73630]`을 부르므로 감싸는 호출의 첫 인자가 곧 키입니다.
- 설치 `0x76510`이 `.vlizer`(`0x11BA8BD`)에 넘기는 0x34바이트 머리는 {pid>>2, exe 베이스, 근처 0x20000 RWX 영역, 대상 `0x1475C90`, 길이 `0x3A9`, 내부 호출 오프셋 `0x30D`, 핸들러 `0x1A890`}이고, 뒤에 붙는 템플릿 `c780a8..c780b0`은 `0x6BD80`이 게임 장면 함수의 바이트 `0x3A9`개를 그대로 복사한 것입니다(✔ `0x6C8CE`–`0x6C946`, `memcpy 0x35A030`). `+0x30D`는 `0x1475F9D call 0x160EE40(queue_set, ctx, &local_88)`입니다(✔ `1475C90` 디컴파일).
- 따라서 감싸는 곳은 둘 중 하나입니다. 입구라면 `rcx = [pass+0x1C68]`(✔ `0x226C2D`)이고, 이것은 패스 객체 안에 박힌 콜백 객체 `(pass+0x1B47) & ~7`, 곧 `pass+0x1B48`을 가리킵니다(✔ 패스 설정 `0x1476EA0`의 `0x1477037`–`0x1477074`). 내부 호출이라면 `rcx = [[pass+0x1C70]+0x30]`, 곧 큐 묶음(`render_queue_set_data_t`)입니다. **어느 쪽이든 패스 포인터와 같지 않습니다.** 2026-10-22 라이브의 "키는 프레임마다 다른 주소, 우리 pass 포인터와 다름"(`proxy_gate.hpp:29`)과 맞습니다.
- 내부 호출 쪽이 더 그럴듯합니다(△ 강함). 템플릿이 함수 전체 사본이고 내부 호출을 호출 대상의 모양(`0x6B8D0`, 즉시값 `0xFFFF`)으로 골라 넘기며, `0x84460`의 "같은 키가 이미 있으면 반환"(`0x84486`–`0x844A6`)은 키를 여러 패스가 나눠 쓸 때만 의미가 있습니다. 확정은 런타임 스텁 덤프로 합니다(§12의 1).
- **설계는 키의 정체에 기대지 않습니다.** §5.2는 push를 "그 push를 낸 패스"(우리 실행자가 아는 큐 인덱스)로 묶고 키는 값 그대로 실어 나르므로, 두 해석 모두에서 직렬과 같은 결과를 냅니다.

## 5. 해법별 설계

### 5.1 (b) 장면 키를 스레드 지역으로: `0x1A890` 입구 훅

명령 지점은 6곳입니다(✔ refs): 쓰기 `0x1A89B`·`0x1A8A4`·`0x1A853`, 읽기 `0x1A69C`·`0x84476`·`0x84670`. 미드훅으로 읽기 세 곳만 스레드 지역 값으로 바꿔 넣는 방식은 가능하지만(쓰기는 막을 수 없어도 전역을 아무도 안 읽으면 무해), `0x1A69C`가 레지스터 적재가 아니라 `cmp [mem], 0`이라 플래그를 흉내 내야 하고, 무엇보다 (c)의 순서 문제가 그대로 남습니다. §5.2에서 `0x1A440`을 실행자 스레드에서 통째로 대신하므로 남는 지점은 `0x1A890` 하나입니다.

```
// dxgi+0x1A890 입구 훅. executor = 이번 프레임 동시 기록의 실행자 스레드(pool_guard의 스레드 지역 플래그)
if (!executor) return original_1A890(rcx, rdx, r8, r9);   // 트램펄린
tls.key = rcx;                                             // 전역 c780e8은 건드리지 않음
r = (*(fn*)(dxgi + 0xC73630))(rcx, rdx, r8, r9);
tls.key = 0;
return r;
```

- 원본은 `sub rsp,0x28` 뒤 그대로 부르므로 스택 인자를 옮기지 않습니다. 감싸는 대상이 `0x160EE40`(인자 3개)이든 콜백(인자 4개)이든 레지스터 인자뿐입니다(✔ `0x1475F9D`, `0x226C4B`).
- 비용: 장면 패스당 1회. 첫 11바이트(`48 83 EC 28` + RIP 상대 `48 8B 05 …`)를 safetyhook이 옮깁니다.

### 5.2 (c) 순서 되살리기: `0x1A440` 대체와 합류 재생

#### 5.2.1 `0x1A440`이 하는 일 (✔ 디컴파일 + `0x1A4B3`–`0x1A881`)

`0x1A440(p1, p2)`는 게임 uniform 값을 바꾸지 않습니다. 카메라를 엿보고 원본으로 꼬리 점프합니다(`0x1A846`에서 `[c735d8]`을 읽고 `0x1A881 jmp rax`, `rcx=p1`, `rdx=p2`).

1. 블록 1(`p2 != 0`): `obj = **(p2+0x18)`, `arg = (*(u8*)(p2+0x20) & 4) ? *(*(p2+0x18)+0x10) : 0`, `m = transform_p(*(p2+0x38), arg)`(`0x1A4B3`). `obj != 0`이고 `(c73638 != obj || c73640 != m[11])`이면: `|m[11]| > 2`이고 `ccccd0 != c288d8`일 때 `ccccd0 = c288d8`, `R = V·T(−pos)`(V는 `obj+0x18`, pos는 `obj+0x98`)를 만들어 `0x84670(…, obj+0x98, obj+0x18, R, m)`. 그 뒤 `c73640 = m[11]`, `c73638 = obj`.
2. 블록 2(`c780e8 != 0`): `P = transform_p(…)`(`0x1A6DD`). `|P[11]| > 0`이고 `obj != 0`이면 `R2 = V·T(−pos)`, `0x84460(…, obj+0x98, obj+0x18, R2, P)`.
3. `c780e8 = 0`(매 호출), 원본으로 꼬리 점프.

`0x84460`은 키가 이미 있으면 반환, 직전 항목과 위치·뷰가 같으면 직전 항목에 건너뜀 표시·`c288f4=1`·새 항목 `+0xE8=1`, 순번을 쓰고 개수를 올립니다(✔). `0x84670`은 단일 기록을 덮어씁니다(✔). 소비자 `0x951F0`은 키를 쓰지 않고 순서·건너뜀·`+0xE8`·`c288f4`만 봅니다(✔ `0x95B28`–`0x95B87`, `0x95E93`).

#### 5.2.2 동시 기록에서 깨지는 것

- `c780e8`: 다른 스레드의 장면 키를 보고 엉뚱한 패스가 push하거나, 남의 `0x1A853`이 지워 push를 잃습니다.
- 링: 비원자 `c7673c`로 같은 칸에 두 스레드가 쓰거나 개수를 잃습니다. 넣는 순서가 완료 순서가 되어 렌더 스레드의 Base Pass가 다른 뷰의 카메라를 꺼냅니다(sensor_coexistence §9.2와 같은 깨짐). 중복 판정이 인접한 같은 카메라끼리에서만 일어나므로 순서가 섞이면 건너뜀 표시가 빠져 항목이 늘고, **19개를 넘으면 반환 없는 오류 경로로 게임이 죽습니다**(`0x8458E`).
- 블록 1: `ccccd0` 검사-후-쓰기 경합으로 기록이 두 번 쓰이거나 찢기고, 직렬에서 이겼을 패스가 아닌 패스가 "프레임당 첫 카메라"가 됩니다. 이 기록은 Base Pass·라이팅·톤맵이 읽습니다.

#### 5.2.3 설계: 실행자 스레드에서는 같은 계산을 패스별 기록에, 합류에서 큐 순서로 재생

실행자 스레드의 `0x1A440` 입구 훅(비실행자는 트램펄린으로 원본):

```
void composer_leaf(p1, p2) {                 // executor only
  Log& L = log[tls.queue_index];             // run_pass가 원본 0x226A00 호출 전에 세움
  uintptr obj = 0, arg = 0;
  if (p2) {
    arg = (*(u8*)(p2+0x20) & 4) ? *(uintptr*)(*(uintptr*)(p2+0x18)+0x10) : 0;
    float m[16]; transform_p(m, *(uintptr*)(p2+0x38), arg);   // base + [dxgi+0xC77FF0], 게임 0x16706E0
    obj = **(uintptr**)(p2+0x18);
    if (obj) L.note_call(obj, m[11], /*후보면*/ copy{pos=obj+0x98, V=obj+0x18, R=V·T(-pos), m, key=tls.key});
  }
  if (tls.key) {
    float P[16] = {}; transform_p(P, *(uintptr*)(p2+0x38), arg);
    obj = **(uintptr**)(p2+0x18);
    if (fabsf(P[11]) > 0 && obj) L.push(copy{key=tls.key, pos, V, R2, P});
  }
  tls.key = 0;
  return original_3EB300(p1, p2);            // [dxgi+0xC735D8], MinHook 트램펄린
}
```

`note_call`은 패스 안에서만 판단할 수 있는 것을 남깁니다. 첫 호출 `(obj, m11, 후보 인자 if |m11|>2)`, 둘째 호출부터 "패스 안 직전 호출과 `(obj, m11)`이 다르고 `|m11| > 2`"인 첫 호출(내부 후보), 마지막 호출 `(obj, m11)`입니다. 비교는 원본과 같은 float `!=`(NaN이면 참, `ucomiss` 결과와 같음)입니다. 원본처럼 `obj == 0` 호출은 세지 않습니다. 행렬 곱은 디컴파일 루프(`0x1A440`의 4x4 루프 두 개)를 그대로 옮깁니다.

합류 재생(모든 실행자가 끝난 뒤, `0x227B1F` 훅이 돌아가기 전, 메인 스레드):

```
carry = {G[c73638], G[c73640]};  won = (G[ccccd0] == G[c288d8]);
for i in 큐 순서(queue_ 인덱스):
  L = log[i]
  if (L.calls) {
    if (!won) {
      c = (L.first.big && L.first.objm != carry) ? &L.first : L.internal;
      if (c) { G[c780e8] = c->key; dxgi_84670(0, c->pos, c->V, c->R, c->m); G[ccccd0] = G[c288d8]; won = true; }
    }
    carry = L.last;
  }
  for p in L.pushes: { G[c780e8] = p.key; dxgi_84460(0, p.pos, p.V, p.R2, p.P); }
G[c73638], G[c73640] = carry;  G[c780e8] = 0;
```

- 블록 1과 블록 2는 서로 다른 상태(기록 대 링)를 쓰므로 패스 안의 상대 순서는 결과에 영향이 없습니다(✔).
- `0x84460`·`0x84670`은 스노위문 함수를 그대로 부릅니다. 키 중복 반환, 중복 판정, 순번, `c288f4`, 19개 한도까지 직렬과 같습니다. 직렬이 넘쳤을 프레임은 재생도 넘칩니다(동작 동일).
- 패스당 push는 1개 이하입니다. 키가 서는 구간은 장면 패스당 한 번이고 `0x1A440`이 첫 호출 뒤 지우기 때문입니다(✔). 그래도 기록은 작은 배열로 둡니다.
- 비용: 실행자 쪽은 원본과 같은 계산(transform 두 번, 4x4 곱 두 번)에 스레드 지역 접근만 더함. 원본 중계 비용은 0.04 ms/프레임(docs/28 §2.10). 재생은 프레임당 push 19회 이하와 기록 1회, 수 µs(△).
- 시점: 렌더 스레드는 합류 뒤 컴파일·제출이 끝나야 이 프레임의 Base Pass를 실행하므로, 재생이 끝난 링만 꺼냅니다(✔ docs/28 §2.1 10단계). 바닐라는 기록 도중에 push하므로 재생은 같은 기록 구간 안에서 더 늦게 넣을 뿐입니다. 프레임 시작 `0x8EC20`과 렌더 스레드의 관계(sensor_coexistence §3.4, △)는 바닐라와 같은 조건이고, push 구간이 짧아지므로 나빠지지 않습니다.
- 합류 전에 원본으로 바로 기록되는 패스(마커 통과, 큐 초과, 메인이 아닌 호출)는 링에 먼저 들어갑니다. 지금 `serial` 모드와 같은 어긋남이고, 정상 플레이에서는 0입니다(docs/28 §3.2).

#### 5.2.4 링을 사후에 정렬하는 방식이 모자란 이유

질문의 안(동시 기록이 끝난 뒤 `[0, c7673c)`를 원래 패스 순서로 재정렬)은 다음 때문에 단독으로는 안 됩니다.

1. 정렬할 항목이 온전하지 않습니다. `c780e8` 경합으로 push가 빠지거나 다른 패스 키로 들어가고, `c7673c` 경합으로 칸이 겹칩니다. (b)를 먼저 해야 합니다.
2. 항목 → 패스 대응이 키로는 불확실합니다(§4). 큐 묶음으로 보면 한 키가 여러 패스의 것이고, `0x84460`이 같은 키의 둘째 push를 버렸으므로 남은 항목이 직렬에서 이겼을 패스의 것인지 모릅니다.
3. 중복 판정·건너뜀·`+0xE8`·순번·`c288f4`는 넣는 순간의 인접 항목으로 정해져 정렬 뒤 모두 다시 계산해야 합니다(스노위문 판정의 재구현).
4. 정렬하기 전에 이미 19개 한도에 걸려 죽을 수 있습니다.
5. "프레임당 첫 카메라" 기록(`0x84670`)은 링 밖이라 정렬로 고칠 수 없습니다.

사후 정렬은 §5.2.3의 판정 재구현이 오히려 더 많아서 대안으로 두지 않습니다.

### 5.3 (a) 짧은 임계 구역

#### 5.3.1 `c76810`과 레코드 참조 수: ID3D11Device vtable 슬롯 감싸기

스노위문은 `0x17B70`에서 D3D11 장치 vtable(공유 객체)의 슬롯 3·5·7·8·9·10·11·12·15·21에 핸들러 주소를 씁니다(README §4.3). 우리도 같은 방식으로 슬롯 7·9·10을 우리 함수로 바꾸고, 우리 함수는 저장해 둔 스노위문 핸들러를 부릅니다.

```
// 슬롯 7 (CreateShaderResourceView): 원래 값 = dxgi+0x16200
HRESULT wrap_csrv(dev, res, desc, out) {
  if (!executor) return sm_16200(dev, res, desc, out);          // 다른 스레드는 그대로(풀 가드 규칙과 같음)
  PoolLock guard;                                                 // 이미 쥔 스레드는 깊이로 통과(pool_guard의 nested 규칙)
  return sm_16200(dev, res, desc, out);
}
// 슬롯 9 (CreateRenderTargetView → 0x164D0), 10 (CreateDepthStencilView → 0x16800): 같은 모양
```

- 삽입 쪽(SRV 미스 `0x2B8AC0`, persistent 이미지 실현의 RTV·DSV)과 지움 쪽(`0x2AE6B0`·`0x32E540`의 Release, 이미 풀 락)이 실행자 스레드 사이에서 서로 배제됩니다.
- 이 방식은 dxgi `.text`를 바꾸지 않고, 게임 쪽 호출 지점 목록이 빠져도(§1의 △) 장치를 거치는 모든 생성 호출을 덮습니다.
- 슬롯 3·12·15(버퍼 id, 셰이더 id·이름 컨테이너)는 지금 경로가 이미 풀 락 안이라 락은 필요 없고, 계수기만 둬서 풀 락 밖에서 불린 적이 있는지 봅니다. 하나라도 있으면 같은 감싸기에 넣습니다. 슬롯 5(CreateTexture2D `0x16710`)는 전역 쓰기가 없습니다(✔).
- 비용: 정상 프레임은 캐시 적중이라 생성 호출이 거의 없습니다(△ §12의 3으로 잼). 0.54.1이 `0x2B9520`의 락을 뺀 이유(적중이 락을 잡지 않게)는 그대로 지켜집니다. 미스의 생성만 락을 잡습니다.
- 바닐라에도 있는 경합(로딩 스레드의 생성·해제와 메인 기록)은 이 감싸기가 고치지 않습니다. 고치려면 dxgi `0x16200`·`0x164D0`·`0x16800`과 소멸자 `0x15EC0`·`0x15F80`·`0x16000`을 모든 스레드에서 한 락으로 감싸야 합니다(dxgi 훅 6개). 바닐라에서 문제가 보고된 적이 없으므로 넣지 않습니다.

#### 5.3.2 TB SRV(`0x2B6EC4`)의 버퍼 vtable 바꿔치기

`0x2B6EC4`는 `ViewDimension = 1`(BUFFER) 버퍼 SRV를 만듭니다(✔ `2B6B90` 디컴파일: 리소스 = `[device+0x3623CD8] + id*0x70 + 0x60`). 버퍼 SRV는 `ID3D11Texture2D` QueryInterface가 실패해 맵에 닿지 않지만(✔ `0x16200`), 그 앞에서 스노위문이 감싼 버퍼의 vtable 포인터를 호출 동안 원래 것으로 바꿨다가 되돌립니다. 두 실행자가 같은 버퍼로 동시에 SRV를 만들면 한쪽 D3D 호출 도중에 다른 쪽이 프록시 vtable로 되돌려 생성이 실패할 수 있습니다(△ D3D11 런타임이 vtable로 자기 객체를 확인한다고 볼 때, 결과는 `[dx11] Failed to create TB SRV` 로그와 그 그리기의 바인딩 누락이고 크래시는 아님).

- 1단계: 위 슬롯 7 감싸기가 버퍼 SRV도 풀 락 아래에 둡니다(가장 단순, 정확).
- 계수기로 실행자의 TB SRV 생성이 프레임당 많다고 나오면, 리소스 vtable의 `Release`가 `dxgi+0x15880`인 경우(감싼 버퍼)만 리소스 주소로 고르는 줄무늬 SRW 64개로 바꿉니다. 이 락은 잎 락입니다(쥔 채로 엔진 코드를 부르지 않음).

#### 5.3.3 `c735bc`: 지금 풀 락으로 충분, 단 조건이 있음

`[0x158]`을 부르는 실행자 경로는 `[0x120]` `0x2E9050`과 `0x2E8100`이고 둘 다 전역 풀 락 안입니다(✔ `pool_guard.cpp:18`·`:19`). 그래서 실행자끼리 `c735bc`가 겹치지 않습니다. 렌더 스레드의 Unmap(`0x2B2CC0`)과 겹치는 경우는 바닐라(메인 `[0x120]` 대 렌더 스레드)와 같습니다.

**조건: 프록시가 있는 동안 `[0x120]`·`0x2E8100`을 전역 풀 락에서 빼지 않습니다.** docs/28 §11.13이 남은 직렬 몫으로 꼽은 `[0x120]`(보유 0.3 ms, 대기 2.7 ms)을 줄이려면, 엔진 장치 vtable(`.rdata 0x22138D8`)의 `[0x158]` 슬롯을 감싸 `[0x158]` 전용 락을 잡게 한 뒤에 `[0x120]`을 풉니다. `[0x158]`은 vtable로 자기를 다시 부르므로 같은 스레드 깊이 통과가 필요합니다.

### 5.4 (d) 제외 근거

§3.4 표입니다. 실행자 스레드가 부르는 컨텍스트 메서드는 Map·Unmap·CopySubresourceRegion(1)뿐이므로(✔ §2.2) 바인드·그리기 썽크의 전역은 렌더 스레드만 씁니다. AA가 켜져 도는 효과 경로(`0x9FE10` 계열, 상태 기계, 히스토리 레코드)는 모두 그 아래입니다. 프레임 시작 `0x8EC20`은 Present 브래킷이라 합류 구간 밖입니다.

## 7. 사전 검사 (실패하면 B안을 켜지 않고 이유를 반환)

1. 게임 `bin/win_x64/dxgi.dll`이 로드돼 있고 sha256이 `d819c16805a9a0ca17f34ef46cc445c5847f32308d10e69bf08f3c1b4779f4dc`(기존 `proxy_gate` 검사 재사용).
2. §6의 H1·H2·C1·C2 바이트가 메모리와 일치.
3. 스노위문 상태: `c737ac == 1`, `c7381c == 0x3D`, `c736b8 == 0`(치명 오류 없음), `0 <= c7673c <= 19`.
4. 장치 vtable 슬롯 3·5·7·9·10·12·15가 위 dxgi 핸들러를 가리키고, 저장된 원본들이 우리 모듈을 가리키지 않음(재설치로 순환이 생기지 않게).
5. 게임 `.text`의 외부 패치가 알려진 스노위문 11곳뿐이고(docs/28 §11 `gate.foreign`), `0x1475C90`·`0x3EB300`·`0x2B5FE0`의 점프가 각각 익명 스텁·MinHook 중계·MinHook 중계를 거쳐 `0x1A890`·`0x1A440`·`0x1A8C0`에 닿음.
6. 풀 가드 구성에 `0x2E9050`·`0x2E8100`이 전역 풀 락으로 들어 있음(§5.3.3).

지금 `workers_allowed`(외부 패치 0)를 "외부 패치 = 알려진 스노위문 집합이고 B안 훅이 모두 걸림"으로 넓히는 것이 게이트 변경의 전부입니다.

## 9. 예상 남는 이득

- 스노위문 때문에 다시 직렬화되는 몫: 텍스처 뷰 생성의 풀 락(미스 때만), TB SRV 생성(1단계에서는 풀 락, 횟수는 S1 계수기로 잼), 합류 재생 수 µs. `0x1A440` 대체와 `0x1A890` 훅에는 락이 없습니다.
- 그래서 정상 프레임의 직렬 몫은 프록시 없는 M3d와 거의 같고(△), 이득도 같은 수준(주행+센서 CPU busy −1.33 ms, 정차 −0.84 ms, docs/28 §11.13–§11.14)을 기대합니다. 스노위문 중계 비용(장면 스텁, 합성 잎)도 함께 병렬로 돕니다.
- AA를 켜면 GPU 일이 늘어 GPU 한계 장면에서는 fps 이득이 CPU busy 이득보다 작게 보일 수 있습니다. 판정은 CPU busy와 합류 시간으로 합니다.

## 12. 게임에서 검증할 항목 (모두 읽기 전용 관측부터)

1. **장면 스텁 덤프**: `0x1475C90`의 FF25 목표(익명 영역)를 프로세스 안에서 읽어 역어셈블. `0x1A890`을 어디서 부르는지(입구 대 `+0x30D` 호출 자리), 절대 주소 qword인지, 전역 쓰기나 VM 진입이 있는지. §4의 △와 R1 변형을 닫음.
2. **패스별 호출 수**: 프레임마다 패스(이름 키)별 `0x1A440` 호출 수, `tls.key`가 선 호출 수, push 수, 블록 1 후보 수. 장면 밖 패스가 `0x3EB300`을 부르는지(R2 판단), 패스당 push ≤ 1인지.
3. **생성 호출 계수**(S1): 동시 프레임 실행자의 슬롯 3·5·7·9·10·12·15 호출 수, 그중 텍스처 SRV와 버퍼 SRV, 풀 락 밖에서 불린 수(0이어야 함), `[dx11] Failed to create TB SRV` 로그 수(0이어야 함).
4. **프레임 경계**: Present 스레드와 렌더 스레드(`0x2B3203`) 비교(sensor_coexistence §6의 1). 합류 시작·재생 끝의 `c7673c`·`b0c17c`, 렌더 스레드 첫 Base Pass 때의 `c288d8`.
5. **그림자 검증**(S2): 링·기록 불일치 0.
6. **동시 비교**(S3): 교차 프레임의 링 순서열·기록이 직렬과 같은지, `proxy_coexistence trace`의 메인 레코드 교체 0/N(센서 1288x720·968x540 프리셋).
7. **장시간**: 30분, 센서 4·9슬롯, 링 최대 19 이하, `c736b8 == 0`, `c737ac == 1` 유지.
8. **persistent 이미지 실현**(§13): 실행자 스레드에서 `0x21DA50`이 불리는 수.
9. **성능**: 프록시 켬·AA 모드 고정 ABAB(`serial` 대 `concurrent`), CPU busy p50과 합류 시간.

## 13. 별견: 엔진 쪽 persistent 이미지 실현 (스노위문과 무관)

`d3d_sites.py`가 blit 콜백 → `0x226E20` → 이미지 조회 `0x21CF60`의 음수 id 가지 → `0x21DA50`을 찾았습니다(✔). `0x21CF60`은 프레임 기록의 `+0x278`이 1이고 이미지 `+0x79F`가 0이면 `0x21DA50`을 부르고, `0x21DA50`은 `+0x79F = 1`을 세운 뒤 이미지가 없으면(`+0x740 == -1`) `0x21D500` → `[0x1A0]`으로 D3D 텍스처와 뷰를 만듭니다(✔ 디컴파일). 검사와 설정이 원자 연산이 아니므로, 같은 persistent 이미지를 처음 쓰는 패스 둘이 동시에 기록되면 이미지를 두 번 실현할 수 있습니다. 프록시 없는 M3c·M3d가 10분 이상 안정적이었으므로 정상 프레임에서는 기록 전에 이미 실현돼 있다고 봅니다(△). docs/28 §3.5 7의 남은 확인("`0x21CEC0`의 음수 id 경로")의 답 후보입니다. 프록시가 있으면 이 가지의 RTV·DSV 생성이 `c76810`에도 닿으므로 §5.3.1의 슬롯 감싸기가 함께 덮습니다. 엔진 쪽을 막으려면 `0x21DA50`을 풀 락에 넣습니다(§6 E2, 호출은 첫 사용 때만이라 비용은 작음 △).
