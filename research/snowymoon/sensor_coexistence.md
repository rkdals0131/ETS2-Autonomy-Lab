2026-10-22. 정적 조사만 했습니다(게임 실행·설치·커밋·게임 폴더 수정 없음). 표시는 ✔ 코드로 확인, △ 추정입니다. 배경은 [README](README.md) §4.3·§5·§10.11, [lessons](../../docs/history/lessons.md) "렌더러를 가로채는 모드", [docs/28](../../docs/28_render_pass_parallel_prototype.md) §2.1입니다.

## 결론

1. **구현 가능한 방법이 있습니다.** 렌더 스레드에서 센서 패스가 도는 동안만 프록시의 `dxgi+0xC7382C`를 0으로 두는 게이트입니다. 센서 구간은 이미 있는 `0x2B3203` 지점(OMSetRenderTargets 호출 직전, 렌더 스레드)에서 컴파일 구간 표로 판정합니다. 이 방법은 프록시 코드를 패치하지 않고 데이터만 씁니다.
2. **그것만으로는 모자랍니다.** 프록시는 장면 패스마다 메인 스레드가 기록 시점에 링 `dxgi+0xC73848[20]`에 넣은 항목을 렌더 스레드가 순서대로 하나씩 가져가는 구조입니다(✔ §3.3). 센서 베이스 패스를 건너뛰면 그 항목이 남아 메인 패스가 센서의 투영을 가져갑니다. 그래서 센서 패스가 쓴 링 항목에 "건너뜀" 바이트(`dxgi+0xC7392C + 0xF0*i`)를 1로 세워야 합니다. 프록시가 중복 항목에 쓰는 바로 그 표시이고 가져가는 쪽이 이미 건너뜁니다(✔).
3. 0x2B3AF0·0x2F0420의 인자에서는 소유를 알 수 없습니다(✔ §1). RT 모양(크기·형식)으로는 프록시 진입 자체를 막을 수 없습니다(✔ §2).
4. 원인 가설("센서 패스가 프록시의 시간 누적 상태를 오염")은 코드에서 근거를 보강했지만 라이브 확인은 없습니다(△ §3.5). 게임 세션에서 §6의 항목으로 확인한 뒤에만 켜야 합니다.

## 1. 렌더 스레드에서 센서 명령 버퍼의 소유를 알 수 있는가

### 1.1 `0x2F0420`·`0x2B3AF0` 인자에는 소유가 없습니다 (✔ 디컴파일)

- `0x2F0420(device, list)`: `list+0x10`개의 **u16 명령 버퍼 id**(`list+8`)를 장치의 링 `device+0x40`(1024칸)에 넣고 `device+0x858`에 개수를 더한 뒤 세마포어 `device+0x850`을 올립니다. 소유·패스 정보 필드는 없습니다.
- 렌더 스레드 루프 `0x2F04D0`은 세마포어를 하나 받을 때마다 id 하나를 꺼내 **큐가 빌 때까지** 스택 배열(최대 0x400개)에 모은 뒤 `[0x110]`(`0x2B3AF0`)에 한 번에 넘깁니다. 한 번의 실행 호출에 메인·센서 id가 섞일 수 있습니다.
- `0x2B3AF0(device, list)`는 `device+0x3999A87`이 0이면 `0x2B2930`을 바로 부르고, 아니면 SRW `device+0x3999A00`을 잡고 id마다 `+0x1D0` 슬롯과 객체 해제를 부릅니다. 어느 쪽도 id만 다룹니다.
- 한 명령 버퍼 안에는 여러 패스가 들어갑니다(컴파일이 저장소를 16개 이상 묶고 경계 플래그 1에서 끊음, docs/28 §2.1 10단계). 그래서 id만으로는 부족하고 id 안의 명령 위치(토큰)까지 필요합니다.

따라서 이 두 지점에 거는 것은 **불가**입니다(소유를 모름).

### 1.2 이미 있는 판정 경로가 소유를 줍니다 (✔ 코드, 단 아래 △)

- 메인 스레드 컴파일 훅(`0x2B1BB0` 시작, `0x2B26DA` 끝, `ot/native/render_probe.cpp:16`)이 `PassCommands::begin/end`(`ot/native/pass_commands.cpp:530`·`:556`)로 **컴파일된 id → 명령 구간 {시작, 끝, 패스}** 표 `compiled_`를 만듭니다. 패스 판정은 `describe`(`:384`)가 합니다. 입력 저장소 `input`에서 `pass=input-0x2E8`을 구하고 `pass+0x1F8` 인덱스로 살아 있는 패스 배열(`manager+0xF0`)에 있는지 확인한 뒤, 출력 이미지의 네임스페이스 라벨 `mirrorN`(`images+0xA8`)과 `camera_mask` 비트로 `camera_slot`을 정합니다.
- 렌더 스레드 훅 `0x2B3203`(`render_probe.cpp:14`, `0x2B2930` 안, OMSetRenderTargets 호출 직전)은 `observe`(`:432`)에서 `compiled_id`(`[rbp-0x30]`이 가리키는 커서)와 토큰(`r12`가 가리키는 데이터 + (`r13`-1)*4)을 읽고 `pass_commands_.lookup(id, token)`(`pass_commands.cpp:586`)으로 패스를 돌려받습니다. 같은 훅이 `r8`(RTV 배열)·`rdx`(개수)·`[rbp+0xA8]`(DSV)도 갖고 있습니다. 1.61.1.9에서 `0x2B3203`의 바이트가 `4C 8B 8D A8 00 00 00 48 8B 88 F0 FC 63 03 48 8B 01 FF 90 08 01 00 00`이고 `call [rax+0x108]`은 컨텍스트 vtable 슬롯 33 OMSetRenderTargets입니다(✔ 바이트 확인). 즉 이 훅은 프록시 썽크 `0x17580`을 부르기 직전에 돕니다.
- 센서 소유 규칙: `lookup`이 돌려준 패스의 `camera_slot`이 `Configuration::mask`(`camera_rig.cpp:86`)에 있고 `private_outputs`이면 센서입니다. 설정 마스크 밖의 `mirrorN`은 네이티브 미러라 메인 쪽입니다(`camera_rig.cpp:117-138`: 센서 슬롯만 비공개 카메라 배열로 돌립니다).

### 1.3 이 경로의 구멍 (구현 시 고쳐야 함)

- ✔ `describe`는 `camera_mask`가 `UINT32_MAX`가 아니면 센서 슬롯의 **지오메트리·최종 색 패스만** 이름을 붙입니다(`pass_commands.cpp:`의 `mirror_output |= camera_mask==UINT32_MAX || target==attributes0 || target==color`). 센서의 라이팅·블러 같은 중간 패스는 이름이 없어 `lookup`이 빈 값을 줍니다. 게이트가 센서 구간을 끝까지 덮으려면 "출력에 센서 슬롯의 `mirrorN` 이미지가 하나라도 있으면 이름을 붙인다"는 모드가 필요합니다(작은 수정).
- 이름이 없는 패스는 메인으로 취급해야 합니다(직전 소유를 물려받지 않음). 그렇지 않으면 센서 구간 뒤의 메인 중간 패스가 센서로 오판됩니다. 매 OMSetRenderTargets에서 `lookup`으로 다시 판정하면 됩니다.
- △ `private_outputs`일 때 최종 이미지 이름이 `ot/sensorN`(`camera_rig.cpp:158`)인데 네임스페이스 라벨이 그대로 `mirrorN`인지는 이 조사에서 직접 읽지 못했습니다. 기존 스트림이 같은 `describe`로 비공개 리그 영상을 잡고 있으므로 라벨은 유지된다고 봅니다.
- △ 컴파일 훅은 메인 스레드 비용을 더합니다(`compile_begin_timing_`). 게이트 모드에서는 이름 붙이기 대상 슬롯만 켜는 것이 비용이 가장 낮습니다.
- 명령 구간 표는 풀 id 재사용 때문에 빈 경계에서 정리됩니다(`pass_commands.cpp:536`). 렌더 스레드가 한 프레임 늦게 도는 동안 메인이 같은 id를 다시 컴파일하면 구간이 지워질 수 있습니다(△). 지워지면 메인으로 판정되어 센서가 프록시를 통과하므로 현재 증상으로 되돌아갈 뿐 새 손상은 없습니다. 지운 횟수를 세어 세션에서 확인합니다.

## 2. 대안: RT 모양으로 구분할 수 있는가

### 2.1 프록시는 RT 모양으로 센서를 거르지 않습니다 (✔ `9F7B0.c`, `951F0.c`)

`0x9F7B0`(`DAT_b10fe8` 상태 기계, README §10.11)가 보는 것은 다음뿐입니다.

- 개수 4, DSV와 RT 네 장이 모두 널이 아니면 베이스 패스(상태 0, `0x951F0`).
- 개수 2이고 `DAT_c76748`이 이번 프레임 레코드이면 SSAO 쪽(상태 1).
- 개수 1이고 RT0의 `GetDesc` Format(`+0x10`)이 10(`R16G16B16A16_FLOAT`)이면 라이팅 합성 쪽(상태 2).
- 인덱스 수 `0x12C0` DrawIndexed(상태 3).

크기·형식·이름으로 "센서가 아님"을 판정하는 코드는 없습니다. 센서의 지오메트리 패스는 메인과 같은 deferred 파이프라인이라 개수 4+DSV 조건을 그대로 만족합니다. 센서 RT 형식을 바꿔 조건을 피하면 센서 영상이 달라집니다.

### 2.2 크기는 프록시 안에서 뷰 구분 키로만 쓰입니다 (✔ `951F0.c:580-606`)

`0x951F0`은 `DAT_c77e58`(RT0)의 폭·높이를 `FUN_1800a9260`으로 읽어 뷰 레코드 20개(`dxgi+0xC785F0`부터 간격 `0x4190`)에서 `{폭, 높이, 프레임 == DAT_c288d8-1}`이 같은 것을 찾고, 없으면 이번 프레임에 쓰이지 않은 레코드를 새로 잡습니다. 즉 시간 누적 상태(히스토리)가 **(폭, 높이, 직전 프레임)** 키로 이어집니다.

- 센서와 메인의 크기가 같으면 같은 레코드를 공유할 수 있습니다(△ 추정: 한 프레임 안의 두 뷰가 같은 키).
- 센서 프리셋의 `base_resolution`은 1280x720, 960x540입니다(`ot/presets/phase1-highway-scania-s-private.json`). 메인 창 크기와 다르면 센서는 별도 레코드를 쓰지만, 센서는 10 Hz라 직전 프레임 키가 맞지 않아 매번 새 레코드가 됩니다. 이 경우 센서 자체는 메인의 히스토리를 직접 덮지 않습니다.

### 2.3 판정

RT 모양은 **우리 쪽 분류 규칙으로는 약합니다.** 개수·크기만으로는 센서의 중간 패스(절반 해상도 SSAO 등)와 메인의 중간 패스를 가를 수 없고, 해상도 설정이 메인과 같아지면 구분이 사라집니다. 보조 검사(구간 표의 판정과 크기가 모순이면 기록)로만 씁니다.

## 3. DAT_c7382c를 다른 스레드가 바꿀 때의 경합

### 3.3 (A)에서 꼭 지켜야 할 쓰기 순서

1. **다시 복사에 덮이지 않게**: 구간 진입 시 프록시가 하는 다시 복사를 우리가 먼저 한다. `if (c73830 != c288d8) { c73830 = c288d8; c7367d = [dxgi+0xC7307F]; c7367e = [dxgi+0xC730B6]; c7382c = a3d840; }`를 그대로 재현한 뒤 `c7382c = 0`을 씁니다. 이렇게 하지 않으면 새 프레임의 첫 그리기가 센서 그리기일 때 프록시가 0을 `a3d840`으로 되돌립니다(✔ 본체 순서).
2. **복원은 `c7382c = a3d840` 읽은 값**입니다(1이 아님, 모드값 1..6, ✔ `8CFF0.c:320`).
3. **상태 기계 상태**: `DAT_b10fe8`이 4가 아닌 채로(메인 베이스·SSAO·라이팅 도중) 센서 구간에 들어갈 수 있습니다. 이때 `0x9F7B0`이 안 불려 상태가 유지되고, 메인으로 돌아와 첫 그리기에서 RT 스냅숏(`c785b0` 이하 0x40바이트와 `c77e98`·`c77ea0`)이 달라 상태 정리 함수(`0x973D0`·`0x9BD20`·`0x9E7C0`)가 그때 돕니다(✔ `9F7B0.c`). 이 정리 함수들은 셰이더 바인딩·복사·그리기를 하는 실제 렌더링 코드입니다(✔ `973D0.c`, `9E7C0.c`). 센서 구간이 끼어도 정리는 메인 RT가 다시 묶인 뒤에 돌아 메인 쪽 순서는 같지만, 정리가 뒤로 미뤄지는 것은 △입니다. 진입 때 `b10fe8`을 읽어 4가 아닌 횟수를 기록합니다(검증 항목).
4. **OM 썽크는 `c7382c`로 막히지 않습니다**(✔ `17580.c`, `A3870.c`). `0xA3870`은 `b10fe8 != 4`이고 RT 집합이 직전과 같으면 원본 호출을 삼킵니다. 센서 RT는 다르므로 통과하고, 복귀 때 메인 RT 집합이 직전 스냅숏과 달라 통과합니다.
5. **링 항목**(§0 결론 2): 센서 장면 패스의 항목에 건너뜀 바이트를 1로 씁니다. 항목 키 `dxgi+0xC73848 + 0xF0*i`가 `DAT_c780e8`(장면 패스 인자, 우리 `pass`)와 같다고 보고 센서 패스 포인터와 비교합니다(△ 같은 포인터인지는 라이브 확인). 쓰는 시점은 렌더 스레드가 메인 베이스 패스에서 가져가기 전, 즉 센서 구간 첫 진입(또는 프레임의 첫 `0x2B3203`)에서 `[0, c7673c)`를 훑는 것이 가장 단순합니다. 링은 프레임 시작 `0x8EC20`이 `c7673c=0`, `b0c17c=-1`로 되돌립니다(✔). 가져가는 쪽 `0x951F0`은 `b0c17c`를 올리며 `c7392c[idx]!=0`인 항목을 건너뜁니다(✔ `951F0.c:560-575`). 쓰기 대상은 바이트 하나이고 프록시 쪽도 같은 값(1)을 같은 의미로 씁니다(`0x84460` 중복 표시).
6. **링 용량**: `0x84460`은 항목 수가 20에 닿으면 반환 없는 오류 경로로 갑니다(✔ `84460.c` 끝, `c7673c<0x14` 아니면 `FUN_180014e70`). 센서 슬롯이 늘어 한 프레임의 장면 패스가 19개를 넘으면 지금도 크래시 위험입니다. 우리 변경과 무관하지만 센서 4~9개 설정에서 같은 세션에 `c7673c` 최댓값을 기록합니다.

### 3.4 프레임 경계 경합 (△)

`c288d8`은 `0x1AEC0`의 `A69C0`→`8EC20`에서 올라갑니다. 이 프레임 브래킷(Present 래퍼 `0x2BFE80`을 감쌈, README §4.2는 "프레임 상태(메인 스레드)"로 적음)이 메인 스레드이고 렌더 스레드가 프레임 N의 명령을 아직 실행 중이면, 프록시는 프레임 N+1의 `c288d8`을 보고 다시 복사해 버리며 링 `c7673c`도 0으로 되돌아갑니다. 프록시 자체의 이 계약이 어떻게 지켜지는지는 정적으로 닫지 못했습니다(`0x227140`은 `frame+0x268`이 서 있을 때만 렌더 스레드 소진을 기다림, ✔ `227140.c:700`). 이미 프록시만으로 안정적으로 도는 것을 보면 실제로는 렌더 스레드와 프레임 브래킷이 같은 스레드이거나 메인이 기다리는 구조일 가능성이 큽니다. 기존 `frames` 응답의 Present `thread_id`와 `0x2B3203` 레코드의 `thread`를 비교하면 한 번에 닫힙니다(검증 항목 1).

### 3.5 증상 원인에 대한 코드 근거 (△ 라이브 없음)

lessons의 설명("시간 누적 AA 히스토리 오염")과 맞는 코드 사실은 다음과 같습니다.

- ✔ 센서 패스는 프록시의 베이스 패스 판정(§2.1)을 통과하고 `0x951F0`이 센서 RT 크기로 뷰 레코드를 잡습니다(§2.2). 프록시는 센서와 메인을 구분하지 않습니다.
- ✔ 링 항목은 센서 장면 패스도 하나씩 차지하고 순서로 소비됩니다. 센서가 10 Hz로 끼는 프레임에서만 순서·개수가 달라집니다.
- △ `c73830`·`c288d8` 프레임 기반 상태(`DAT_c76748`, 레코드 `+0x2C`, `+0x18A8`)를 센서 패스가 갱신하면 메인의 이후 SSAO·라이팅 상태 조건(`9F7B0.c`의 `*(c76748+0x2c)==c288d8` 계열)이 어긋날 수 있습니다. 이것이 10 Hz 깨짐의 직접 원인인지는 모릅니다.

따라서 **게이트가 증상을 없애는지는 가설이며, 한 번 켜 보기 전에는 결론을 낼 수 없습니다.** (C)(`a3d840`=0)는 "AA 끔"과 같아 증상이 없어지는 것이 이미 관찰된 방법이라 A/B 대조군으로 씁니다.

### 4.2 사전 검사 (실패하면 모드를 켜지 않고 이유를 반환)

1. `GetModuleHandleW(L"dxgi.dll")`가 있고 `GetModuleFileNameW` 경로가 게임 `bin/win_x64`입니다(시스템 `dxgi.dll`이면 프록시 없음 → 게이트 불필요, 기능 꺼짐).
2. 그 파일의 sha256이 `d819c16805a9a0ca17f34ef46cc445c5847f32308d10e69bf08f3c1b4779f4dc`입니다(이 조사에서 게임 폴더의 `dxgi.dll.off`가 같은 값임을 읽기 전용으로 확인했습니다). 같지 않으면 오프셋이 다르므로 거절합니다.
3. 메모리 속 프록시 `.text` 바이트가 파일과 같은지 일부 확인합니다. `dxgi+0x9FE10`의 첫 32바이트 `48 89 5C 24 08 48 89 6C 24 10 48 89 74 24 18 57 41 56 41 57 48 83 EC 30 8B 05 AA 8A B8 00 41 8B`, `dxgi+0x17580`은 `48 89 5C 24 08 48 89 74 24 10 57 48 83 EC 20 48 8B 05 8A 08 C6 00 49 8B F9 8B DA 49 8B F0 8B D3`입니다(`.text`는 다시 배치되지 않음, `.reloc`로 `RIP` 상대 명령은 같음).
4. 프록시 상태 값: `dxgi+0xC737AC == 1`(설치 성공), `dxgi+0xC7381C == 0x3D`(1.61), `dxgi+0xA3D840 <= 6`, `dxgi+0xB10FE8 <= 4`.
5. `VirtualQuery`로 위 쓰기 대상이 `.data`의 쓰기 가능 페이지임을 확인합니다(섹션 `.data` `0xA19000`..`0xCD0ED8`, 특성 `0xC0000040`).
6. 게임 exe가 1.61.1.9이고 기존 훅 시그니처 검사(`render_probe.cpp`의 `find_target`)가 통과합니다. `device vtable [0x108]==0x2B1AA0`(또는 `[0x110]==0x2B3AF0`, `[0x118]==0x2F0420`)도 확인합니다.
7. 프록시 객체가 이미 바뀌었는지(패스 구간 표 정리 횟수, `lookup` 미스 비율)는 실행 중에 계속 기록하고 한계를 넘으면 자동으로 게이트를 끕니다.

### 4.3 구현 스케치 (구현은 이 조사 범위 밖)

1. `PassCommands::describe`에 "센서 슬롯 모든 패스" 모드를 추가합니다(출력에 센서 슬롯 `mirrorN`이 있으면 이름을 붙임).
2. `RenderProbe::observe`와 별개의 가벼운 게이트 콜백을 `0x2B3203`에 둡니다. 소유 = `lookup` 결과가 센서이면 센서, 아니면 메인. 바뀔 때만 프록시 데이터를 씁니다.
3. 센서 진입 시 §3.3의 1, 5를 하고 `c7382c=0`. 메인 복귀 시 `c7382c = a3d840`. Present 훅에서 상태 초기화.
4. 기록·상태 키(`gate_enter`, `gate_exit`, `b10fe8_nonidle_entries`, `lookup_miss`, `ring_flagged`, `ring_max`)를 `status`에 노출합니다.

## 5. 이 방법이 못 푸는 것

- M3c·M3d(락 축소 패스 병렬 기록)와는 별개입니다. 그쪽 불가 판정(README §6)은 그대로입니다. 이 게이트는 기록 경로를 건드리지 않습니다.
- 센서 영상은 프록시를 거치지 않은 순정 렌더가 됩니다(전제와 같음). 센서 영상이 프록시를 켠 상태에서 바뀌는지는 §6의 5로 비교합니다.
- 프록시가 이미 센서 패스에서 만들어 낸 부수 효과(로그, 레지스트리 `DAT_ccb680` 항목)는 센서 패스가 통과하면 생기지 않습니다. 반대로 센서 영상에 프록시 조명이 필요하다면 이 방법은 맞지 않습니다.

## 6. 게임 세션에서 검증할 항목

게임이 켜진 세션에서만 가능하고 모두 읽기 전용 관측으로 시작할 수 있습니다.

1. **스레드**: `frames`의 Present `thread_id`, `0x2B3203` 레코드의 `thread`, 컴파일 훅 스레드(메인)를 비교합니다. 프레임 브래킷이 렌더 스레드인지 메인인지 닫습니다(§3.4).
2. **소유 판정 범위**: 프레임마다 `0x2B3203`에서 센서/메인 판정 횟수, `lookup` 미스, 센서 슬롯 이미지가 있는 패스 중 이름이 없는 것의 수(0이어야 함).
3. **프록시 값 관측**: 센서 구간 안과 밖에서 `c7382c`, `a3d840`, `c73830`, `c288d8`, `b10fe8`, `c7673c`, `b0c17c`를 기록합니다. 구간 진입 때 `b10fe8`이 4가 아닌 비율.
4. **링 정합**: 프레임 끝의 `b0c17c`와 건너뛰지 않은 항목 수가 같은지, 센서 항목 포인터가 `c73848` 키와 일치하는지(§3.3의 5, 포인터 동일성 확인). 일치하지 않으면 링 표시 단계는 쓰지 않고 `b0c17c`를 올리는 방식으로 바꿉니다.
5. **증상 A/B**: (a) 현재(프록시 켬, 게이트 끔), (b) 게이트만(링 표시 없음), (c) 게이트+링 표시, (d) `a3d840`=0(AA 끔). 각각 Present 간격 패턴(48 FPS에서 5프레임마다 반복)과 화면 캡처로 메인 깨짐을 비교합니다. (b)가 깨지고 (c)가 안 깨지면 링 계약이 확인됩니다.
6. **센서 영상**: (c)와 (d)의 센서 RGB·깊이가 같은지(둘 다 프록시를 안 거침), (a)와 얼마나 다른지.
7. **장시간**: 10분 이상, 센서 9슬롯 설정과 4슬롯 설정에서 크래시·링 용량 오류(`c7673c` 최댓값 19 이하)·`lookup` 미스 증가 없음.
8. **M3b-1·M3b-2**와 같이 켠 세션에서 플래그 쓰기가 기록 스레드와 겹치지 않는지(링 표시를 렌더 스레드에서만 쓰므로 겹치지 않는 설계, 확인용).

- 프록시 AA 설정 값은 4(DLSS Quality)였습니다. 범위는 0..6이고(설정 UI `25A40.c`), 처음 사전 검사가 이 값을 거절해 0.50.2에서 상한을 고쳤습니다.
- 기준선(게이트 끔): 정적 화면은 깨지지 않고, 움직여서 화면이 갱신될 때 깨집니다. TAA(1), DLAA(3), DLSS Quality(4) 모두 깨지고 Disabled(0)는 깨지지 않습니다(사용자 관찰). 시간축 히스토리를 쓰는 모드에서만 생깁니다.
- 게이트 켬: 약 5초에 센서 구간 진입·종료 420회, 센서 바인드 1,260, 링 표시 0. **메인 깨짐이 훨씬 심해져** 바로 껐고, 끈 뒤 `c7382c`는 `a3d840`(4)으로 돌아왔습니다. 센서 그리기 동안 효과를 끄는 방식(§2 방법 A)은 기각입니다.
- 링 직접 읽기: 프레임마다 항목 6 또는 10개. 끝의 2개가 메인 쪽이고 그중 하나는 프록시가 스스로 건너뜀(+0xE4 = 1)으로 둡니다. 앞의 4 또는 8개가 센서 4대 몫입니다. 키(+0)는 프레임마다 다른 주소라 우리 `RenderPassSample::pass`(지속 포인터)와 같지 않습니다. §3.3의 "키 = 패스 포인터" 가정은 틀렸습니다.

## 9. 링과 히스토리 레코드 다시 읽기 (2026-10-22, §8 뒤)

### 9.1 코드 사실 (✔)

- **넣는 쪽 `0x84460`**(uniform composer 훅 `0x1A440`이 부름, 패스 기록 시점, 메인 스레드): 항목 하나 = `+0` 순번, `+8` 키(`DAT_c780e8`), `+0x10` 카메라 위치 3 float, `+0x20`·`+0x60`·`+0xA0` 4x4 행렬 셋, `+0xE8` 중복 표시, `+0xEC` 건너뜀 바이트. 직전 항목과 위치·첫 행렬이 같으면 직전 항목을 건너뜀으로 표시합니다. **`c7382c`를 보지 않으므로 AA 사본을 0으로 둬도 항목은 그대로 쌓입니다.**
- **꺼내는 쪽 `0x951F0`**(그리기 본체 → `0x9F7B0` 상태 기계 → 베이스 패스, 렌더 스레드, `c7382c != 0`일 때만): `b0c17c`를 건너뛰지 않은 다음 항목까지 올리고, 그 항목의 위치·행렬을 RT0 (폭, 높이, 직전 프레임 사용) 키로 고른 히스토리 레코드(20개, `dxgi+0xC785F0`, 간격 `0x4190`)의 이번 짝홀 칸에 복사합니다. 이전 칸과 400 넘게 떨어지면 이전 칸을 이번 값으로 덮어 히스토리를 리셋합니다. 고른 레코드는 `DAT_c76748`에 남고 뒤 패스들이 씁니다.
- 프레임 시작 `0x8EC20`(Present 브래킷)이 `c288d8++`, `c7673c = 0`, `b0c17c = -1`, 짝홀 `c76740`·`bec1d8`을 둡니다.

### 9.2 게이트가 더 나쁘게 만든 이유 (✔ 코드로 설명됨)

게이트가 센서 패스 동안 `c7382c = 0`을 쓰면 센서 베이스 패스에서 `0x951F0`이 불리지 않아 커서가 센서 항목을 지나가지 않습니다. 넣는 쪽은 센서 항목을 이미 쌓았으므로, 뒤이은 메인 베이스 패스가 **첫 센서 항목을 꺼내 메인 레코드에 센서 카메라 행렬을 씁니다.** 효과를 끄는 방식은 넣는 쪽과 꺼내는 쪽의 개수를 어긋나게 만들 뿐이라 기각합니다.

### 9.3 기준선 깨짐의 후보 (△, 다음 게임 세션에서 가름)

- 링 항목 수는 매 프레임 6 또는 10이었습니다. 화면에 보이는 게임 미러 4개(매 프레임 렌더, docs/26)와 메인 2개가 6, 10 Hz 센서 4대가 끼면 10으로 보는 것이 가장 단순합니다(추정).
- **(가) 커서 어긋남**: 센서 한 대가 쌓는 항목 수와 센서 베이스 패스가 `0x951F0`을 부르는 횟수가 다르면, 센서가 낀 프레임에서 뒤의 미러·메인이 한 칸씩 밀린 항목을 꺼냅니다.
- **(나) 레코드 빼앗기**: 센서 RT0 크기가 메인이나 미러와 같으면, 먼저 그려지는 센서가 "직전 프레임에 같은 크기" 레코드를 가져가고 뒤의 뷰는 새(오래된) 레코드를 받습니다. 센서 프리셋은 1280x720·960x540이고, DLSS Quality가 1920x1080 출력이면 내부 렌더도 1280x720입니다. 다만 TAA(업스케일 없음)도 깨지므로 (나)만으로는 설명이 부족합니다.
- 두 후보 모두 "정적이면 멀쩡, 움직이면 깨짐"과 맞습니다. 잘못된 행렬·히스토리라도 화면이 그대로면 재투영 차이가 거의 없기 때문입니다.

### 9.4 가르는 방법

- core 0.51.0 `ot.cmd proxy_coexistence trace`(읽기 전용, 프록시에 쓰지 않음): 렌더 스레드 훅에서 소유가 바뀌거나 프레임이 바뀔 때마다 커서, 항목 수, 고른 레코드 번호·크기, 커서 항목과 마지막 항목의 카메라 위치를 한 줄씩 남깁니다. `ot.cmd proxy_coexistence dump --out <file>`로 저장합니다. 센서 구간 하나에서 커서가 센서 항목 수만큼 나아가는지(가), 센서와 메인이 같은 레코드 번호를 쓰는지(나)를 봅니다.
- 코드 없는 대조: 센서 해상도를 조금 바꿔(예: 1280x720 → 1288x720) 깨짐이 사라지면 (나)입니다.
- 결과에 따른 수정 방향: (가)면 센서 구간이 끝날 때 프록시가 꺼내지 않은 센서 항목만큼 커서를 맞추거나, 센서 항목을 건너뜀으로 표시(키 대신 순번·위치로 식별)합니다. (나)면 센서 RT 크기를 메인·미러와 겹치지 않게 고르는 것으로 끝납니다.
