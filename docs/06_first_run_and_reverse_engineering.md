# 첫 실행과 렌더 경로 역공학

첫 런타임 결과물은 게임이 정상 진행되는 동안 운전석과 다른 방향의 영상을 실제로 얻는 것입니다. 이후 독립 센서의 생성과 RGB·depth 정합을 확인합니다. [오프라인 분석](10_installed_game_static_analysis.md)은 완료했고 아래 런타임 단계는 아직 수행하지 않았습니다. 첫 실행에서는 [도로 정차 데이터 관찰 순서](11_idle_memory_and_telemetry.md)를 함께 사용합니다.

## 게임 실행 전에 할 수 있는 작업

- 소스에서 카메라 객체, 텍스처 경로, 입력 ABI의 관계를 읽습니다.
- SCS SDK 예제의 빌드 조건과 DLL 로딩 위치를 확인합니다.
- 사용할 게임·플러그인 버전 후보를 맞춥니다.
- 출력할 메타데이터와 좌표·시간 규약의 초안을 정합니다.
- 필요한 도구만 준비하고 외부 SSD의 기록 경로를 정합니다.

현재 실행 파일에서 카메라 함수 후보의 RVA와 전역 포인터 슬롯까지 확보했습니다. 실제 프로세스의 객체 값, 미러 업데이트 조건, 추가 카메라의 호환성과 성능은 실행 관찰이 필요합니다.

## 첫 실행의 기준 상태

연구용 프로필에서 차량·도로·날씨·시간을 정하고 게임 로그와 전체 빌드를 확인합니다. 초기 장면은 정지 상태의 정면 물체, 옆을 지나는 차량, 뒤로 접근하는 차량을 볼 수 있으면 충분합니다.

게임 단독의 운전석·미러가 정상인지 먼저 봅니다. 게임 실행 속도를 변경하지 않습니다. 초기 프레임 측정은 같은 장면에서 비교 가능한 수준으로만 남깁니다. 별도 벤치마크 시스템을 만들 필요는 없습니다.

## 미러의 생산자와 소비자 찾기

1. 디지털미러의 재질과 카메라 정의를 찾습니다. 추출된 파일에서 mirror_data, cam_m_h, mirror_camera, parking 관련 항목을 검색합니다.
2. 해당 카메라를 보여주는 GPU 프레임을 캡처합니다.
3. 미러를 화면에 합성하는 draw의 텍스처를 찾고, 그 텍스처에 앞서 쓰는 패스를 따라갑니다.
4. 그 패스의 color/depth target, viewport, 투영과 view 상수, 원래 리소스 재사용 시점을 봅니다.
5. F2 켜기·끄기, 머리 회전, 거울이 화면 밖으로 나가는 상황을 비교합니다.

뷰어에 보이는 해상도가 같다는 이유로 카메라를 식별하지 않습니다. 실제 바인딩과 쓰기 이력을 사용합니다. 한 텍스처가 atlas인지, 여러 뷰가 depth target을 재사용하는지도 확인합니다.

[RenderDoc texture viewer](https://github.com/baldurk/renderdoc/blob/v1.x/docs/window/texture_viewer.rst)와 [호출 스택 수집 옵션](https://github.com/baldurk/renderdoc/blob/v1.x/docs/window/capture_attach.rst)이 출발점입니다. RenderDoc과 현재 ETS2의 호환성은 첫 캡처에서 확인할 사항입니다.

## 렌더 호출에서 엔진 객체로 이동

GPU API 호출 스택의 게임 실행 파일 주소를 x64dbg 또는 Ghidra에서 연결합니다. 디버그 심볼이 없더라도 호출 주소와 객체 사용을 조사할 수 있습니다.

연결할 정보는 다음과 같습니다.

- 카메라 객체의 생성·초기화·등록·선택.
- 차체 또는 로케이터에서 카메라 자세로 가는 변환.
- 거울이 보여야 업데이트되는 조건.
- 투영과 시야 내 물체 목록을 만드는 함수.
- 렌더 타깃 생성과 재사용.
- 장면 뷰를 실제 렌더러에 제출하는 함수.

SPF의 카메라 조회·초기화, MobileCam의 갱신 함수, PrismTextureStreamer의 텍스처 큐를 서로 다른 진입점으로 사용합니다. 공개 코드의 패턴과 offset은 선택한 게임 빌드에서 다시 의미를 확인해야 합니다.

## 기존 영상의 외부 추출

렌더가 완료되고 해당 리소스가 덮어써지기 전에 색상·깊이를 보존합니다. 낮은 해상도에서 비동기 CPU readback으로 실제 영상을 보는 것이 첫 결과물일 수 있습니다.

여기서 확인할 것은 다음입니다.

- 사용자가 보는 게임 화면과 추출 영상이 동시에 갱신됩니다.
- 카메라를 화면에 표시하지 않아도 필요한 때에 갱신됩니다.
- 영상의 좌우 반전·crop·투영을 설명할 수 있습니다.
- depth의 물체 윤곽과 RGB가 같은 위치에 있습니다.
- 종료 후 게임 또는 플러그인이 소유한 리소스가 남지 않습니다.

이 단계에서 얻은 것은 기존 피드 추출입니다. 아직 새로운 센서 생성이 아닙니다.

## 독립 정면 센서 생성

남는 보조 카메라 슬롯이나 주차 카메라를 활용할 수 있으면 초기 가능성 실험에 사용합니다. 최종적으로는 원래 운전석과 미러를 유지해야 합니다.

정면 센서는 차체 기준 위치·자세·투영을 갖도록 만듭니다. 사용자가 옆을 보거나 운전석 FOV를 바꾸어도 센서가 따라 움직이지 않아야 합니다. 이 독립성이 확인되면 센서 역할의 카메라 생성에 성공한 것입니다.

해결할 대상은 projection 행렬 하나가 아닙니다. 뷰의 물체 선별, depth, 출력 대상, 후처리 이력과 엔진 상태 복원을 함께 다뤄야 합니다.

## 같은 상태의 4뷰와 6뷰

한 번 갱신된 렌더 장면 상태를 기준으로 센서 뷰를 추가 제출합니다. 엔진이 읽는 장면 상태가 도중에 바뀌지 않는 호출 위치를 확보해야 합니다. 임의 시점의 월드 포인터를 저장했다고 장면 snapshot이 생기는 것은 아닙니다.

카메라별로 필요한 렌더 타깃과 이력을 분리하고 미러 전용 물체 제외 규칙을 조사합니다. 센서 묶음을 만들 때는 일부 카메라가 과거 프레임이면 완성된 최신 묶음으로 내보내지 않습니다.

움직이는 주변 차량, 운전자 머리 회전, 트레일러가 꺾이는 상황으로 시간·좌표 정합을 봅니다. 실제 프레임 타임과 GPU 메모리를 확인한 뒤 4뷰에서 6뷰로 확대합니다.

## 제어와 학습 연결

영상 생성이 안정된 뒤 작은 제어 명령을 적용하고 즉시 해제하는 경로를 확인합니다. 수동 해제, 외부 프로세스 종료, 일시정지·복귀 후 입력 적용 상태를 실제 게임에서 봅니다.

이후 짧은 주행을 기록하고 재생 영상·상태·입력의 시점을 확인합니다. 카메라 여러 장이 저장됐다는 사실만으로 학습 데이터 준비가 끝난 것은 아닙니다.

## 막힌 지점별 다음 조사

| 관찰 | 다음 조사 |
| --- | --- |
| 기존 미러가 화면 밖에서 멈춤 | 가시성 검사와 카메라 활성 조건 |
| RGB는 되지만 depth가 어긋남 | 다른 패스·viewport·반전·투영·depth 재사용 |
| 카메라 행렬은 바뀌지만 뒤쪽 물체가 없음 | 주 시점으로 만든 물체 목록과 culling |
| 센서가 고개를 따라 움직임 | 주 카메라/미러 투영과 차체 로케이터의 결합 |
| 한 장은 되지만 여러 장이 섞임 | 공유 RT, atlas, 완료 시점과 버퍼 소유권 |
| FPS가 급격히 하락 | 물체 처리·draw call·조명·readback·추론을 단계별 측정 |
| 버전 변경 후 플러그인이 실패 | 지원 범위와 구조체·함수 패턴 변경 |

완료 판정에는 실제 게임 영상과 간단한 수치가 우선입니다. 이 작업을 위해 별도의 검증 프레임워크나 테스트 인벤토리를 만들지 않습니다.
