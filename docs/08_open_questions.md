# 미해결 사항과 결정 시점

현재 문서로 결정할 수 있는 것은 프로젝트 방향과 조사 순서입니다. 게임 실행과 GPU 캡처가 필요한 사실은 아래의 구체적인 관찰로 해결합니다.

2026-10-08 정적 조사와 외부 메모리 관측에 이어 RenderDoc 4뷰의 실제 픽셀·같은 pass 상수·카메라 공간 점군을 확보했습니다. 일반 DX11에서 0.5.0 DLL의 mirror5 색상/Z/재질을 5초·50표본·10 Hz로 기록했고, Present 구간 연결과 세 hook의 패닉 복원·완전한 SDK 언로드를 확인했습니다. **현재 핵심 미해결 경계는 DLL 다중 뷰·장시간 수집, 영상과 상태값의 같은 시점 연결, 갱신 조건, 독립 센서 생성입니다.** [13번 구현 상태](13_game_operating_table.md)에 실제 결과와 남은 검증을 기록했습니다.

## 실행 전 결정할 수 있는 것

| 항목 | 작업 기본안 | 다시 볼 조건 |
| --- | --- | --- |
| 운영체제 | Windows 네이티브 | 사용자가 방향 변경 |
| 주 게임 | ETS2 | 사용자가 방향 변경 |
| 시간 처리 | 정상 속도와 같은 상태의 센서 묶음 | 변경하지 않는 요구사항 |
| 첫 센서 모델 | 고정 pinhole | 어안의 실제 필요와 엔진 지원 확보 |
| 첫 그래픽 조사 | 지원되면 DX11 | 선택한 게임·도구가 지원하지 않음 |
| 시각화 | Foxglove SDK와 Windows 앱 | 실제 배포·연결 조건이 맞지 않음 |
| 제어 입력 | 하나의 소유자, 명시적 해제 | 실제 입력 경로에 맞게 구현 조정 |
| 모델 | 센서 확보 후 작은 모델부터 | 데이터·VRAM·목표 기능 확인 |
| AC | 별도 문서로 보존 | ETS2 작업을 자동 대체하지 않음 |

## 실행해야 해결되는 질문

| 질문 | 현재 근거 | 필요한 관찰 | 결정에 미치는 영향 |
| --- | --- | --- | --- |
| F2와 실제 미러가 같은 RT인가 | 모드의 재질 재사용과 작성자 설명 | GPU resource 사용 이력 | 복사 지점과 중복 렌더 비용 |
| 화면 밖 센서가 계속 갱신되는가 | 시야 검사와 별도 HUD 요청의 합집합으로 미러 선택. HUD 요청은 slot 0·2 전용이며 `showmirrors`/`g_mirrors`에 연결. `g_mirrors_keep_hidden`은 창 분기와 요청 bit를 분리. GPU 갱신은 미확인 | 머리 회전·F2·숨김 설정과 각 GPU 프레임 대조, 독립 센서 요청 경로 | 활성 조건 처리 |
| 카메라 슬롯을 몇 개 추가할 수 있는가 | 미러 생성·갱신·제출은 0–8 고정 순회. 그래프 구성은 제출 개수를 순회하지만 같은 index의 원본 카메라·drawable·적용 mask에 의존. 엔진 전체의 9뷰 상한으로 확인한 것은 아님 | 새 카메라·출력의 소유권과 생성·해제, 추가 뷰의 실제 렌더 | 기존 슬롯 활용 또는 엔진 확장 |
| 기존 미러가 차체 고정 센서인가 | 모드 0은 현재 시점 위치 사용. 모드 1은 사용자 좌석 보정 전의 기준 위치 사용. 공통 parent는 본체와 캐빈 서스펜션의 상대 자세를 합성하며 CPU 표본으로 대조 | 디지털미러 실영상·운전석 변경 전후의 상대 자세, 큰 캐빈 운동, 재구성 뒤 동작, 독립 자세 생성 | 샤시·캐빈 기준 선택과 센서 외부 파라미터 |
| 임의 위치의 새 뷰를 생성할 수 있는가 | 카메라·초기화·렌더 후킹 코드 | 실제 함수와 소유 객체 | 프로젝트의 핵심 기술 가능성 |
| 새 뷰가 모든 필요한 물체를 그리는가 | 종류별 미러 제외와 차량·연결 모델 제출을 연결. LOD·cut plane·Visibility area 모두 선택된 게임 카메라 기준. actor 표시 조건 85개, Road 제외 26개, cut plane 64개, 영역 활성 48개를 대조. UID 예외와 controller 내부 갱신 순서 확인. Compound 32개의 부모 segment·자식 211개를 구별하고 두 부모의 Q 11개를 미러 후보와 연결. mover 인물 3개의 모델 경로·거리별 선택을 대조하고 뷰별 구 경계 검사·Q 제출 경로 확인. 별도 pedestrian_hookup도 게임 카메라 기준 LOD를 쓰는 정적 경로 확인 | 센서 기준 영역·대상 목록·LOD 분리, 물리·traffic 갱신과 렌더 프레임 사이 연결, Compound 자식별 geometry 대응·동적 부가 객체와 pedestrian_hookup 실측, 같은 상태 GPU 비교 | 센서용 물체 선택 규칙 |
| depth의 정확한 의미는 무엇인가 | 기본 diffuse의 `attributes_0.w`는 카메라 Z. 미러 4개의 pass 투영·viewport·기본 카메라·ray 연결. 후속 원본 객체 표본에 camera/ray override·MVP filter 없음. DX11 NDC는 reversed Z, 미러 surface 범위 0.01–0.9. main 실내는 0.9–1.0과 별도 투영 사용 | GPU 픽셀·실거리 대조, 실행 draw의 최종 상태, main 실내·실외 구분, 특수 재질 확인 | 미터 단위 출력과 점군 |
| 렌더 상태와 텔레메트리 시점은 같은가 | 약 16.666 ms step의 AI 사전 갱신→물리 world（PhysX 결과 대기 포함）→사후 갱신→SDK 전달 뒤 자세 이력 발행·보간→카메라→가시성→LOD→미러 준비를 연결. SDK frame_end는 렌더 완료가 아님. world placement와 local velocity는 물리 body를 읽음. 사후 처리에서 speed=-local vz, acceleration은 속도 차분의 10-step 이동평균으로 저장. 가속도 갱신은 telemetry plugin 존재 조건. AI 판단은 별도 배치 처리 | 움직이는 장면의 GPU 픽셀·pass 상수·telemetry 시각 연결, 수집 중 프레임 변경 처리, 필터를 포함한 상태값의 시간 해석 | timestamp와 pose 수집 지점 |
| 6뷰가 3060 Ti에서 얼마나 빠른가 | 픽셀·데이터량 계산뿐 | CPU/GPU 프레임 타임 | 해상도·주기·모델 예산 |
| alt-tab·최소화 때에도 가능한가 | 현재 검증 없음 | 각 창 상태에서 게임·센서 갱신 | 백그라운드 실행 지원 범위 |
| 트레일러 센서 자세를 얻을 수 있는가 | 트레일러 상태 접근 단서 | 관절 회전과 실제 카메라 | 동적 외부 파라미터 |
| 실제 DLL의 ABI와 reader가 맞는가 | 선택 source revision의 선언·할당·C# 소비자는 대조 완료 | 나중에 배치할 DLL의 revision과 실행 결과 | 외부 클라이언트 직렬화 |

사용자가 운전석을 보면서 센서를 화면 밖에서 렌더하는 경우, alt-tab 상태, 게임 창을 최소화한 경우는 각각 다릅니다. offscreen 카메라가 된다고 최소화 상태에서도 게임이 계속 렌더한다는 뜻은 아닙니다. 첫 목표는 사용자가 운전석을 보는 상태입니다.

## 실제 위험과 대응 시점

| 조건 | 가능성 | 영향 | 지금 필요한 조치 |
| --- | --- | --- | --- |
| 게임 업데이트 후 내부 구조가 달라짐 | 충분히 예상 가능 | 플러그인 실패·충돌 | 선택 버전과 지원 범위 기록 |
| 기존 미러의 최적화가 센서에 상속됨 | 관련 기능은 확인, 실제 영향은 미측정 | 일부 물체 누락 | 센서 패스 조사 항목에 포함 |
| 다중 뷰와 추론이 GPU 예산을 넘음 | 가능, 정도 미측정 | 프레임·입력 지연 | 단계별 측정, FPS 약속하지 않음 |
| 복사와 저장이 느림 | 높은 원시 데이터량으로 예상 가능 | 제어 지연·기록 누락 | 비동기 전달과 기록량 분리 |
| 모드가 같은 mirror_data를 덮어씀 | 모드 조합에서 보고됨 | 카메라 오동작·충돌 | 초기에는 최소 모드 구성 |
| 특정 도구가 현재 게임 빌드와 안 맞음 | 미확인 | 조사 경로 변경 | 한 도구부터 실제 연결 |

현재 알려진 사실은 문서의 조사 방향을 정하기에 충분합니다. 위 미확인 사항을 이미 해결한 것으로 취급하거나, 반대로 모두 불가능하다고 결론 내리지 않습니다.
