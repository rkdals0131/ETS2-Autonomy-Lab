# 성능과 병목

## CPU 병목 분석

2026-10-12, core 0.31.1–0.32.0, Windows 네이티브 릴레이. 장비는 Ryzen 7 3700X(8코어 16스레드, L3 두 묶음: CPU 0–7·8–15), RTX 3060 Ti, ETS2 1.61.1.1 DX11입니다. PresentMon 2.6.0(`research/tools/`, 관리자 권한 불필요)으로 30–60초씩 쟀고, 정차 측정은 모두 같은 주차 위치입니다. 원본은 로컬 `research/live/2026-10-12-p1-sensor/`(정차는 `standstill/`)에 있습니다. 개선 계획은 [26 CPU 최적화 계획](26_cpu_optimization_plan.md)입니다.

### 요약

- ✔ 게임은 메인 스레드 하나에 묶인 CPU 바운드입니다. 주행 중 메인 스레드(SDK 콜백 스레드와 같은 tid)가 한 코어의 93.6%를 쓰고, 게임 전체는 약 1.6코어입니다. 작업 관리자의 전체 사용률 30%대는 여유가 아니라 논리 CPU 16개 중 하나가 포화된 모습입니다.
- ✔ 엔진 메인 스레드의 일을 다른 코어로 나누는 설정·실행 옵션·OS 조정은 없습니다([웹 조사](#웹-조사)).
- 줄일 수 있는 것은 네 가지입니다. 센서 뷰 렌더 횟수, 뷰당 엔진 비용(미러 시야거리), 메인 스레드와 다른 프로세스의 경쟁, 메인 스레드 위 우리 코드.
- ✔ 0.32.0에서 자세만 남은 카메라의 렌더를 미리보기 주기로 묶어 센서 렌더가 초당 117.9회에서 79.5회로 줄었습니다(−33%, fps +3%). ✔ 런처의 CPU 배치는 연속 A/B에서 프레임 CPU 시간을 5.9 ms(−13.6%) 줄였습니다.

| 스레드·프로세스 | 주행 중 | 정차·뷰어 켬 |
| --- | ---: | ---: |

| FMOD 믹서 | 13–22% | 20.9% |
| NVIDIA 드라이버(`nvwgf2umx.dll`) | 약 12% | 11.8% |
| 게임 전체 | 약 1.6코어 | 1.6코어 |
| Foxglove 뷰어 앱 | 약 1.9코어 | — |
| 런처(pythonw) | 0.38코어 | — |

100%는 논리 코어 하나입니다. 런처는 Tk 위젯을 4 Hz로 매번 다시 설정하느라 CPU를 썼고, 0.32.0과 같은 커밋에서 바뀐 값만 다시 그리게 고쳤습니다(재측정 남음). 메인 스레드는 렌더가 20 fps 안팎이어도 SDK 프레임을 초당 60번 처리합니다.

### 정차 장면 분해

core 0.31.1, `r_mirror_view_distance 400`. 이때는 자세 출력이 30 Hz로 렌더를 일으켰습니다.

| 조건 | fps | CPU busy p50 ms | GPU busy p50 ms | 원본 |
| --- | ---: | ---: | ---: | --- |
| 브리지 끔 | 40.7 | 24.0 | 8.6 | `off.csv` |
| 릴레이 대기(Tier 1, 구독 없음) | 38.9 | 25.1 | 9.7 | `on-idle.csv` |
| 뷰어와 같은 토픽을 헤드리스로 구독 | 30.4 | 32.4 | 11.7 | `headless2.csv` |
| Foxglove 뷰어 | 20.1 | 48.6 | 14.3 | `viewer2.csv` |

- 뷰어가 구독하는 토픽은 미리보기 JPEG 4개, 미리보기 `camera_info` 4개, 표시용 점군 3개, `/tf`·`/tf_static`·`/ets2/gnss/fix`·`/diagnostics`입니다.
- ✔ 헤드리스 구독은 센서 렌더를 초당 약 113회(렌더 프레임당 3.7뷰) 일으키고 프레임당 7.3 ms를 더합니다.
- ✔ 뷰어는 렌더가 오히려 적은데(초당 80회, 렌더 프레임마다 4뷰) 16 ms를 더 씁니다. 같은 차이가 1차 측정(`on-headless` 35.5 ms, `on-viewer` 49.1 ms)에서도 났습니다. 뷰어 앱과의 경쟁입니다. △ CPU 배치로 5.9 ms를 되찾았고, 나머지는 GPU 공유나 메모리 대역 경쟁으로 추정합니다. 뷰어 쪽 GPU busy도 함께 늘었습니다.

### CPU 배치 A/B

뷰어 켬, 거리 400, 같은 장면에서 한 단계씩 연달아 30초씩 쟀습니다(`affinity-*.csv`).

| 단계 | fps | frame p50 / p99 ms | CPU busy p50 ms |
| --- | ---: | --- | ---: |
| 기준 | 22.9 | 43.4 / 61.6 | 43.0 |
| 뷰어를 CPU 8–15, BELOW_NORMAL로 | 24.3 | 40.6 / 54.6 | 40.3 |
| + 게임 프로세스를 CPU 0–7로 | 24.6 | 40.3 / 55.3 | 40.0 |
| + 메인 스레드를 CPU 2에 고정, 다른 게임 스레드는 CPU 2·3 밖으로 | 26.4 | 37.5 / 53.1 | 37.1 |

런처의 **CPU 배치**(0.32.0 커밋, 기본 켬)가 마지막 단계를 자동으로 적용합니다. 게임은 CPU 0이 속한 L3 묶음, 메인 스레드는 그 묶음의 두 번째 물리 코어에 혼자 둡니다. 릴레이·Foxglove 서버·기록기(Job affinity)와 뷰어(BELOW_NORMAL)는 다른 L3 묶음으로 보냅니다. 중지할 때 되돌립니다. ✔ 게임 로그의 `[cpu] sched_class`는 CPU 0–3(코어 0·1)이 6으로 가장 높아, 메인 코어 CPU 2가 이 머신의 선호 코어에 속합니다.

### 미러 시야거리

뷰어 켬, core 0.31.1, 연달아 측정(`mvd*.csv`). 사용자 설정은 `r_mirror_view_distance 400`, `r_deferred_mirrors 2`, `r_mirror_scale_x/y 2`, `g_traffic 1.0`이었습니다.

| `r_mirror_view_distance` | fps | CPU busy p50 ms |
| ---: | ---: | ---: |
| 400 | 17.0 | 57.4 |
| 250 | 22.6 | 43.2 |
| 150 | 27.0 | 35.5 |

- 이 cvar는 게임 미러(슬롯 0·1·2·5)와 센서 뷰(3·4·6·7) 모두에 적용됩니다. SCS 위키 기본값은 80입니다.
- 전방 라이다 최대 거리 250 m에 맞춰 250을 권장했고, 사용자가 250으로 바꿨습니다(✔ `config.cfg`). 측면 라이다는 150 m라 뷰별로 거리를 달리하면 더 줄일 수 있습니다([26](26_cpu_optimization_plan.md) C6).
- 같은 위치에서 앞서 잰 400 m 값은 43–49 ms였고 이 측정에서는 57.4 ms였습니다. 수십 분 사이 교통 등 장면이 바뀌므로, 비교는 연달아 잰 값끼리만 합니다.

### 0.32.0 결과

거리 250, 뷰어 켬, 연달아 측정.

| 실행 | fps | frame p50 / p99 ms | CPU / GPU busy p50 ms | 센서 렌더/초 |
| --- | ---: | --- | --- | ---: |
| A: 0.31.1, 이전 런처 | 32.5 | 30.2 / 44.6 | 29.9 / 9.5 | 117.9 |
| B: 0.32.0, CPU 배치 끔 | 33.6 | 29.5 / 41.1 | 29.2 / 9.7 | 79.5 |
| C: 0.32.0, CPU 배치 켬 | 70.3 | 13.8 / 25.0 | 13.5 / 3.6 | 80.0 |

- ✔ B는 자세 rider로 렌더가 33% 줄고 fps가 3% 늘었습니다.
- C는 판정하지 않습니다. ✔ 배치는 의도대로 적용됐습니다(게임 0xff, 메인 스레드 0x4, 릴레이·뷰어 0xff00). 하지만 CPU 배치로는 게임의 GPU 작업이 줄 수 없는데 GPU busy가 9.7 → 3.6 ms로 함께 줄었습니다. △ 주변 교통이 줄었거나, 뷰어 창이 가려져 Electron이 그리기를 멈췄을 가능성이 큽니다. 배치 효과는 위 연속 A/B의 −5.9 ms를 기준값으로 씁니다.

### 비용 구조

- ✔ 0.32.0에서 뷰어만 구독하면(라이다·미리보기 10 Hz) 센서 렌더는 초당 80회입니다. 4뷰 × 10 Hz × 2입니다. 수집 사이에 쉬는 프레임이 있으면 수집 직전 렌더가 하나씩 붙기 때문입니다([수집 직전 렌더](history/lessons.md#센서-렌더-생략과-정적-물체-깜빡임)). 0.31.1은 자세가 30 Hz로 거의 매 렌더 프레임 수집해 수집 직전 렌더가 따로 없었습니다(뷰어 구독 20초: 렌더 1600회·묶음 396개, 렌더 프레임마다 4뷰).
- △ 센서 뷰 1회의 메인 스레드 비용은 400 m에서 약 2 ms(대기 25.1 → 헤드리스 32.4 ms, 렌더 프레임당 3.7뷰), 250 m에서 약 0.8 ms(A·B 두 측정의 연립)입니다. 나머지 프레임당 약 24–28 ms는 플레이어 화면과 게임 미러 4개입니다.
- ✔ 우리 훅 본문은 0.31.1 뷰어 구독(4뷰를 매 렌더 프레임 수집)에서 렌더 프레임당 약 1.7 ms입니다. OM bind 1.39 ms, compile begin 0.30 ms, compile end 0.04 ms입니다. OM bind 누적 최대는 한 번 600 ms였습니다(△ 첫 수집의 GPU 자원 생성).
- ✔ SDK 콜백(Tier 0, SDK 프레임당): channel 26회 약 78 µs, frame_end 약 107 µs, frame_start 약 18 µs입니다. 초당 약 12 ms로 메인 스레드의 1.2%입니다. 엔진 스냅샷이 붙는 Tier 1·2는 재지 않았습니다. 0.32.0의 `sdk_timing` 명령으로 잽니다.

### 웹 조사

2026-10-12–13, 사용자가 준 세 페이지와 추가 검색입니다.

- SCS 포럼 [t=340852](https://forum.scssoft.com/viewtopic.php?t=340852) "Multicore.dll": ✔ 게시된 코드는 스레드 하나의 affinity를 0xFF로 바꿀 뿐입니다. 답글은 효과 없음·시작 충돌·보안 우려입니다.
- [Steam 토론(2017)](https://steamcommunity.com/app/227300/discussions/0/135512555425449185/): affinity를 코어 하나로 줬다가 되돌리는 방법입니다. 검증 없는 일화 한 건입니다.
- [Reddit 1mi5hpc(2025-08)](https://www.reddit.com/r/ETS2/comments/1mi5hpc/is_there_a_way_to_use_multi_cores_instead_of_just/): "엔진 한계라 우회법 없음"이 답이고, 교통량을 낮춘다는 답이 하나입니다. 처음에는 접근이 막혀 2026-10-13 RSS로 읽었습니다.
- ✔ SCS: 렌더러는 DX11 "for now"이고([1.50 블로그](https://blog.scssoft.com/2024/05/euro-truck-simulator-2-150-update.html)), 1.55의 비동기 로딩은 끊김을 줄이는 목적입니다. 1.61까지 멀티스레드 렌더링 일정은 없습니다. `-rdevice dx12|vk`는 실험적이고 DX11보다 느리다는 보고가 있습니다.
- ✔ SCS 직원(2018): 미러 하나는 "게임 월드를 한 번 더 렌더하는 것"입니다([t=256023](https://forum.scssoft.com/viewtopic.php?t=256023)).
- ✔ 이 머신의 `game.log.txt`: `using 6 worker thread(s)`, IO 3, real-time 3. 엔진 worker는 있지만 장면 준비와 렌더 명령 컴파일은 메인 스레드에 남습니다. D3D11 명령 버퍼 실행은 엔진 렌더 스레드가 따로 맡습니다(✔ 2026-10-14, [27 §6](27_main_thread_parallel_research.md#6-m0-결과-정차브리지-끔)).
- NVIDIA "Threaded optimization"은 OpenGL 설정(`OGL_THREAD_CONTROL`)이고, Microsoft는 HAGS로 큰 변화가 없다고 합니다.
- 효과 있는 설정은 `r_mirror_view_distance`(가장 큼), `g_traffic`, `g_lod_factor_*`, `r_deferred_mirrors`(센서 영상이 바뀜)입니다. `config.cfg`의 `r_mirror_group "3"`은 위키에 없어 의미를 확인하지 못했습니다.

### 측정 방법

- 도구: `.\ot\ot.cmd perf <label> [--profile-hz 250]`(core 0.33.0, 호출 스택·스레드별 CPU는 0.34.0). PresentMon 통계와 센서·게임 미러 렌더/초, 훅·SDK 콜백 시간, stream 누락, 교통 차량 수, 게임·뷰어·릴레이 CPU, 게임 창 전경 비율을 `research/live/<날짜>-perf/<label>.json`에 남깁니다. `ot.cmd perf_table <json...>`이 한 줄씩 비교하고, `ot.cmd hotspots`가 저장된 스택을 함수별로 묶습니다([27](27_main_thread_parallel_research.md#4-도구)).
- 재기 전에 확인합니다. 런처 phase, `tier`, 뷰어 연결, 게임 창 전경, `paused`.
- 조건은 연달아 ABAB로 반복합니다. 교통 차량 수와 뷰어 프로세스 CPU를 함께 기록합니다. 수십 분 떨어진 측정끼리는 비교하지 않습니다.
- 센서 렌더 수는 `camera_rig`의 `views[].applied` 증분, 훅 시간은 `hooks`의 timing, SDK 콜백은 `sdk_timing`으로 잽니다. `snapshot.frame_id`는 SDK 프레임(초당 60) 번호라 그 증분으로 나눈 값은 렌더 프레임당 값이 아닙니다. 렌더 프레임당 값은 PresentMon fps로 환산합니다.

## 이전 실측 — core 0.26.1, 2026-10-09(이전 TCP 수신 구성)

FH5 같은 정차 장면에서 각 60초를 측정했습니다. 게임 전경 표본은 모두 100%였고 Foxglove는 종료했습니다. 당시 별도 수신 프로세스를 거친 실제 ROS 소비자가 JPEG 4개·라이다 3개·차량 GT 4개를 구독했습니다. Windows 네이티브 릴레이 노드의 재측정은 [포팅 계획](20_windows_native_port_plan.md) P1 완료 기준입니다. 센서 렌더 해상도는 전방 1280×720·측면 960×544이며 원본 RGB·depth 전송은 껐습니다. 게임 그래픽 설정은 바꾸지 않았습니다.

| 조건 | FPS | 평균 프레임 ms | p50 / p99 ms | CPU / GPU busy 중앙값 ms |
| --- | ---: | ---: | --- | --- |
| JPEG 30 Hz·전체 라이다 10 Hz·GT 30 Hz (`full_30`) | 62.46 | 16.01 | 15.84 / 23.42 | 15.68 / 6.48 |
| JPEG 10 Hz·표시용 라이다 10 Hz·GT 30 Hz (`display`) | 66.00 | 15.15 | 15.20 / 21.83 | 15.06 / 6.29 |

`full_30`은 원본 RGB-D 전체 전송을 뜻하지 않습니다. 두 조건 모두 카메라 요청과 GT는 30 Hz입니다. 표시용 점군은 전체 수직 링을 유지하고 수평 빔 4개마다 하나의 XYZ·range를 전달합니다. 전체 점군의 원래 필드와 10 Hz 출력은 별도 토픽에 유지됩니다.

| 전달·CPU 비용 | full_30 | display |
| --- | ---: | ---: |
| ROS 수신 묶음/초 | 29.91 | 30.03 |
| 대용량 전송 MB/s | 41.16 | 5.24 |
| Windows 릴레이 CPU | 31.41% | 12.41% |
| 수신 VM CPU(현재 구조에는 없음) | 30.99% | 15.01% |
| 상태 왕복 p99 ms | 1.160 | 1.112 |
| native 수집 실패 | 0 | 0 |
| GPU ring이 바빠 넘긴 기회 | 7 | 3 |
| native 발행 큐 누락 | 0 | 3 |
| 릴레이 큐 누락 | 0 | 0 |

CPU 100%는 논리 코어 하나입니다. 수신 VM CPU에는 그 VM의 다른 작업도 포함됩니다. 송수신 카운터의 구간 경계 때문에 전달률이 설정값 30 Hz를 조금 넘을 수 있습니다.

같은 장면의 앞선 0.26.0 연속 렌더 비교는 full_30 **58.11 FPS / p99 25.11ms**, display **62.71 FPS / p99 22.49ms**였습니다. 0.26.1 수집 직전 렌더 방식은 각각 62.46 / 66.00 FPS였습니다. 그때의 센서 끔 기준은 87.06 FPS였습니다. 각 조건을 순서대로 한 번 측정한 결과이며, Foxglove 화면 부하와 주행 성능은 이 수치에 포함되지 않습니다. 자료는 로컬 `research/live/2026-10-09-pipeline-optimized/`, `2026-10-09-pipeline-warmup/`에 있습니다.

## 줄인 작업

- private 센서는 유휴 뒤 요청 뷰를 한 프레임 준비하고 바로 다음 Present에서 수집합니다. 10 Hz·한 뷰·12초의 동일 실패 장면 비교에서 945회 연속 렌더가 240회로 줄고 나무·가로등·깊이를 유지했습니다. [렌더 생략 실패와 현재 수정](history/lessons.md#센서-렌더-생략과-정적-물체-깜빡임).
- 카메라 자세·CameraInfo·TF 요구와 차량 GT 요구를 분리했습니다. 실제 요청된 GT 카메라에서만 차량 목록과 모델 자세를 읽고, actor·형상 작업 배열을 재사용합니다.
- 렌더 관측은 숫자 구조체와 같은 SDK 스냅샷 참조를 전달하며, 완성된 묶음의 전송 작업자가 JSON을 한 번 생성합니다.
- GPU 깊이·라이다 및 노출·축소 영상 작업의 상태 저장을 공유합니다. 릴레이는 카메라 복사를 모아 한 번 Flush하고 같은 이벤트를 재사용하며 각 공유 fence 순서는 유지합니다.
- JPEG는 WIC에 BGR을 직접 전달합니다. 미리보기는 기본 10 Hz 기회에서 pack·readback하며 인지용 축소 RGB는 카메라 주기를 따릅니다.
- 고정 라이다 방향과 projection·픽셀에 따른 빔 오차, CameraInfo 보정 계산을 재사용합니다. 표본 timestamp와 실제 차량 pose는 새로 반영합니다.

실제 ROS 비교에서 전체·표시 점군 738쌍의 선택된 XYZ·range·NaN과 stamp가 같았습니다. 인지용 영상은 약 29.62 Hz, JPEG·라이다는 약 9.95 Hz로 수신됐습니다. 빔 오차의 CPU 참조와 83,763개를 비교한 최대 차이는 3.74×10⁻⁹도였습니다. 구독 전환·출력 없는 유휴·리그 재설정·stream 재시작과 panic 뒤 이전 owner의 재시작 거절을 확인했습니다. 자료는 `2026-10-09-pipeline-contract/`와 warmup의 `lifecycle.json`에 있습니다.

## 비용 분해와 남은 범위

최적화 전 단계별 60초 비교는 센서 끔 80.54 FPS에서 실제 ROS 전달 49.88 FPS까지 평균 프레임 시간이 7.63ms 증가했습니다. 렌더 3.14ms, 관측·pack·공유 GPU 복사 2.11ms, CPU 영상 읽기 0.22ms, JPEG·메시지 생성 0.46ms, TCP·ROS 전달 1.71ms였습니다. 렌더·수집이 증가분의 약 69%였습니다. 현재 측정과 기준 FPS가 다르므로 49.88 → 66.00을 동일 조건의 개선률로 사용하지 않습니다. 원본은 `research/live/2026-10-09-pipeline-cost/`, 재현 방법은 [처리 단계별 진단](../bridge/README.md#처리-단계별-성능-진단)에 있습니다.

현재 full_30의 60초 누적 compile begin은 2.48초, OM bind는 2.98초이며 display는 2.43 / 1.45초입니다. OM 시간에는 GPU pack·복사 명령 제출도 들어갑니다. GT 30 Hz가 요청하는 렌더와 차량 자세 읽기, 공유 GPU readback·드라이버 작업, ROS 전달·표시가 남은 비용입니다.

기존 Foxglove 레이아웃의 점군 패널에서 `/ets2/lidar/{name}/preview/points`를 선택해야 표시용 점군을 사용합니다. 필요한 패널·토픽만 구독하고 모델에는 필요한 `/perception/image_raw`를 추가합니다. 원본 RGB·depth는 구독할 때 고해상도 pack·readback·전송을 수행합니다. 30 Hz 원본 RGB-D 전송, 실제 주행·야간·트레일러는 아직 측정하지 않았습니다. Foxglove 화면과 CPU 배치는 위 [CPU 병목 분석](#cpu-병목-분석)에서 쟀고, DX12는 시험하지 않았습니다.
