# 성능과 다음 진단

## 전경 실측 — 2026-10-09

FH5 정차·같은 장면과 그래픽 설정·각 60초, 기본 미러 활성. CPU 사용률은 논리 코어 하나를 100%로 계산합니다. 고해상도는 전방 1280×720·측면 960×544, 저해상도는 각각 절반입니다.

| 조건 | FPS | 프레임 p50 / p95 / p99 ms | CPU / GPU busy 중앙값 ms | 게임 / 릴레이 CPU |
| --- | ---: | --- | --- | --- |
| 리그 끔 | 77.69 | 12.68 / 15.43 / 17.67 | 12.54 / 4.99 | 153.1% / — |
| 고해상도 리그 연속 렌더 | 63.88 | 15.31 / 18.93 / 22.10 | 15.18 / 4.93 | 153.6% / — |
| 저해상도 전체 브리지 | 61.58 | 14.85 / 22.83 / 26.91 | 14.68 / 5.07 | 153.2% / 35.9% |
| 고해상도 전체 브리지 | 46.35 | 20.81 / 32.01 / 38.15 | 20.59 / 5.71 | 153.5% / 74.7% |
| 고해상도 JPEG·라이다·GT·TF | 64.12 | 14.18 / 23.15 / 26.08 | 14.03 / 4.94 | 155.2% / 28.5% |

마지막 조건은 ROS 소비자가 JPEG·점군·GT·TF를 받는 구성입니다. Foxglove 데스크톱 부하와 perception/image_raw의 비용은 별도 측정합니다. 저해상도·고해상도 전체·미리보기 구성의 상태 왕복 응답 p99는 2.17 / 1.71 / 1.19 ms였습니다. 고해상도 전체 실행은 시작 시 두 묶음이 릴레이 큐에서 누락됐고, 수집 실패는 0회였습니다.

원본: 로컬 `research/live/2026-10-09-optimization/final-*`. 비교는 같은 세션에서 수행합니다. 이전 세션의 약 51 FPS 기준선과 현재 77.69 FPS를 직접 증감률로 비교하지 않습니다.

## 운용 구성

| 용도 | 구독 |
| --- | --- |
| 실시간 표시·주행 개발 | JPEG 미리보기·라이다·GT·TF·상태. 모델은 필요한 perception/image_raw를 추가 |
| 데이터셋 수집 | 필요한 카메라의 원본 RGB·depth·CameraInfo와 상태·TF·GT |

센서 렌더 해상도는 고해상도를 유지하고 구독 채널로 readback 양을 조절합니다. 그래픽 옵션을 올릴 때는 같은 장면에서 다시 비교합니다. 미러 가시거리는 라이다 장거리 관측과 함께 결정합니다.

## 병목 가설

CPU busy가 GPU busy보다 길고 원본 채널 추가 시 프레임 시간이 늘어납니다. 후보는 잔여 hook·가시성 제출 비용, GPU 공유 자원 드라이버 작업, 중계기·WSL의 복사와 스케줄링 경합입니다.

연속 렌더 63.88 FPS와 JPEG 브리지 64.12 FPS는 각각 렌더·전송 작업 구성이 다릅니다. 게이팅 효과와 고정 비용을 분리하려면 아래 조건이 필요합니다. 프로세스 CPU 사용률만으로 같은 작업이 느려진 것인지 추가 작업이 생긴 것인지 구별할 수 없습니다.

## A–G 분해 계획

사용자가 게임을 전경에 둔 뒤 같은 장면에서 각 60초를 측정합니다.

| 조건 | 구성 | 비교 목적 |
| --- | --- | --- |
| A | DLL 로드, hook 0 | 최소 기준선 |
| B | 관측 hook 설치, 리그 끔 | hook 진입 비용 |
| C | 리그 설정, 캡처 요청 없음 | 비수집 프레임의 선택·ego_parts·엔진 작업 |
| D | 고해상도 pack·공유 GPU 복사, 소비 결과 폐기 | 게임 GPU 명령·드라이버 작업 |
| E | D + staging Map·CPU 복사, 전송 없음 | readback 비용 |
| F | E + CDR·TCP·WSL 실제 구독 | 인코딩·전송·ROS 비용 |
| G | F + 측정된 CPU 토폴로지에 맞춘 affinity | CPU·캐시 경합 가설 |

C는 연속 렌더 모드와 분리해 선택·제출 카운터를 확인합니다. D에서도 소비 완료 fence 반환을 유지합니다. D/E는 진단 모드 구현이 필요합니다.

PresentMon CPU/GPU busy·프레임 분포, hook 본문 시간 합계, 선택/제출 수, 게임·릴레이·vmmem CPU와 WSL 내부 ROS CPU, 전달률·큐 누락을 함께 기록합니다. vmmem과 게스트 CPU는 겹치는 회계 범위이므로 합산하지 않습니다.

3700X의 실제 코어·SMT·캐시 구성을 확인한 뒤 affinity를 배치합니다. `.wslconfig`의 processors 값은 vCPU 수를 제한하며 특정 CCX 고정을 보장하지 않습니다. G는 Windows vmmem의 실제 affinity 적용 가능 여부까지 확인해 조건을 명시합니다. 설정은 비교 후 원래 값으로 복구합니다.

## 슬롯과 주행 범위

현재 FH5는 0·1·2·5를 기본 미러로 사용합니다. 다른 트럭·미러 구성에서는 3·4의 사용 여부부터 조사하고 프리셋을 배치합니다. 트레일러, 주야간 장시간 주행, 실제 WSL 주소 변경 복구가 남아 있습니다.
