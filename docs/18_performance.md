# 성능과 병목

## 센서 생성과 ROS 전달 비용 — 2026-10-09

같은 FH5 정차 장면에서 각 60초씩 단계를 추가했습니다. 카메라 30 Hz·라이다 10 Hz, HD 센서 렌더, JPEG 4개·라이다 3개·GT 구독을 유지했습니다. Foxglove는 종료했고 WSL의 ROS 수신기가 같은 11개 센서 토픽을 구독했습니다. 실제 PresentMon 측정 구간의 전경 표본은 모든 조건에서 100%였습니다.

| 마지막 처리 단계 | FPS | 평균 프레임 ms | p99 ms |
| --- | ---: | ---: | ---: |
| 센서 끔 | 80.54 | 12.42 | 16.93 |
| 센서 화면 4개 렌더만 | 64.29 | 15.56 | 21.27 |
| 관측·pack·공유 GPU staging 복사 | 56.62 | 17.66 | 26.23 |
| CPU 영상 읽기까지 | 55.92 | 17.88 | 25.72 |
| JPEG·점군·ROS 메시지 생성까지 | 54.52 | 18.34 | 26.05 |
| TCP 전송·ROS 발행·실제 수신까지 | 49.88 | 20.05 | 29.18 |

평균 프레임 시간 증가분은 렌더 **3.14ms**, 관측·pack·공유 GPU 복사 **2.11ms**, 영상 CPU 읽기 **0.22ms**, JPEG·메시지 변환 **0.46ms**, TCP·ROS 전달 **1.71ms**였습니다. 전체 증가 7.63ms 중 렌더·수집 단계가 약 69%입니다. 작은 단계 차이는 한 번의 60초 비교값입니다.

| CPU 사용률 — 논리 코어 하나 = 100% | GPU 복사까지 | CPU 읽기까지 | 메시지 생성까지 | 실제 ROS 전달 |
| --- | ---: | ---: | ---: | ---: |
| 게임 | 152.12% | 150.95% | 150.65% | 152.56% |
| Windows 릴레이 | 9.26% | 13.77% | 41.04% | 44.15% |
| vmmemWSL | 7.64% | 6.50% | 8.59% | 38.07% |

실제 ROS 전달 단계의 CPU/GPU busy 중앙값은 19.42/6.05ms였습니다. ROS 전달 비교에는 TCP 송수신·WSL·DDS 발행·구독자 처리가 함께 들어 있습니다. GPU 복사 단계에서 릴레이의 상태 중계도 시작하므로 해당 2.11ms에 포함됩니다. 이후 모든 수집 단계에서 상태 TCP와 lease를 유지합니다. GPU 복사 조건도 소비 완료 fence를 반환하고 DLL의 작은 라이다·노출 버퍼는 읽습니다.

GPU 복사·CPU 읽기·메시지 생성 단계의 센서 송신은 0개였고, 각각 약 30묶음/초를 계속 소비했습니다. 최종 단계는 약 41.3 MB/s를 전송했습니다. ROS에서 카메라·GT 각각 1,917개와 라이다 각각 640개를 수신했고 영상·GT stamp 전체가 일치했습니다. 라이다 stamp도 해당 영상 stamp의 부분집합입니다. 수집 실패·발행 큐 누락·릴레이 큐 누락은 모두 0회였습니다.

현재 우선순위는 센서 렌더·관측·pack 비용입니다. 전송 최적화의 측정 대상은 약 1.71ms이며, Foxglove 표시 비용은 아래 별도 비교에 있습니다. 진단 실행은 [브리지 처리 단계](../bridge/README.md#처리-단계별-성능-진단)를 사용합니다. 원본은 로컬 `research/live/2026-10-09-pipeline-cost/`에 있습니다.


## 메타데이터 최적화 전후

FH5 같은 정차 장면·그래픽 설정에서 각 60초를 측정했습니다. 카메라 30 Hz·라이다 10 Hz, 전방 1280×720·측면 960×544 센서 렌더, JPEG 4개·라이다 3개·차량 GT를 사용했습니다. 원본 RGB·depth 전송은 껐고 전경 표본은 모두 100%였습니다.

| 조건 | FPS | 프레임 p50 / p99 ms | CPU / GPU busy 중앙값 ms |
| --- | ---: | --- | --- |
| 변경 전 0.24.5 + 현재 Foxglove 화면 | 35.66 | 27.05 / 42.92 | 26.88 / 7.84 |
| 숫자 관측·공통 참조 적용 0.25.0 + 같은 화면 | 39.72 | 24.19 / 38.48 | 24.02 / 7.35 |
| 0.25.0, Foxglove 연결 없이 ROS 소비 | 49.45 | 19.77 / 29.85 | 19.62 / 6.70 |

같은 Foxglove 조건에서 FPS는 11.4% 증가하고 프레임 p99는 10.3% 줄었습니다. compile begin의 60초 누적 실행 시간은 **10.630 → 4.517초**, OM bind는 **4.331 → 3.537초**였습니다. 평균 호출 시간은 각각 31.38 → 12.68µs, 27.17 → 18.42µs입니다. OM 시간에는 GPU pack·복사 명령 제출도 들어 있습니다.

| CPU 사용률 — 논리 코어 하나 = 100% | 변경 전 | 0.25.0 | 0.25.0, Foxglove 연결 제외 |
| --- | ---: | ---: | ---: |
| 게임 | 155.64% | 154.75% | 149.57% |
| Windows 릴레이 | 38.65% | 44.61% | 44.61% |
| vmmemWSL | 70.67% | 68.61% | 40.36% |
| Foxglove 프로세스 합계 | 189.38% | 186.30% | 53.54% |

Foxglove 제외 조건도 실제 ROS 소비자가 JPEG·라이다·GT를 받습니다. Foxglove 서버·WebSocket 전송·화면 갱신과 그 화면의 추가 토픽 구독을 함께 제외한 결과입니다. 데스크톱 앱은 열어 두었습니다. 표시 경로를 분리하니 FPS가 39.72 → 49.45로 올랐습니다. vmmem에는 ROS 외의 WSL 작업도 포함됩니다.

0.25.0 + Foxglove의 ROS 수신은 29.81묶음/초, 상태 왕복 지연은 p50 0.791ms·p99 2.126ms였습니다. 종료 시 DLL 수집 실패·발행 큐 누락은 0회, 릴레이 송신 대기 큐 누락은 1회, GPU ring이 바빠 수집 기회를 넘긴 횟수는 15회였습니다. Foxglove 제외 시험에서는 카메라·GT 각 1,918개와 라이다 각 642개를 ROS에서 받았습니다. 카메라 29.85 Hz·라이다 9.99 Hz이며 GT와 영상 stamp 전부가 일치하고 라이다 stamp는 그 부분집합입니다.

앞선 측정의 0.24.5 46.04 FPS는 Foxglove CPU가 28.52%인 화면 구성이었습니다. 이번 35.66 FPS 기준치는 같은 게임에서 새로 측정했습니다. 이전 세션 수치를 새 변경의 전후 비교에 섞지 않습니다.

## 수집 경로 최적화

- 고정된 엔진 주소표를 숫자 구조체로 한 번 해석합니다.
- 실제 카메라·차량 렌더 자세는 compile 시점에 숫자 구조체로 읽고, 같은 SDK 스냅샷은 불변 참조로 공유합니다.
- 명령 구간과 GPU 슬롯은 같은 표본을 참조합니다. 캡처가 완성되면 전송 작업자가 JSON을 한 번 생성합니다.
- ROS 수집은 슬롯 번호와 출력 종류로 식별합니다. 상세 pass·이미지 연결 이름과 전체 SDK 채널은 원시 캡처·수동 진단에서 만듭니다.
- GT는 해당 카메라에서 요청한 묶음에만 읽습니다. 실제 수집에서 GT 요구를 오른쪽 포드에서 전방 광각으로 전환해 확인했습니다.
- 무관한 pass는 명령 블록 vector를 만들지 않습니다. 빈 명령 버퍼 경계에서 이전 이름과 표본을 해제합니다.
- OM 바인딩은 유지 중인 RTV 포인터로 반복 리소스 조회를 줄입니다. 깊이+라이다, 자동 노출+영상 변환은 GPU 상태 저장·복원을 각각 한 번으로 묶습니다.
- 릴레이는 BELOW_NORMAL 우선순위를 사용합니다. 코어 affinity·게임 그래픽 설정은 기존 값을 유지합니다.

원시 진단 캡처는 기존 Python 차량 박스·라이다 복원 도구에서 읽힙니다. 같은 픽셀을 선택한 GPU·CPU 유효 빔 83,479개의 최대 거리 차이는 0.149mm였습니다. 픽셀 경계에서 서로 다른 참조 픽셀을 고르는 311개 빔은 별도로 남습니다. 수동 draw 관측의 차량 상수 버퍼도 전방 광각 2개·오른쪽 포드 7개를 확보했습니다. 자료는 `research/live/2026-10-09-metadata-reference/`에 있습니다.

## 운용 구성과 남은 비용

활성 리그는 매 프레임 렌더합니다. 렌더를 건너뛰면 나무·가로등이 사라지므로, pack·readback에만 요청 주기와 구독 조건을 적용합니다. 새 리그의 첫 장면 준비가 끝난 뒤 stream 수집을 시작합니다.

| 용도 | 구독 |
| --- | --- |
| 실시간 표시·주행 개발 | JPEG 미리보기·라이다·GT·TF·상태. 모델은 필요한 perception/image_raw를 추가 |
| 데이터셋 수집 | 필요한 카메라의 원본 RGB·depth·CameraInfo와 상태·TF·GT |

현재 60초의 compile begin 누적 4.52초와 OM bind 3.54초가 남은 게임 측 비용입니다. GT의 pass별 차량 목록·렌더 자세 읽기는 유지합니다. Foxglove 표시 경로도 별도의 큰 비용이므로 필요한 패널·토픽만 열어 사용합니다. CPU·캐시 경합과 공유 GPU 드라이버 비용은 아래 단계별 비교로 분리합니다.

센서 해상도와 그래픽 옵션을 바꿀 때는 같은 장면에서 비교합니다. 미러 가시거리는 라이다 장거리 관측과 함께 결정합니다. 원본 RGB·depth의 30 Hz 전송 비용은 별도 측정 대상입니다.

## 추가 분해 항목

사용자가 게임을 전경에 둔 뒤 같은 장면에서 각 60초를 측정합니다.

| 조건 | 구성 | 비교 목적 |
| --- | --- | --- |
| A | DLL 로드, hook 0 | 최소 기준선 |
| B | 관측 hook 설치, 리그 끔 | hook 진입 비용 |
| C | 리그 설정, 캡처 요청 없음 | 비수집 프레임의 선택·ego_parts·엔진 작업 |
| D | 고해상도 pack·공유 GPU 복사, 소비 결과 폐기 | 게임 GPU 명령·드라이버 작업 |
| E | D + staging Map·CPU 복사, 전송 없음 | readback 비용 |
| F | E + CDR·TCP·WSL 실제 구독 | 인코딩·전송·ROS 비용 |
| G | F + 측정된 CPU 토폴로지에 맞춘 affinity | CPU·캐시 경합 가설 |

C는 현재 연속 렌더 비용을 포함하며 수집·전송은 끕니다. D에서도 소비 완료 fence 반환을 유지합니다. D/E와 메시지 생성·전송 단계는 위의 처리 단계별 진단으로 측정했습니다. B와 G는 추가 비교 대상입니다.

PresentMon CPU/GPU busy·프레임 분포, hook 본문 시간 합계, 선택/제출 수, 게임·릴레이·vmmem CPU와 WSL 내부 ROS CPU, 전달률·큐 누락을 함께 기록합니다. vmmem과 게스트 CPU는 겹치는 회계 범위이므로 합산하지 않습니다.

3700X의 실제 코어·SMT·캐시 구성을 확인한 뒤 affinity를 배치합니다. `.wslconfig`의 processors 값은 vCPU 수를 제한하며 특정 CCX 고정을 보장하지 않습니다. G는 Windows vmmem의 실제 affinity 적용 가능 여부까지 확인해 조건을 명시합니다. 설정은 비교 후 원래 값으로 복구합니다.

## 슬롯과 주행 범위

현재 FH5는 0·1·2·5를 기본 미러로 사용합니다. 다른 트럭·미러 구성에서는 3·4의 사용 여부부터 조사하고 프리셋을 배치합니다. 트레일러, 주야간 장시간 주행, 실제 WSL 주소 변경 복구가 남아 있습니다.
