# 성능과 다음 진단

## 전경 실측 — 2026-10-09

FH5 같은 정차 장면·그래픽 설정에서 조건마다 60초 측정했습니다. 모든 조건의 전경 표본이 100%였고, 브리지는 고해상도 센서 렌더·JPEG 미리보기 4개·라이다 3개·GT·Foxglove를 사용했습니다. 카메라 요청은 30 Hz, 라이다는 10 Hz입니다. 원본 RGB·depth 전송은 껐습니다.

| 조건 | FPS | 프레임 p50 / p99 ms | CPU / GPU busy 중앙값 ms |
| --- | ---: | --- | --- |
| 브리지 끔, hook 0 | 78.44 | 12.73 / 17.13 | 12.60 / 4.97 |
| 센서 리그 연속 렌더 | 62.13 | 15.84 / 21.75 | 15.70 / 5.19 |
| 전체 브리지 0.24.1 | 31.39 | 30.85 / 46.10 | 30.70 / 9.17 |
| 관측 범위 축소 후 0.24.2 | 39.24 | 24.93 / 38.65 | 24.76 / 7.67 |

리그를 추가한 프레임 중앙값 증가는 3.11ms, 0.24.1의 수집·브리지 추가 증가는 15.01ms였습니다. CPU busy가 GPU busy보다 길었습니다. 이 장면의 주 병목은 CPU 측 작업입니다.

0.24.2는 수집 중인 카메라의 출력만 이름·메타데이터로 만들고, attributes_0을 **출력하는 형상 pass**에서만 카메라·차량 자세를 읽습니다. 기본 미러와 attributes_0을 입력으로 사용하는 후처리 pass의 반복 계산을 제거했습니다. 명령 버퍼 pool 재사용 시 이전 카메라 이름이 섞이지 않게 수명을 추적합니다.

compile begin callback 누적 시간은 60초 구간에서 18.44 → 10.71초, 호출당 평균은 52.49 → 30.63µs로 줄었습니다. FPS는 25.0% 증가했습니다. 영상 해상도·요청 주기·GT 출력은 유지했습니다. 실제 ROS에서 차량 박스와 영상·라이다 수신을 확인했고, 정차 나무의 사라짐은 재발하지 않았습니다.

| 전체 브리지 CPU 사용률 | 0.24.1 | 0.24.2 |
| --- | ---: | ---: |
| 게임 | 145.74% | 152.15% |
| Windows 릴레이 | 40.50% | 48.61% |
| vmmemWSL | 60.73% | 63.85% |
| Foxglove 프로세스 합계 | 29.00% | 28.77% |

논리 코어 하나를 100%로 계산했습니다. vmmemWSL은 ROS 외의 WSL 작업도 포함합니다. 0.24.2의 전송 큐 누락·수집 실패는 측정 종료 시 0회였고 GPU ring이 바빠 수집 기회를 넘긴 횟수는 실행 시작부터 13회였습니다. 30 Hz는 요청값이며 모든 수집 기회가 완료되는 보장은 없습니다.

원본: 로컬 `research/live/2026-10-09-visibility-performance/`, `2026-10-09-visibility-performance-optimized/`. 이전 0.22.0의 10 Hz 비교는 `research/live/2026-10-09-optimization/final-*`에 있습니다.

0.24.3은 센서와 무관한 pass의 명령 블록 vector 할당을 없애고, 빈 명령 버퍼 경계에서 이전 이름을 지웁니다. OM 바인딩은 수집 중인 RTV 참조를 유지해 같은 포인터의 반복 리소스 조회를 생략합니다. 실제 ROS에서 카메라·GT 각각 433회와 라이다 144–145회를 받았습니다. 0.24.4는 깊이 변환+라이다 gather, 자동 노출+영상 변환의 GPU 상태 저장·복원을 각각 한 번으로 묶었습니다. 전경 성능 비교는 사용자 준비 후 진행합니다.

## 운용 구성과 남은 비용

활성 리그는 매 프레임 렌더합니다. 렌더를 건너뛰면 나무·가로등이 사라지므로, pack·readback에만 요청 주기와 구독 조건을 적용합니다. 새 리그의 첫 장면 준비가 끝난 뒤 stream 수집을 시작합니다.

| 용도 | 구독 |
| --- | --- |
| 실시간 표시·주행 개발 | JPEG 미리보기·라이다·GT·TF·상태. 모델은 필요한 perception/image_raw를 추가 |
| 데이터셋 수집 | 필요한 카메라의 원본 RGB·depth·CameraInfo와 상태·TF·GT |

개선 후에도 리그만 실행한 62.13 FPS와 전체 브리지 39.24 FPS 사이에 비용이 남아 있습니다. 계측된 compile begin의 누적 10.71초, OM bind callback의 3.98초가 다음 관측 코드 최적화 대상입니다. OM callback에는 GPU pack·복사 명령 제출도 포함됩니다. CPU·캐시 경합과 공유 GPU 드라이버 비용은 아래 단계별 비교로 분리합니다.

센서 해상도와 그래픽 옵션을 바꿀 때는 같은 장면에서 비교합니다. 미러 가시거리는 라이다 장거리 관측과 함께 결정합니다. 원본 RGB·depth의 30 Hz 전송 비용은 별도 측정 대상입니다.

## A–G 분해 계획

사용자가 게임을 전경에 둔 뒤 같은 장면에서 각 60초를 측정합니다.

| 조건 | 구성 | 비교 목적 |
| --- | --- | --- |
| A | DLL 로드, hook 0 | 최소 기준선 |
| B | 관측 hook 설치, 리그 끔 | hook 진입 비용 |
| C | 리그 설정, 캡처 요청 없음 | 비수집 프레임의 선택·ego_parts·엔진 작업 |
| D | 고해상도 pack·공유 GPU 복사, 소비 결과 폐기 | 게임 GPU 명령·드라이버 작업 |
| E | D + staging Map·CPU 복사, 전송 없음 | readback 비용 |
| F | E + CDR·TCP·WSL 실제 구독 | 인코딩·전송·ROS 비용 |
| G | F + 측정된 CPU 토폴로지에 맞춘 affinity | CPU·캐시 경합 가설 |

C는 현재 연속 렌더 비용을 포함하며 수집·전송은 끕니다. D에서도 소비 완료 fence 반환을 유지합니다. D/E는 진단 모드 구현이 필요합니다.

PresentMon CPU/GPU busy·프레임 분포, hook 본문 시간 합계, 선택/제출 수, 게임·릴레이·vmmem CPU와 WSL 내부 ROS CPU, 전달률·큐 누락을 함께 기록합니다. vmmem과 게스트 CPU는 겹치는 회계 범위이므로 합산하지 않습니다.

3700X의 실제 코어·SMT·캐시 구성을 확인한 뒤 affinity를 배치합니다. `.wslconfig`의 processors 값은 vCPU 수를 제한하며 특정 CCX 고정을 보장하지 않습니다. G는 Windows vmmem의 실제 affinity 적용 가능 여부까지 확인해 조건을 명시합니다. 설정은 비교 후 원래 값으로 복구합니다.

## 슬롯과 주행 범위

현재 FH5는 0·1·2·5를 기본 미러로 사용합니다. 다른 트럭·미러 구성에서는 3·4의 사용 여부부터 조사하고 프리셋을 배치합니다. 트레일러, 주야간 장시간 주행, 실제 WSL 주소 변경 복구가 남아 있습니다.
