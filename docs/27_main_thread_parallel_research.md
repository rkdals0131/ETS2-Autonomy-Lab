# 메인 스레드 병렬화 연구

2026-10-14 시작. ETS2 메인 스레드의 일을 다른 코어로 옮길 수 있는지 엔진을 직접 분석해 확인합니다. 표시는 ✔ 확인, △ 추정입니다. 일을 줄이는 최적화는 [26 CPU 최적화 계획](26_cpu_optimization_plan.md)에 있고, 이 문서는 그 다음 단계입니다.

## 1. 범위

- 엔진 전체를 다시 짜지 않습니다. 소스 없이 가능한 형태는 두 가지입니다.
  1. **훅 안 fork-join**: 핫 함수 하나를 훅하고, 그 안의 반복을 여러 스레드로 나눈 뒤 반환 전에 모두 기다립니다. 바깥에서 보면 순서가 같습니다.
  2. **엔진 worker로 넘기기**: 엔진의 작업 제출 함수를 찾아, 메인 스레드가 하던 독립 작업을 기존 worker 풀에 넣습니다.
- 개인 싱글플레이용입니다. 실행 파일은 바꾸지 않고, 지금처럼 런타임 훅 DLL로만 적용합니다.
- 기대치: 4 ms짜리 일을 4코어로 완벽히 나눠도 3 ms이고, 현재 프레임 24–28 ms의 약 11%입니다. [C3](26_cpu_optimization_plan.md#c3-메인-스레드-전용-코어-s-구현-완료-게임-확인-남음) CPU 배치가 −5.9 ms였습니다.

## 2. 전제

- ✔ 메인 스레드 하나가 게임 로직·장면 준비·D3D11 제출을 맡고 병목입니다([18](18_performance.md#cpu-병목-분석)).
- ✔ 엔진은 이미 스레드를 씁니다. `game.log.txt`: `using 6 worker thread(s)`, IO worker 3, real-time worker 3. PhysX CPU dispatcher 2스레드. 이 worker들이 프레임 중에 얼마나 노는지는 아직 모릅니다.
- ✔ `eurotrucks2.exe` 1.61.1.1: 53 MB, `.text` 31 MB. `.pdata` 120,236항목 중 53,466개는 다른 함수에 딸린 chained 조각이라, unwind 정보가 있는 함수는 66,770개입니다. leaf 함수는 따로 있습니다.
- ✔ 기존 훅 주소는 모두 함수 중간입니다. 예: compile begin `0x2B1B40`과 end `0x2B266A`는 함수 `0x2B1A30` 안, rig select `0x538A4E`는 `0x538860` 안.
- △ 우리 작업에서 가장 유력한 후보는 뷰별 장면 준비(가시성·후보 선택)입니다. 센서 4뷰와 준비 렌더로 뷰 수가 배로 늡니다. 다만 엔진이 뷰마다 이전 프레임 가시성 상태를 쓰는 것으로 보여([26 C1](26_cpu_optimization_plan.md)), 아래 조건 3에 걸릴 수 있습니다.

## 3. 후보 조건

후보 함수는 모두 만족해야 구현합니다.

1. 메인 스레드에서 프레임당 2 ms 이상(`hotspots` inclusive).
2. 서로 독립인 원소(뷰, 차량, 오브젝트 묶음)의 반복.
3. 반복 본문이 공유 상태에 쓰지 않음. 엔진 할당기, 참조 카운트, 전역 캐시, 로그, 난수, "이전 프레임" 상태. D3D11 immediate context 호출도 안 됩니다.
4. 패턴으로 다시 찾을 수 있는 훅 경계. 게임 업데이트마다 `ot/schema`처럼 다시 고정합니다.
5. 반복 결과를 합치는 순서가 결과를 바꾸지 않음(예: 목록에 덧붙이는 순서가 그리기 순서가 되면 안 됨).
6. 본문이 작업 시스템이나 그 전역 락(`0x304B2E8`)을 다시 쓰지 않음. 중첩 대기는 교착할 수 있습니다.

## 4. 도구

### 메인 스레드 호출 스택 (core 0.34.0, ✔ 게임 없는 시험)

- `main_profile`에 `depth`를 주면 샘플마다 호출 스택을 풉니다. 함수 단위 inclusive 시간이 있어야 "어느 반복이 비싼지"를 고를 수 있습니다.
- `RtlLookupFunctionEntry`는 함수 테이블 락을 잡을 수 있고, `RtlVirtualUnwind`는 잘못된 프레임에서 예외를 냅니다. 둘 다 로더 안에서 멈춘 메인 스레드와 교착할 수 있어 쓰지 않습니다. SEH로 감싸는 것도 대안이 아닙니다. 게임의 VEH·크래시 핸들러가 먼저 받고, 디스패치가 함수표 락을 잡을 수 있습니다.
- `stack_unwind.cpp`는 시작 때 참조를 잡아 둔 모듈(`GetModuleHandleExW`, 실행 끝에 해제)의 unwind 데이터·코드와 대상 스레드의 `[RSP, StackBase)`만 읽습니다(prologue 부분 실행, epilogue, chained unwind, machine frame 처리). 실행 중 모듈이 내려가 같은 주소에 다른 모듈이 올라오는 경우도 읽던 메모리가 사라지지 않습니다. 시작 때 `.pdata`와 모든 UNWIND_INFO를 한 번 읽어 두어, 정지 중 첫 접근 page fault를 피합니다.
- `ot_unwind_test` 결과(2026-10-14): 게임 exe·ntdll·kernel32·KernelBase·d3d11을 이미지로 매핑해, 모든 `.pdata` 항목(chained 조각 포함)을 본문 시작과 prologue 각 지점에서 우리 unwinder와 `RtlVirtualUnwind`로 풀었습니다. 446,572개 중 446,553개가 RIP·RSP·정수 레지스터 16개 모두 같았습니다.
  - 남은 19개는 모두 `jmp rel32`로 시작하는 chained 조각입니다. d3d11 18개는 PGO cold 코드가 본문으로 돌아가는 5바이트 jmp이고, exe 1개(`0x5CA0B8`)는 switch 표로 보이는 데이터입니다.
  - `RtlVirtualUnwind`는 이 jmp를 꼬리 호출 epilogue로 보고 반환 주소만 꺼내고, 우리는 부모 prologue를 되돌립니다. 이 지점에서는 프레임이 살아 있어 우리 쪽이 맞다고 봅니다(△). 비동기 샘플이 그 명령 하나에 걸릴 때만 차이가 납니다.
  - 남은 차이: `UWOP_SET_FPREG_LARGE`(op 11)는 처리하지 않아 `bad_frame`으로 끝나지만, 위 이미지에는 없습니다.
- `ot_sampler_test` 결과(2026-10-14):
  - 오라클: `RtlCaptureContext` 문맥을 우리 unwinder로 푼 결과가 `RtlCaptureStackBackTrace`와 9프레임 모두 같음. alloca(frame pointer), `__chkstk` 큰 프레임, XMM 저장, 레지스터 7개 보존 함수를 거침.
  - 샘플: 1,275개 스택 100%가 스레드 시작까지 풀리고, 100%가 두 호출자를 지남.
  - 교착: 힙을 계속 잡는 스레드, `LoadLibrary`/`FreeLibrary`를 3초에 약 7,500번 하는 스레드 모두 끝까지 샘플.
  - 모듈 참조: 표가 잡은 동안 `FreeLibrary`한 모듈이 매핑돼 있고, 해제 뒤 내려감.
  - 정지 시간: depth 48에서 평균 약 31 µs(RIP만 25 µs), 250 Hz면 메인 스레드의 약 0.8%.
- safetyhook 트램펄린 같은 익명 코드에서 오는 반환 주소는 풀 수 없어 `unknown_code`로 끝납니다. 우리 훅 안의 샘플은 엔진 호출자를 잃지만, 훅 시간은 `hooks`로 따로 잽니다.

### perf 확장

- `ot.cmd perf <label> [--profile-hz 250] [--profile-depth 48]`: 기존 항목에 더해 게임 스레드별 CPU(`threads`: 이름, 시작 주소 module+RVA, 코어)를 항상 남기고, `--profile-hz`가 있으면 스택을 `<label>.stacks.json`에 남깁니다. 화면 출력에 샘플러 상태(정지 평균·최대, 평균 프레임 수, 스택 끝 분포)와 바쁜 스레드 10개(메인 스레드 표시)가 나옵니다.
- `ot.cmd hotspots <json...> [--top 40] [--focus eurotrucks2.exe+0xRVA] [--folded out.txt]`: 함수별 self·inclusive ms/프레임, 스택 끝 분포, 한 함수의 호출자·피호출자, speedscope용 folded stacks. 프레임은 디스크의 `.pdata`로 함수에 매핑하고, Ghidra 함수표가 있으면 leaf 함수(3,926개)와 이름을 붙입니다. 여러 파일을 합칠 때 샘플은 자기 파일의 샘플당 시간으로 가중합니다.
- `ot.cmd main_profile stacks --out <file>`: perf 없이 돌린 `main_profile`의 스택을 저장합니다(fps가 없어 비중만 나옴).

### Ghidra 영구 프로젝트

- Ghidra 12.1.4(`research/tools/`, 취득 기록은 [research](../research/README.md)), JDK 23. 프로젝트는 `research/ghidra/projects/`(Git 제외)에 한 번만 분석해 둡니다. ✔ 2026-10-14 자동 분석 1,676초(약 28분, 힙 14 GB 한도·14코어), 프로젝트 664 MB, 함수 70,696개. 이름이 붙은 함수는 1,216개이고 대부분 정적 링크된 MSVC 런타임(ConcRT 등)입니다.
- `py -3 research/ghidra/ghidra.py import | export | decompile <rva...> | refs <rva...>`. 조회는 읽기 전용으로 열어 프로젝트를 바꾸지 않고, 한 번에 15–20초입니다. `export`는 `research/ghidra/out/eurotrucks2.functions.csv`(hotspots 이름), `decompile`은 `out/decomp/<entry>.c`(호출자·피호출자, 요청 주소 주변 명령, C 의사코드), `refs`는 전역·vtable·함수를 참조하는 모든 위치를 씁니다.
- 엔진 assert 문자열에 소스 경로(`prism/src/p3core/...`)와 맹글된 타입 이름(`array_t<prism::thread::task_t*>` 등)이 남아 있어, 이름 없는 함수의 역할을 고르는 데 씁니다.
- REA(morluto/rea)는 쓰지 않았습니다. Windows에서 읽기 전용 P0이고, 세션마다 임시 DB에 다시 import·분석해서 53 MB 실행 파일에는 매번 큰 비용이 듭니다. 함수 이름도 저장하지 않습니다.

✔ 2026-10-14 Ghidra 디컴파일과 참조로 확인했습니다. 주소는 1.61.1.1 RVA입니다.

| 풀 생성 | `0x167660` | 풀 크기를 쓰고 작업 관리자 전역을 만듦. 스레드 priority·ideal processor 설정 |

- `prism::thread::task_t` 배치: `+0x00` vtable, `+0x08/+0x10` 목록 연결, `+0x18` 소유자, `+0x20` 상태(0 생성, 1 대기열, 2 실행, 3 끝, 4 회수), `+0x26` 우선순위, `+0x27` 남은 실행자 수, `+0x28` 실행 중 수. 한 작업을 여러 worker가 동시에 실행하는 구조입니다.
- 작업 종류 문자열 33개: 로딩(`sector_load`·`map_load`·`resource_data`·`gameplay_loading` 등), 저장·프로필·스크린샷·이미지, 경로(`route`·`lane_routing`·`navigation_gen`), `instance_task_t`, `dynamic_billboard_task_t`, DX12 PSO 생성(`compile_pipeline_task_t`, DX11에서는 안 씀).
- parallel-for: `parallel_loop_task_t`(vtable `0x21EC488`, execute `0x190C70`).
  - 호출자 스택에 작업 객체(약 0xA8바이트)를 만들고, 표 [0]으로 일반 풀에 넣은 뒤 [3]으로 함께 일하며 기다립니다. 실행자 수는 일반 worker 수+1(`[0x304B300]+1`, 255 한도), 우선순위 1, 소유자는 작업 관리자 표라 실행자마다 부르는 완료 콜백은 빈 함수입니다.
  - execute는 `+0x40`의 본문 함수를 `+0x38` 캡처 포인터와 함께 부를 뿐입니다. 본문(예: `0xC74B80`·`0xC74F70`)은 작업 `+0x88` 원자 카운터에서 512개 단위 덩어리를 가져가 처리하고, 남은 덩어리가 없을 때까지 반복합니다. 그래서 바쁜 worker가 오지 않아도 도착한 실행자(대기하는 스레드 포함)만으로 끝납니다.
  - 쓰는 곳은 맵 에디터(서브맵 가져오기, KDOP 트리, 이정표 재계산, 마커)와 DirectStorage 결과 처리(`0x18B810`)뿐입니다.
- 엔진 스레드는 TLS에 실행 문맥을 둡니다. 문맥이 없는 스레드가 작업을 돌리면 `0x167F30`이 `0x119F40`으로 문맥을 지연 생성하고 `[thread] Detected an alien thread with missing run context priming.`을 한 줄 남깁니다. 우리 스레드도 돌아는 갑니다.

해석(△, M0에서 확인):

- 주행 중 매 프레임 시뮬레이션·DX11 장면 준비는 엔진 작업 시스템을 거의 거치지 않습니다. worker는 비동기 로딩·저장·경로 계산용이라, 주행 중에는 대부분 놀고 있을 가능성이 큽니다. 근거는 작업 종류 문자열뿐이고, `instance_task_t`(`0xA58C30`)와 `dynamic_billboard_task_t`는 프레임 단위 렌더 준비일 수 있습니다.
- 그렇다면 코어는 이미 남아 있고, 문제는 메인 스레드 일을 안전하게 나눌 수 있느냐입니다(조건 3).
- M3는 우리 스레드 풀보다 엔진의 `parallel_loop_task_t`를 쓰는 쪽이 낫습니다.
  - CPU 예산: C3 배치가 게임을 CPU 0–7에 묶었고 엔진 스레드가 이미 14개입니다. 스레드를 더 만들기보다 노는 worker를 쓰는 편이 맞습니다.
  - 엔진 worker는 TLS 문맥이 준비돼 있어, 본문이 스레드 문맥을 쓰는 엔진 함수를 불러도 경고가 없습니다.
  - 덩어리 원자 배분이라 메인 스레드 혼자서도 끝까지 처리되고, worker가 오는 만큼 빨라집니다.

열린 질문:

- M3에서 `parallel_loop_task_t`를 우리가 직접 구성할지, 엔진의 기존 직렬 반복을 훅해 병렬 본문으로 바꿀지. M2 후보 표에 이 열을 넣습니다.
- 직렬 큐 클래스(`0x1905xx`)를 쓰는 쪽을 M1 잔여로 확인합니다. worker 유휴 해석에 영향이 있습니다.
- depth 기본값 48과 64는 M0 smoke의 `depth` 끝 비율로 정합니다.

같은 날 더 읽은 결과(✔ 디컴파일과 `--focus`, 의미는 △):

- 미러 반복 `0x4D4450`의 시간은 가시성 `0x4D4210` 0.87 ms와 렌더 큐 `0x147B0E0` 0.45 ms가 거의 전부입니다. 뷰 등록 `0x41CCF0`은 0.013 ms입니다.
- 반복 본문은 항목마다 전역 `DAT_143645580+0xD0/0xD4`(뷰 크기로 보이는 float 2개)를 설정한 뒤 `"mirror%u"`로 `0x41CCF0`를 부르고, 반복이 끝나면 1024×768로 되돌립니다. 반복끼리 전역 하나를 거쳐 값을 넘기므로 **뷰 반복을 통째로 나누는 것은 조건 3에 걸립니다**.
- 무거운 부분은 뷰마다 부르는 `0x62DA80`입니다. 이 함수는 전역 등록 목록(`PTR_DAT_142d8c388`, 끝 `0x2D8C398`)의 렌더 시스템마다 `vtable+0x38`(뷰 준비)을 부르는 방송이고, 메인 뷰·미러·`0x4CFDB0` 경로에 모두 나옵니다. `0x977CA0`은 그중 한 시스템의 처리 함수입니다.
- 그 아래 `0x15E1380`은 `model_hookup_u` 배열(`+0x320`, 개수 `+0x328`, 켜짐 비트 `+0x190`)을 돌며 항목마다 `vtable+0x90`을 부르는 객체별 반복입니다(호출자 10곳). 더 아래 `0x15817F0`(4.4 KB)은 `vec_t<float,2/3>` 배열을 다룹니다. 뷰 방향에 맞춘 정점 생성으로 추정합니다.

M2 순위는 이렇게 바꿉니다.

1. hookup 반복 `0x15E1380`: 조건 2는 구조상 ✔. 조건 3은 `vtable+0x90` 구현들(`0xA2E470` → `0x156DD70` → `0x1582930` → `0x15817F0`)이 공유 버퍼에 쓰는지 확인해야 합니다. `parallel_loop_task_t`의 512개 덩어리 배분과 모양이 맞습니다.
2. 방송 `0x62DA80`의 시스템별 호출: 시스템끼리 독립인지 확인해야 합니다(조건 3·5).
3. 미러 반복 전체: 전역 뷰 상태 때문에 보류.

다음 확인: hookup `vtable+0x90` 구현과 `0x15817F0`의 쓰기 대상, 센서 켬 측정에서 `0x62DA80`·`0x15E1380`이 뷰 수에 비례하는지, 주행 표본에서 worker 사용량.

## 7. 단계

| 단계 | 크기 | 내용 | 완료 기준 |
| --- | --- | --- | --- |
| M0 | S, 게임 | core 0.34.0 설치 뒤 [26 §6](26_cpu_optimization_plan.md#6-다음-게임-세션-진행) 측정에 스택을 함께 기록 | ✔ 브리지 끔 정차(§6). 남은 것: 센서 켬, 주행 표본 |
| M1 | M | 엔진 worker 시스템 분석 | ✔ 정적 분석 완료(§5). 남은 것: M0 스레드 표로 worker가 주행 중 노는 비율 |
| M2 | M | `hotspots` 상위 30개 함수를 디컴파일해 조건 4개로 분류 | 후보 표. 통과 0이면 이 연구는 접고 26의 일 줄이기에 집중 |
| M3 | L, 연구 | 후보 하나로 fork-join 또는 엔진 worker 제출 시제품 | 같은 입력에서 단일·병렬 결과 해시 일치, 장시간 주행 무충돌, ABAB에서 frame time 감소 |

- CPU 배치(C3)는 게임을 CPU 0–7에 묶고 메인 스레드에 CPU 2를 줍니다. 엔진 worker 6+3+3과 PhysX 2개가 남은 7개 논리 CPU를 나눠 씁니다. M0의 스레드 표에서 worker가 바쁘면 배치를 다시 정합니다.
