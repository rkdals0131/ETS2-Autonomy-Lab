# 카메라와 데이터 설계

Phase 1은 전방 두 뷰와 좌우 미러 포드의 측후방 두 뷰를 사용합니다. 뷰별 인지와 객체 수준 융합을 우선하며, 6뷰 BEV는 후속 연구로 둡니다. [사용자가 정한 센서 구성](14_phase1_highway_sensors.md)과 [실제 구현·영상](../ot/README.md#phase-1-고속도로-4뷰)을 기준으로 합니다.

## Phase 1 카메라 배치

각도는 차체 전방 0도·왼쪽 양수입니다. 아래는 0.16.0에서 **현재 FH5 4×2·l2h1 낮은 캡·좌핸들**의 실제 도장 외판과 미러 하우징에 맞춘 값입니다. 표면 법선 방향으로 35mm 떨어진 광학 중심을 사용합니다. 트레일러 가림·선회·차종 변경 시 관측 범위는 따로 확인합니다.

| 카메라 | 위치 x/y/z (m) | yaw / pitch | HFOV | 현재 출력 |
| --- | --- | --- | --- | --- |
| C_FN 전방 협각 | 5.038 / 약 0 / 3.092 | 0 / −1.5° | 30° | 1280×720 |
| C_FW 전방 광각 | 같은 원점 | 0 / −8° | 120° | 1280×720 |
| C_RL 좌측 포드 | 4.653 / +1.484 / 2.645 | +145 / −12° | 100° | 960×544 |
| C_RR 우측 포드 | 4.653 / −1.484 / 2.645 | −145 / −12° | 100° | 960×544 |

측후방 목표 960×540은 현재 엔진에서 960×544로 나옵니다. 실제 viewport와 projection을 저장하며 임의 crop으로 보정값을 바꾸지 않습니다. 정후방 센서는 두지 않습니다. 옆면 바로 옆의 근거리까지 빈틈없이 보인다는 보장은 없으며 측방 광각은 Phase 2 후보입니다.

기존 6뷰 프리셋은 자유 배치 연구용으로 유지합니다. 학습 모델의 카메라 가정과 실제 설치가 다르면 모델 입력이나 배치를 맞춰야 합니다.

후방 카메라는 트랙터 뒤와 트레일러 뒤에서 보이는 장면이 다릅니다. 트레일러에 달면 연결부 회전 때문에 차체 기준 외부 파라미터가 시간에 따라 변합니다. 기본 보정 상수 하나로 취급하지 않습니다.

## 좌표계

작업 기본안은 다음과 같습니다.

- world: 게임 월드에서 변환한 공통 좌표.
- base_link: 구동 후축 중심 아래 명목 지면에 고정한 차량 좌표, x 전방·y 좌측·z 위쪽. SDK 바퀴 중심에서 반지름을 뺀 높이로 정하며 실제 노면 변화마다 원점을 갱신하지 않습니다.
- camera optical: x 영상 오른쪽·y 아래쪽·z 광축 전방.
- trailer: 필요할 때 별도 동적 좌표계.

SDK 1.15에서 자차 축은 X 오른쪽·Y 위·Z 뒤, 월드 축은 X 동쪽·Y 위·Z 남쪽으로 확인했습니다. 자차 벡터를 base_link로 옮기는 변환은 `(-z,-x,y)`입니다. SDK Euler 단위는 회전수이며 내부 ETS2LA quaternion은 wxyz, 셀 결합은 `(cx*512+x,y,cz*512+z)`입니다. [좌표와 시간 조사](11_idle_memory_and_telemetry.md)에 근거를 정리했습니다.

위 축 변환은 벡터에 대한 식입니다. 위치에는 후축 원점 이동도 필요합니다. `position_base_link` 프리셋을 적용하면 Python이 `truck_config`에서 구동 바퀴의 `wheel.position`·`wheel.radius`를 읽고 `p_chassis = axle_ground + (-y, z, -x)`로 바꿉니다. 여러 구동축이 있으면 `base_link_wheels`로 기준축의 바퀴 index를 명시해야 합니다.

실제 장착이 캐빈 외판에 있으면 chassis에 강체 고정하지 않습니다. `basis: cabin`은 위 neutral chassis/model 좌표를 그대로 받고, head pose를 적용하기 전의 캐빈 parent로 월드 변환합니다. 따라서 캐빈 서스펜션 운동을 따르며 운전자 시선 회전은 따라가지 않습니다. 현재 네 카메라는 모두 이 방식입니다. [형상·장착점과 실측](../ot/README.md#phase-1-고속도로-4뷰)에 기준을 기록했습니다.

설치 빌드의 SDK 차량 자세와 엔진 렌더 본체 이력은 같은 차량 기준점에서 출발하며, 렌더 쪽에 시간 보간이 적용됩니다. 이 차량 자세는 물리 actor의 원시 자세에 로컬 원점 보정을 적용한 결과이므로 그 보정을 다시 적용하지 않습니다. ETS2LA camera record의 `truck_pos_*`는 여기에 회전된 AABB 중심을 추가한 별도 위치입니다. 현재 차량에서는 로컬 위쪽으로 약 1.87 m 차이가 있어 센서 장착 변환에 직접 영향을 줍니다. [기준점 연결과 실제 보정량](12_dx11_mirror_render_path.md#sdk-차량-자세와-렌더-이력은-같은-기준점을-사용한다)을 따르며, 기준점을 차량의 기하학적 중심이나 질량 중심이라고 임의로 바꾸지 않습니다.

SDK 선형 속도는 질량중심의 속도를 차량 축으로 표현하며, SDK 위치 원점의 속도로 옮기는 보정은 없습니다. 현재 트럭에서 두 점은 약 0.78 m 떨어져 있습니다. 센서 장착점의 속도가 필요하면 같은 시각의 `v_COM + omega × r_COM_to_sensor`로 옮기며, SDK 각속도의 rotations/s를 rad/s로 변환합니다. 캐빈·트레일러의 상대 운동은 별도로 포함해야 합니다. [속도 측정점과 변환식](11_idle_memory_and_telemetry.md#sdk-선형-속도는-질량중심의-속도이며-위치-원점-보정이-없다)에 근거와 적용 범위를 정리했습니다.

T_A_B는 B 좌표를 A 좌표로 바꾸는 변환으로 정의합니다. 따라서 카메라 점을 월드로 옮길 때 T_world_base × T_base_camera를 사용합니다. 트레일러 센서는 연결 변환을 추가합니다.

## 가상 IMU

SDK 가속도를 `sensor_msgs/Imu.linear_acceleration`에 그대로 넣지 않습니다. 설치 빌드의 값은 차량 축 속도 차분의 10-step 평균이고, 가속도계가 보고하는 specific force와 다릅니다. 현재 트럭은 PhysX 자동 중력을 끄고 차량 코드에서 `(0,-9.81,0)`에 내부 질량을 곱한 힘을 별도로 누적합니다. 물리 엔진 내부 질량·힘에도 단위 스케일이 있어 그대로 kg·N으로 취급하지 않습니다.

가상 가속도계는 같은 물리 시각의 월드 속도 변화, 회전 운동, 센서 장착 위치, 중력을 함께 반영해 계산합니다. 필터는 센서 모델 계산 뒤 적용하며, 캐빈에 달린 센서는 캐빈의 상대 운동도 포함해야 합니다. [중력 경로와 IMU 변환식](11_idle_memory_and_telemetry.md#차량-중력-경로와-가상-imu에-필요한-보정)에 정리했습니다. 실제 IMU 발행과 주행 대조는 아직 구현하지 않았습니다.

## 영상 보정

각 카메라에 해상도, 투영 모델, fx·fy·cx·cy, 왜곡 계수 또는 실제 투영행렬, 장착 변환을 연결합니다. 좌우 반전·crop·resize·letterbox가 있으면 결과 영상 기준의 보정값도 함께 갱신합니다.

운전자의 고개 움직임, FOV 설정, 좌석 이동이 센서 투영을 바꾸는지 확인합니다. 일반 미러의 곡면 표시를 정상적인 pinhole 영상이라고 취급하지 않습니다.

어안은 후속 확장입니다. pinhole 한 장을 왜곡해도 원본 시야 밖의 장면은 생기지 않습니다. 180도 근처 또는 그 이상의 시야는 엔진의 투영 지원이나 여러 방향 렌더 후 재투영이 필요할 수 있습니다. cubemap을 쓰면 출력 영상 한 개보다 많은 렌더 패스가 발생합니다.

## depth와 의사 LiDAR

GPU depth buffer는 보통 미터 거리 그 자체가 아닙니다. 사용 중인 projection, clip 범위, reversed Z, viewport, 샘플링과 후처리 여부를 확인합니다.

현재 설치 빌드의 DX11 기본 투영 경로는 **NDC에서** near=1, far=0인 reversed Z입니다. 실제 미러 surface 작업의 viewport 깊이 범위는 약 0.01–0.9였으므로 텍스처 값을 그대로 NDC 깊이로 쓰면 안 됩니다. 메인 실내는 0.9–1.0이며 실외와 투영의 near/far도 다릅니다. 아래 `P`에는 scene의 원본 CPU 행렬이 아니라 backend 보정까지 적용한 행렬을 사용해야 합니다. 한편 기본 diffuse의 `attributes_0.w`에는 이미 선형 카메라 Z가 저장되므로 같은 pass의 ray 상수로 복원하는 별도 경로를 우선 조사합니다. [분석 근거와 적용 범위](12_dx11_mirror_render_path.md)를 참고합니다. 아직 GPU 픽셀과 실거리를 대조한 결과는 아닙니다.

열벡터와 표준 D3D NDC 깊이를 가정한 역투영의 기본 형태는 다음과 같습니다. 실제 엔진이 다른 규약 또는 별도 깊이 인코딩을 사용하면 변환도 바뀝니다.

~~~text
x_ndc = 2 * (u + 0.5) / width - 1
y_ndc = 1 - 2 * (v + 0.5) / height
depth_ndc = (depth_buffer - MinDepth) / (MaxDepth - MinDepth)
q = inverse(P) * [x_ndc, y_ndc, depth_ndc, 1]
p_camera = q.xyz / q.w
~~~

뷰포트가 텍스처 일부이면 u·v와 width·height는 해당 영역 기준으로 해석합니다. 행벡터 엔진에서는 행렬 표현도 맞춥니다. depth를 선형화해 광축 방향 거리 Z로 내보낸 뒤에는 pinhole에서 다음 식을 사용할 수 있습니다.

~~~text
X = (u - cx) * Z / fx
Y = (v - cy) * Z / fy
point_base = T_base_camera * [X, Y, Z, 1]
range = sqrt(X*X + Y*Y + Z*Z)
~~~

광축 거리 Z와 카메라 원점에서의 유클리드 거리 range는 다릅니다. 하늘·clear depth·유효하지 않은 픽셀은 무한한 점으로 넣지 않고 결측으로 처리합니다.

여러 depth 영상을 역투영해 합치면 의사 LiDAR를 만들 수 있습니다. 실제 LiDAR의 스캔 시간차·강도·다중반사·재질 반응까지 재현하는 것은 아닙니다. 게임 raycast API를 사용하는 방식도 별도이며, ETS2에서 필요한 동적 장면 raycast 접근은 아직 확인되지 않았습니다.

색상과 depth는 같은 카메라·같은 장면 상태·같은 crop에서 가져옵니다. 렌더 타깃이 다른 뷰에 재사용되기 전에 보존해야 합니다. 원래 미러에서 물체를 제외하는 규칙은 의사 LiDAR에도 그대로 누락을 만들 수 있습니다.

## 시간 정합

같은 센서 묶음은 동일한 렌더용 장면 상태를 사용합니다. GPU 작업 완료 시각과 실제 관측 시각은 별도로 다룹니다. 서로 다른 패스가 장면 갱신을 사이에 두고 실행되지 않는지 확인해야 합니다.

현재 설치 빌드에서는 SDK 전달이 물리 사후 처리 뒤, 렌더용 자세 보간·카메라·미러 준비 전에 있습니다. 따라서 SDK `frame_end`를 GPU 프레임 완료로 사용하지 않습니다. 또한 SDK 선형 가속도는 local velocity 차분의 10-step 이동평균이며 현재 step 길이에서 약 166.66 ms 구간을 반영합니다. 채널 이름만으로 순간 IMU 값이나 영상 시각의 정답으로 취급하지 않고, 원래의 simulation 시각과 필터 특성을 함께 보존합니다. [채널의 원본·갱신 시점과 필터 분석](11_idle_memory_and_telemetry.md#속도가속도는-사후-물리-갱신에서-계산되며-가속도에는-10-step-필터가-있다)에 실제 코드와 읽기 근거가 있습니다.

차량 내부에는 바깥 step당 세 번의 힘·자세 계산이 있으며, 이는 SDK의 발행 빈도와 별개입니다. scalar speed·가속도 캐시를 계산한 뒤 backend 자세·속도를 다시 변경하는 순서도 확인했습니다. 같은 callback 묶음만으로 모든 채널의 적분 단계가 같다고 보장하지 않으며, IMU용 자세·속도는 같은 단계에서 수집해야 합니다. [내부 계산과 PhysX 결과 연결](11_idle_memory_and_telemetry.md#힘-누적값의-소비와-physx-결과의-반영)에 현재 설정에서의 분기와 미확인 범위를 정리했습니다.

TAA jitter나 temporal history가 있으면 카메라마다 이력을 분리하거나 초기 센서 패스에서 해당 효과를 제어해야 합니다. 처음에는 motion blur 등 기하 검증을 방해하는 효과를 줄이는 기본안을 사용합니다.

동적 차량이 이동하는 장면과 사용자가 고개를 돌리는 장면에서 정합을 확인합니다. 정상 속도에서 움직이는 한 차량이 카메라 사이에 시간차 때문에 다른 위치로 나타나는지 볼 수 있습니다.

## 3060 Ti에서의 비용 계산

아래는 직접 계산한 비압축 데이터 크기입니다. 게임 실행 성능 측정값이 아닙니다. MB와 GB는 10진 단위입니다.

| 구성 | 센서 픽셀 수 | RGBA8와 32비트 depth 한 묶음 | 20묶음/초의 원시 데이터량 |
| --- | ---: | ---: | ---: |
| 4 × 1280 × 720 | 3,686,400 | 29.49 MB | 589.82 MB/s |
| 6 × 1280 × 720 | 5,529,600 | 44.24 MB | 884.74 MB/s |

6뷰의 RGBA8+depth를 이 형식 그대로 저장하면 약 53.08 GB/분입니다. RGB8만 저장해도 6뷰·720p·20Hz에서 약 19.91 GB/분입니다. 압축률은 장면과 코덱에 따라 달라지므로 미리 특정 비율을 보장하지 않습니다.

FHD 운전석과 4뷰·6뷰를 합친 출력 픽셀은 각각 약 5.76 MP·7.60 MP입니다. 4K의 8.29 MP보다 작아도 같은 렌더 비용이라는 뜻은 아닙니다. 각 뷰의 물체 선별, draw call, 조명, depth, 이력 버퍼와 원래 미러가 추가됩니다.

작업용 성능 후보는 다음과 같습니다. 달성 보장이 아닌 측정 순서입니다.

1. 기존 피드와 독립 센서 1~2개를 낮은 해상도로 확인.
2. 4뷰 720p에서 10~20Hz의 센서 묶음을 비교.
3. 여유가 있으면 6뷰로 확대.
4. 렌더링과 별개로 모델 입력 해상도를 축소하고 보정값 갱신.
5. 게임 단독 → 센서 추가 → 추론 추가 → 기록 추가 순으로 병목 측정.

줄일 수 있는 것은 뷰 수, 묶음 주기, 렌더 품질, 기록량, 모델 크기입니다. 시간 감속이나 카메라별 서로 다른 시점 촬영으로 대체하지 않습니다.

## 기록과 저장

MCAP에는 시각화·상태·보정·명령을 함께 남기는 방향을 기본으로 합니다. 대용량 영상의 코덱과 MCAP 내 포함 여부는 기록 비용을 보고 결정합니다. 원본 이미지가 JPEG로만 남으면 depth·정밀 영상 학습에 필요한 정보를 잃을 수 있으므로 채널별 저장 목적을 구분합니다. [MCAP 안내](https://mcap.dev/guides/getting-started)

자료는 실험별로 차량, 게임 빌드, 센서 구성, 경로와 기상, 적용 명령을 연결합니다. 미래 시점 상태를 현재 관측에 섞지 않습니다. 대용량 기록 경로와 여유 공간을 먼저 정하고 바탕화면 문서 폴더에는 장기 데이터셋을 쌓지 않습니다.
