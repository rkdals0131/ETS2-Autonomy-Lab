# 시스템 설계

Windows 게임 프로세스 안에는 카메라·렌더링·상태·입력을 연결하는 작은 플러그인을 두고, 모델과 기록·시각화는 외부 프로세스에서 실행하는 구성을 기본안으로 합니다. 이 구조는 제안이며 아직 구현된 API가 아닙니다.

## 데이터 흐름

~~~text
ETS2 게임 프로세스
  장면 갱신과 렌더용 보간 자세
    ├─ 운전석 화면과 원래 미러 → FHD 모니터
    └─ 센서 뷰 4~6개 → RGB / depth / 카메라 파라미터
  텔레메트리와 게임 내부 상태 ─────────────┐
                                        ↓
Windows 외부 프로세스
  동기화된 센서 묶음 → 전처리 → BEV / 정책 → 주행 명령
          ├─ 기록 → MCAP / 선택한 영상 저장 형식
          └─ Foxglove → 카메라 / 점군 / 경로 / 상태
                                        ↓
게임 플러그인의 입력 적용 → 조향 / 가속 / 제동
~~~

정상 속도의 장면 상태 하나에 대해 센서 렌더 패스를 제출합니다. GPU 패스가 차례대로 수행되는 것과 서로 다른 게임 프레임에서 카메라를 전환하는 것은 다른 동작입니다. 센서 주기를 낮출 때도 4~6개를 한 묶음으로 갱신합니다.

## 게임 프로세스의 책임

1. 공식 SDK로 얻을 수 있는 기본 상태와 이벤트를 먼저 사용합니다.
2. 내부 카메라 관리자와 보조 뷰의 생성·갱신·렌더 제출을 연결합니다.
3. 각 카메라의 영상, depth, 실제 투영행렬, 해당 렌더 상태의 자세를 확보합니다.
4. 출력 완료를 표시한 뒤 외부 프로세스에 묶음을 전달합니다.
5. 제어 명령을 적용하거나 해제합니다. 추론을 기다리며 렌더 스레드를 막지 않습니다.
6. 해상도 변경·세션 종료 시 소유한 리소스와 후킹을 해제합니다.

센서 생성은 엔진의 적절한 호출 지점에서 해야 합니다. 별도 스레드에서 엔진 장면 함수를 임의로 호출하는 방식을 가정하지 않습니다. D3D11의 device와 device context는 스레드 안전성도 다릅니다. [Microsoft 설명](https://learn.microsoft.com/en-us/windows/win32/direct3d11/overviews-direct3d-11-render-multi-thread-intro)

## 외부 프로세스의 책임

- 카메라 좌표와 시간을 정규화하고 필요한 전처리를 수행합니다.
- 센서 관측만 쓰는 정책과 게임 내부 정보를 쓰는 비교 정책을 구분합니다.
- 모델 추론·제어·기록·시각화를 연결합니다.
- 지연된 묶음을 무한히 쌓지 않습니다. 온라인 제어는 최신의 완성된 묶음을 사용합니다.
- 기록기가 밀리면 기록 누락을 드러내고 제어 경로를 유지합니다.

기록을 줄이는 것은 가능하지만, 카메라별 과거 영상을 섞어 최신 묶음처럼 표시하면 안 됩니다.

## 프로세스 간 전달

| 데이터 | 첫 구현 | 성능 확장 |
| --- | --- | --- |
| 상태와 카메라 메타데이터 | 작은 공유 메모리 또는 로컬 IPC | 실제 소비자 요구에 맞춰 유지 |
| 제어 명령 | 명령과 생성 시각·소유권을 함께 전달 | 게임 버전별 입력 어댑터 |
| 영상 | 저해상도·낮은 주기의 비동기 readback | 지원되는 공유 GPU 텍스처 |
| depth | 정의를 확인한 선형 depth 또는 원본과 투영 정보 | GPU에서 R32_FLOAT 등 출력용 형식으로 변환 |
| 시각화 | 선택·축소한 영상과 점군 | 필요한 채널만 구독·전송 |

CPU readback은 첫 영상 확인에 쓸 수 있지만, 6뷰 고해상도의 최종 전달 방식으로 확정하지 않습니다. 공유 GPU 리소스도 자동으로 PyTorch Tensor가 되지는 않습니다. 포맷, 어댑터, 프로세스 간 handle, 소유권과 완료 시점을 맞춰야 합니다.

D3D11에는 공유 리소스와 keyed mutex가 있고, CUDA에는 D3D11 리소스 등록·매핑 기능이 있습니다. 지원하지 않는 depth 포맷·생성 플래그는 별도 출력 텍스처로 변환해야 합니다. 리소스 등록은 매 프레임 반복할 작업이 아닙니다. [Microsoft 공유 리소스](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/ne-d3d11-d3d11_resource_misc_flag), [NVIDIA D3D11 interop](https://docs.nvidia.com/cuda/cuda-runtime-api/cuda_runtime_api/group__CUDART__D3D11.html)

CPU 메타데이터 공개만으로 GPU 쓰기가 완료됐다고 판단하지 않습니다. 실제 GPU 완료·소비자 사용 완료와 버퍼 재사용을 연결합니다. 링 버퍼 슬롯을 처리 중인 소비자에게서 빼앗아 덮어쓰는 구조를 피합니다. 버퍼 수는 프로파일링 후 정합니다.

## 제안하는 데이터 계약

| 단위 | 필요한 정보 |
| --- | --- |
| 세션 | 게임 빌드, 플러그인 revision, 렌더 API, 차량·센서 구성 |
| 센서 묶음 | 묶음 식별자, 렌더 상태 시각, 단조 증가 시계 시각, ego pose |
| 카메라 | camera_id, frame_id, 해상도, 영상 형식, 투영 모델, 내·외부 파라미터 |
| 프레임 | 해당 묶음의 이미지·depth, 실제 렌더 투영, 완료된 출력 위치 |
| 제어 명령 | 조향·가속·제동, 생성 시각, 활성화 상태 |
| 상태 | 실제 입력 적용 여부, 일시정지 여부, 최근 관측과 명령의 지연 |

이는 외부 ABI를 지금 고정한 것이 아닙니다. 타임스탬프는 게임 시간이 배율을 갖는지, 렌더·물리 시계가 다른지 확인한 뒤 이름과 단위를 명확히 정합니다. UTC는 파일 식별 등에 사용할 수 있지만 지연 계산은 벽시계 조정의 영향을 받지 않는 시계를 기본으로 합니다.

## 수동 운전과 활성화

처음 시작하면 수동 운전입니다. 단축키로 자율주행을 켜고 끄며, 실제 적용 상태를 표시합니다. 해제·수동 개입·제어 프로세스 종료·기한 지난 명령에서는 입력 override를 해제하는 방향을 기본안으로 합니다.

조향 출력이 핸들 입력인지 바퀴각인지, 값의 단위와 범위가 무엇인지는 입력 경로별로 확인합니다. 플러그인 종료 시 마지막 가속값이 남는지도 실제 게임에서 확인할 항목입니다. 같은 축을 ETS2LA와 새 컨트롤러가 동시에 쓰지 않도록 입력 소유자는 하나로 둡니다.

기본 UI는 활성화, 적용 중인 조향·가속, 현재 속도, 목표 속도, 관측 지연을 보여 줍니다. 내부 주소나 후킹 상세는 운전용 UI에 노출하지 않습니다.

## Foxglove와 운전석 UI

[Foxglove](https://foxglove.dev/download)는 Windows에서 사용할 수 있고, [SDK](https://docs.foxglove.dev/docs/sdk)는 C++·Python·Rust에서 실시간 전송과 MCAP 기록을 지원합니다. 초기 통합에 ROS 2를 필수로 두지 않습니다. 로컬 연결은 127.0.0.1에 한정하는 구성을 기본안으로 합니다.

권장 화면은 전방 영상, 필요할 때만 나머지 카메라, 차량 좌표의 3D 점군·경로, 속도·입력·지연 그래프입니다. FHD 화면 하나에서 운전할 때는 작은 상태 UI를 유지하고 상세 진단 화면은 전환해서 봅니다.

[PrismTextureStreamer](https://github.com/Baldywaldy09/PrismTextureStreamer)의 외부 화면 주입을 응용하면 BEV·계획 경로를 트럭 내비게이션에 표시할 수 있습니다. 기존 프로젝트의 기능을 활용한 제안이며 아직 통합 검증되지 않았습니다.
