## 1. 요약

- **훅 경계**: `0x227140`의 반복 전체 대체도, `0x226960` 단위 병렬화도 아닙니다. `0x226960`(타입 1 패스 실행)을 인라인 훅으로 가로채 **실행을 미루고**(기록 없이 반환), 패스 반복이 끝난 직후 `0x227B1F`(미드훅)에서 **합류**해 미룬 패스들을 엔진 `parallel_loop_task_t`로 병렬 기록합니다. 본문은 원본 `0x226960`을 트램펄린으로 그대로 부릅니다. 엔진 코드를 다시 쓰지 않고 호출 순서만 바꿉니다(§3.1).
- **왜 가능한가**: 패스마다 명령 저장소가 따로 있고(`pass+0x2E8`), 컴파일 순서는 `0x227140`이 모은 저장소 배열이 정하므로 기록 순서는 결과에 영향이 없습니다(✔ §2.5). 저장소 안에서 미룬 구간 앞뒤에 엔진이 쓰는 명령은 DX11 컴파일러가 건너뛰는 op 0xD뿐이고, 순서 보존이 필요하면 dword 복사로 되돌릴 수 있습니다(§3.2).
- **장애물의 실체**(✔ §2.6): 장치 버퍼 풀만이 아닙니다. 가장 뜨거운 공유 쓰기는 **프레임 선형 할당기 `0x1E05B0`**(저장소 청크·바인딩 패킷·draw 배치가 모두 여기서 받음, 비원자 bump)이고, 그 다음이 uniform 링 커서(`0x2E5040`, 메인 스레드 2.93 ms/프레임), 풀 유지보수 `device->vtable[0x120]`(= `0x2E8FE0`, 0.375 ms), 버퍼 레코드 획득·해제(`0x2E8090`·`0x2E8440`), 지연 생성 캐시(`0x2B94B0`·`0x2BEA70`·`0x2AE640`)입니다. 통계 카운터는 `lock add`라 문제가 아닙니다.
- **이득 상한**(✔ 외부 폴링, §2.8): 패스 기록 구간은 평균 4.27 ms(브리지 끔·다른 장면) / 5.46 ms(Scania S 정차, 캡처 멈춤) / 5.68 ms(센서 켬, 카메라를 그리는 프레임 6.79 ms)이고, 그중 메인 `scene defattr` 패스가 1.75–1.89 ms(33–41%)입니다. 패스 단위 병렬의 임계 경로는 메인 패스이므로 이상 상한은 **메인 밖 시간 2.5 / 3.6 / 3.8 ms**(카메라 프레임 4.9 ms)입니다. 1단계(풀 함수 통째 락)는 `0x2E5040`·`[0x120]`의 락 직렬 몫(기록 구간의 54–62%, △ 표본 비율)이 바닥이라 상한 1.6 / 2.5 / 2.2 ms이고, 경합 비용을 빼면 기대 −1…−1.5 ms입니다(△). 2단계(스레드별 uniform 세그먼트)는 메인 패스 + 합류 비용만 남아 −2.3 / −3.4 / −3.6 ms(카메라 프레임 −4.7 ms)가 상한입니다(△). 컴파일 `0x2B1A30` 약 1 ms와 업로드 flush `0x2B62B0` 0.53–0.98 ms(장면 의존)는 메인에 남습니다. 메인 패스가 절반 미만이므로 패스 내부 분할(B안)은 1차 필수가 아닙니다. 센서 켬이 기록에 더하는 몫은 프레임 평균 0.2–0.5 ms뿐이고, 절대 이득이 커지는 것은 카메라를 그리는 프레임(30%, +1.3 ms)에 한정됩니다. **운영 장면인 고속도로**(63–68 km/h, ✔ §2.9)에서는 기록 구간 2.44 / 2.98 ms이고 가장 큰 패스가 약 20%(✔ M3a 실측 0.47 ms, dword 비중 18 / 15%)뿐이라 임계 경로는 메인 패스가 아니라 분배(구간 ÷ 실행자 4 ≈ 0.6–0.75 ms)입니다. M3a가 잰 타입 1 기록 합은 2.75 ms/프레임(64 km/h, 계측 포함)이고, 이상 상한 ≈ 1.9 ms, 1단계 0.5 ms(상한 1.0), 2단계 1.8 ms(△ §2.9). 프레임 갱신 `0x426360`(5.6 ms, 메인의 52%)이 더 크지만 1.2 ms 이하 항목의 긴 꼬리라 그중 하나를 나눠 얻는 상한은 0.8 ms 이하입니다(§2.9).
- **검증**: 단계를 나눠 각 단계가 앞 단계의 가정을 증명합니다. (a) 미루기만 하고 합류점에서 **직렬** 재실행(✔ M3a, core 0.35.0, 2026-10-15), (b) 엔진 worker에서 실행하되 티켓 순서로 한 번에 한 패스(스레드 전환만 검증), 그다음 순서 자유 + 한 락, (c) 락 축소. **같은 프레임을 두 번 기록하는 shadow 비교는 불가능합니다**(✔ 2026-10-15: 두 번째 기록에서 blit 패스 콜백 `0x151BF80`이 엔진 assert로 게임을 종료. 패스 기록은 패스 객체 상태를 소비하므로 멱등이 아님, §2.11). 오라클은 교대 프레임 비교(§4.2: 직렬·병렬 프레임을 번갈아 기록하고 패스 키별 dword·draw·토큰 히스토그램을 이웃 프레임과 비교, 직렬끼리의 차이가 기준선), 기존 센서 영상·라이다 기준(§4.3), 불변량(키 집합·패스 수·draw 수·GPU busy), 엔진 assert·alien 경고 0입니다.
- **중단 기준**: 판정 세트는 운영 장면인 고속도로 ABAB(§6 세트 0)이고, 정차 세트는 상한 확인용입니다. 1단계(통째 락)는 고속도로 상한이 0.9 ms라 이득 문턱 대신 진단(락 보유 합이 예측과 맞고, 락 밖 몫이 병렬로 줄었는가)으로 2단계 진입을 정합니다. 2단계는 고속도로 CPU busy p50 −1 ms(정차 −2 ms) 이상이어야 운영 후보이고, 아니면 중단합니다(§7).

## 2. 코드에서 확인한 구조

### 2.1 렌더 그래프 실행 `0x227140` (`rendergraph_builder_t::execute`, ✔ 디컴파일)

호출자는 `0x1DBCE0`(present 프레임) 하나이고, 인자는 (builder `0x304FC50`, frame = builder 안의 0x2A8 간격 기록 중 `builder+0x7F8`번째)입니다. 순서는 다음과 같습니다.

1. `frame+0x268`이 서 있으면 `DAT_143681BC0->[0x98](0,0)`(동기 프레임 표시). 끝에서 `[0xA8]`과 함께 `device+0x858`(렌더 스레드 미처리 수)이 0이 될 때까지 조건변수(`device+0x868`, 락 `device+0x860`) 대기.
2. 스택의 헤더 저장소에 op 0xF(frame id `frame+0x210`)를 쓰고 저장소 배열(스택, 1024개)에 넣음. 경계 플래그 배열(스택, 1024개)에 1.
3. 처음 한 번 GPU 타이머 stat id 두 개를 조회해 `builder+0x7FC`·`+0x7FE`에 둠. 매 프레임 `FUN_14022C3C0(frame+0x280)`으로 패스별 프로파일러 범위 배열을 리셋하고, id가 −1이 아니면 op 0x18.
4. `device->[0x2D0]`(`0x2EDCE0`): 보류 삭제 목록 처리(SRW `device+0x878`).
5. **패스 반복**: `frame+0x1A0`의 패스 인덱스 배열(`0x2263A0`이 present 패스에서 역추적해 만든 순서)마다 `pass = frames[current].passes[idx]`(`manager+0xF0`, `pass_commands.cpp:PassCommands::describe`가 같은 배열로 패스를 확인).
   - 앞 전이 blob(`pass+0x12D8`, 개수 `+0x12E0`)이 있으면 프레임 할당기로 복사해 **패스 저장소 `pass+0x2E8`**에 op 0xD.
   - stat id가 있으면 op 0x19·0x1B, 프로파일러 범위 객체(`frame+0x280` 배열, 0x140바이트) 확보.
   - 타입(`pass+0x8`) 1이면 `0x226960(builder, 인자, pass, 마커 또는 NULL)`. 2·3·4·5면 `0x219BB0`으로 컨텍스트(228바이트)를 만들어 `(pass+0x1C68)->vtable[1](ctx, pass, pass+0x1C70)`. 그 외는 assert. 실측(✔ `pass_names.py`, 브리지 끔)에서 프레임당 타입 1이 100–113개, 타입 3(present) 1개, 타입 5(Generate mips) 3개였고 타입 2·4는 없었습니다.
   - op 0x1B·0x1A, 뒤 전이 blob(`+0x15F8`/`+0x1600`) op 0xD.
   - 저장소 포인터를 배열에 넣고 **경계 플래그 = (`pass+0x200` == 0)**.
6. 꼬리 저장소에 op 0x1C(마커 집계, id≠−1일 때)와 op 0x10(프레임 끝).
7. `DAT_143681868->[0x50]`.
8. **업로드 flush**: `device+0xF1470` 배열(0x28 간격 {id, GPU 오프셋, CPU 그림자, 사용량 +0x18, 완료 +0x20})의 미완료 구간을 `[0x160]`(`0x2B62B0`, `UpdateSubresource`, 컨텍스트 SRW `device+0x3999A00`)로 올림. 메인 스레드 0.98 ms/프레임.
9. `[0x120]`(`0x2E8FE0`), `[0x2D8]`(`0xF2DA0`, 빈 함수).
10. **묶음 컴파일**: 저장소를 최소 16개씩, 경계 플래그가 1인 저장소 뒤에서만 끊어 `[0x108]`(`0x2B1A30`, `cmd_buffer_compile`)에 넘기고 id를 모음. `[0xD0](0x10)` 능력(DX11에서 1)이면 `[0x118]`(`0x2F03B0`: 스핀락 `device+0x848`, 링 `device+0x40`, `lock add device+0x858`, 세마포어 `device+0x850`)로 **렌더 스레드 큐에 넣음**. 렌더 스레드 루프 `0x2F0460`이 꺼내 `[0x110]`(`0x2B3A80`)으로 실행합니다. 메인 스레드가 `[0x110]`을 직접 부르는 경우는 렌더 스레드 능력이 없을 때뿐입니다.

### 2.2 패스 실행 `0x226960` (✔ 디컴파일, 호출자 `0x227140` 하나)

인자 (param_1 미사용, param_2 값, pass, 마커 포인터). 순서: `pass+0x204 == −1 || == pass+0x1F8`이면 op 3(타깃 `pass+0x2B2`·`+0x2B4`) → 마커가 있으면 op 0x19 → cvar 두 개에 따라 op 0x11(`[0xD0](0x14)` 조건)·op 0x14 → 컨텍스트 `0x219BB0` 구성(`+0xE4` 타깃 설명 `0x21CEC0(pass[0], 첫 출력)+0x1EC`, `+0xF0` 저장소 = `pass+0x2E8`, `+0xF8` = `pass+0x2B0`, `+0x100` = `pass+0x2B8`, `+0x108` = `pass+0x1A00`), `[0x220]`(`0xF5350`, 0 반환) → `0x27AAF0(ctx, 0)` → **`(pass+0x1C68)->vtable[1](ctx, pass, pass+0x1C70)`** → 마커가 있으면 op 0x1A → `pass+0x200 == 0`이면 op 4(패스 끝) → `[0x120]`.

M0 표본에서 이 가상 호출 아래에 보인 함수는 `0x160CF10`(장면, 1.00 ms) · `0x151BB90`(0.35) · `0x160EB80`(0.22) · `0x166D2F0`(0.14) · `0x1465260`(0.09)입니다. 장면 콜백의 실제 진입은 `0x1473E60`(✔ 디컴파일: 콜리 `0x160C990`·`0x160CF10`·`0x160D010`, 저장소 `0x28CE60`, 투영 변환 `0x27AC30`; 직접 호출 `0x1476140`, `.rdata` 표 `0x2641F24`·`0x2641F8C`에서 참조)인데, snowymoon이 그 입구에 14바이트 절대 점프를 심어 스택에서는 익명 중계 코드로만 보입니다(§2.10). 장면 경로는 `0x1473E60` → `0x160CF10` → `0x160D010`(그룹 반복, 서브뷰마다 뷰포트·행렬을 컨텍스트에 쓰고 op 0xA) → `0x160D580` → draw 배치 `0x2E5FF0`입니다.

### 2.3 명령 저장소와 프레임 할당기 (✔)

- `r_cmd_storage_t`(`pass+0x2E8`, vtable `0x21FD700`): `+0x8` 청크 배열, `+0x10` 개수, `+0x18` 용량, 인라인 청크 기록 32개(0x18바이트 {data, 사용 dword, 용량 0x10000}), `+0x320` 현재 청크. `0x28CE60(storage, n)`은 현재 청크에 `사용+n < 0x10000`이면 bump, 아니면 새 기록을 만들고 **프레임 할당기 `0x1E05B0(0x40000, 0x10)`**으로 256 KB를 받습니다. 명령 하나가 청크 경계를 넘지 않습니다. 컴파일러는 청크를 순서대로 읽습니다.
- 프레임 할당기 `0x1E05B0(size, align)`: 현재 청크 `DAT_143681898`의 `+0x20` 커서를 **원자 연산 없이** 올립니다(정렬한 커서에 `size <= 0x200000 − 커서`면 bump, 결과 = `chunk+0x18`의 데이터 포인터 + 커서). 청크 태그 `+0x10`이 `DAT_14304D828 | 0xFAFAFAFA00000000`(프레임 번호)과 다르거나 모자라면 `0x166B30(태그)`로 새 2 MB 청크를 받아 전역을 바꾸고 커서를 16 정렬로 다시 시작하며, 그래도 안 들어가면 0을 돌려줍니다. `0x166B30`·`0x166C50`은 SRW `DAT_14304B228` 아래에서 프리 리스트(`PTR_DAT_1427334C8`)·사용 목록(`PTR_PTR_142733500`)을 다루고, `0x166C50(태그)`는 **같은 태그의 청크를 모두 반납**합니다. 호출자 29곳: `0x28CE60`, `0x2E5FF0`(배치마다 `count*0x30`), `0x2B6B20`(아이템의 바인딩 단계마다), `0x2E6AF0`, `0x2E8090`, `0x227140`, 컴파일 쪽(`0x2BAD00`·`0x2BB840`·`0x2BBF20`) 등.
- **프레임 태그 전진 `0x1E0710`**(✔ 디컴파일): `lock xadd`로 `DAT_14304D828`을 1 올리고, 콜백 목록(`PTR_DAT_142738DC0`의 세 칸 중 이전 태그 % 3번, 항목마다 `vtable[1]`)을 실행한 뒤 `0x166C50((이전 태그 − 3) | 0xFAFAFAFA00000000)`을 부릅니다. 즉 프레임 N의 청크는 태그가 N+3에서 N+4로 바뀔 때, **3프레임 뒤에** 반납됩니다. 호출자는 둘입니다. 메인 루프 `0x1CBEE0`이 프레임당 1회(디컴파일 순서상 렌더 제출 `0x1DBCE0` 뒤, `0x227140` 밖이므로 합류 구간 동안 태그는 고정), 그리고 장치 drain `0x2DE240`(호출자 `0x293FD0`·`0x2AD780`·`0x2C3850`·`0x300C90`; 종료 플래그 `DAT_143050959`·`device+0x8D8`를 세우고 렌더 스레드 종료를 기다린 뒤 풀·세그먼트·보류 목록을 전부 비움)이 **3회 연속** 불러 떠 있는 세 프레임의 청크를 모두 반납합니다. 그래서 태그는 프레임 없이 3 뛸 수 있습니다.
- draw 배치 `0x2E5FF0`의 스크래치(아이템당 0x2C0바이트 번들, 2978개 단위)는 `0x166B30(DAT_143673554 | 0x5C5C5C5C00000000)`로 받아 `0x166C50`으로 돌려주므로 이미 스레드 안전합니다. 일련번호 `DAT_143673554 += 1`은 비원자지만 `0x166B30`은 이 값을 소유자 태그로만 저장합니다(`chunk+0x10`). 중복돼도 할당 결과는 바뀌지 않습니다.

### 2.5 DX11 컴파일러 `0x2B1A30`의 op 처리 (✔)

- 저장소마다 상태 바이트(`local_1fb`)를 `device+0x3623C83`로 초기화하고, **타깃 상태(`local_1b4`·`local_218`)는 한 번의 컴파일 호출 안에서 저장소 사이로 이어집니다.** 그래서 op 4(패스 끝)를 쓰지 않는 `pass+0x200 != 0` 패스는 다음 저장소와 같은 명령 버퍼에 있어야 하고, `0x227140`의 경계 플래그가 그 분할을 막습니다. 27의 "묶음 분할 이유 미확인"은 이것입니다. 최소 16개 묶음은 명령 버퍼 수를 줄이는 휴리스틱으로 보입니다(△).
- op 0xD(전이 blob)는 **3 dword를 건너뛰는 no-op**입니다. op 0xF·0x11·0x12는 1 dword 건너뜀. op 1(draw) 10 dword → `0x2BAB30`, op 3 → `0x2BD980`, op 4 → `0x2BDEA0`, op 0xA 상태 바이트, op 0x10 → `lock mov device+0x39999FA = 1`.
- **op 0x18–0x1C(GPU 마커)에는 case가 없고 default는 assert**("Unknown command or corrupted token stream")입니다. 게임이 매 프레임 그 assert에 걸리지 않으므로 정상 플레이에서 stat id는 −1이고 마커는 기록되지 않습니다(✔ 귀류, 그리고 실측 `builder+0x7FC/+0x7FE` = (−1, −1)). 따라서 패스 저장소에서 `0x226960`의 앞·뒤에 `0x227140`이 쓰는 명령은 op 0xD뿐입니다.
- 기록 쪽 상태 캐시는 컨텍스트(패스마다 스택에 새로 생성) 안에만 있습니다(`0x160D010`이 `ctx+0x140` 바이트와 비교해 op 0xA를 냄). 장치에 "현재 상태"를 두는 코드는 읽은 범위에서 없습니다(△ 전체 클로저는 §3.5에서 확인).

### 2.11 패스 기록은 멱등이 아니다 (✔ 2026-10-15 shadow 시험, 디컴파일)

M3a의 shadow 모드(같은 프레임을 사설 저장소에 먼저 기록하고 실제 저장소에 다시 기록)는 켠 지 5초 안에 엔진 assert `array_t<rg_blit_pair_t>::operator[]: Index outside array boundaries: 0 >= 0`로 게임을 종료시켰습니다. 경로는 이렇습니다.

- blit 패스 콜백 `0x151BF80`(타입 1): `0x226C40(pass)` → `pass+0xDC0`(blit 쌍 개수)이 0이면 assert → `0x1519670(ctx, pass+0xDB8)` → `0x226D80(pass, ctx)`.
- `0x226C40`: 패스의 blit 쌍 배열(`pass+0xDB8`, 개수 `+0xDC0`, 0x40바이트 항목)을 돌며 `0x21CEC0(builder, id)`(현재 프레임 기록의 `rendergraph_image_t` 배열 조회, 0x7F0 간격, 읽기만)와 장치 `[0x1E8]` = `0x2B58A0`(`dx11_image_object_t` 배열 `device+0x363FE60` 조회, 0xA8 간격, 읽기만)로 두 이미지를 찾아 쌍의 필드를 채웁니다. 쓰기는 패스 자신의 배열 안뿐입니다.
- `0x226D80`: 쌍마다 이미지의 `rendergraph_access_t` 표(`image+0x750`, 개수 `+0x758`, 쌍이 가진 인덱스로 읽기)와 포맷(`+0x1E4`·`+0x1F4`)을 읽고, 컨텍스트 `+0xE4/+0xE8`(타깃 크기)을 쓰고, `0x219C50(ctx, rect)`(뷰포트·행렬을 컨텍스트 `+0x110…+0x138`에 씀)를 부른 뒤 `0x28CE60(storage, 0x10)`으로 16 dword의 op 7(blit)을 기록합니다. 마지막에 **`pass+0xDC0 = 0`**으로 배열을 비웁니다. 두 번째 기록은 여기서 죽습니다.
- 같은 두 함수를 부르는 콜백이 9개(`0x22DE30`·`0x329300`·`0x3294A0`·`0x3295A0`·`0x4213D0`·`0x494620`·`0x4DE700`·`0x1475F90`·`0x151BF80`)라 blit 계열 패스는 모두 자기 쌍 배열을 소비합니다. 다른 콜백도 비슷한 소비가 있다고 보는 것이 안전합니다.

결론 셋입니다. (1) 한 프레임에 한 패스를 두 번 기록할 수 없으므로 같은 프레임 비교는 없습니다(§4.2가 교대 프레임 비교로 바뀜). (2) 패스 콜백이 **자기 패스 객체**를 바꾸는 것은 패스 단위 병렬에 문제가 없습니다. 읽은 범위에서 이 경로가 쓰는 곳은 패스 객체·컨텍스트·패스 저장소뿐이고 공유 표(`rendergraph_image_t`, `dx11_image_object_t`, `rendergraph_access_t`)는 읽기만 합니다(✔ `0x226C40`·`0x226D80`·`0x2B58A0`·`0x21CEC0` 양수 id 경로; △ `0x21CEC0`의 음수 id 경로 `0x21D250`·`0x21D9B0`, `0x219C50` 꼬리, `0x1519670`는 §3.5 7). (3) 같은 패스 객체를 한 프레임에 두 번 기록하거나 두 스레드가 같은 패스를 만지는 경로가 없어야 합니다. 큐가 패스마다 한 항목이고 실행자가 `fetch_add`로 서로 다른 항목만 집으므로 설계상 보장되지만, M3b는 패스 포인터 중복을 합류 전에 검사해 중복이면 그 프레임을 직렬로 돌립니다.

### 3.2 한 프레임의 동작

1. **프레임 래치**: `0x227140` 진입(또는 그 프레임의 첫 `0x226960` 호출)에서 원자 플래그를 읽어 프레임 모드를 정합니다(`off`·`serial`·`parallel`·`alternate`; ✔ M3a `ParallelPasses::latch`, 일시정지·장치 변경 프레임은 off). 프레임 도중에는 바뀌지 않습니다.
2. **미루기**(`0x226960` 훅, ✔ M3a `ParallelPasses::queue_pass`): 모드가 off, 호출 스레드가 메인이 아님(`non_main_calls` 카운터), 합류 중 재진입, 저장소 vtable 불일치, 큐(1024) 초과면 원본을 바로 부릅니다. 마커가 NULL이 아니면(정상 플레이에서는 없음) 미루지 않고 원본으로 보냅니다(`marker_passthrough`). 아니면 (builder, 값, pass, splice 정보 {usable, k})를 큐에 넣고 반환합니다. 미룰 때 저장소 레코드가 0개인 패스가 절반입니다(✔ `storage_records_at_deferral`: 앞 전이 blob이 없는 패스). 그때 k = 0이고, 합류 전에 `0x227140`이 붙이는 dword는 모두 뒤 blob입니다. 나머지는 레코드 1개에 k = 4(앞 blob)입니다.
3. **합류**(`0x227B1F` 훅): 큐의 패스를 실행자에게 나눕니다. 패스 i의 본문은 **원본 `0x226960`을 트램펄린으로 호출**하는 것뿐입니다(스레드 지역 재진입 플래그를 세움). 실행 전에 저장소에 `k` 뒤로 늘어난 dword(`0x227140`이 쓴 뒤 전이 blob)를 떼어 두고, 실행 후 다시 붙입니다(**splice**). 전제는 저장소 청크가 1개이고 `+0x320`이 그 청크를 가리키는 것이며, 아니면 그 패스는 splice 없이 실행합니다(DX11에서 op 0xD는 no-op이라 결과는 같음, §2.5). 명령은 절대 주소만 담고 저장소 내부 오프셋은 쓰지 않으므로 dword 복사가 안전합니다(✔ op 1의 바인딩 포인터, op 0xD의 blob 포인터). 구현은 `pass_stream.hpp:run_spliced`이고 `observe` 지점에서 본체만 요약할 수 있습니다(§4.2). 고속도로 34K 패스에서 폴백·orphan 0(✔).
4. 모든 실행자가 끝나면 훅이 반환하고 엔진이 꼬리 저장소·flush·컴파일을 평소대로 합니다.
5. 타입 2–5 패스(실측에서는 타입 3 present 1개와 타입 5 Generate mips 3개뿐, ✔ §2.8)는 지금처럼 `0x227140` 안에서 메인 스레드가 순서대로 기록합니다. 범위 밖입니다.

### 3.3 실행자

- 엔진 `parallel_loop_task_t`를 씁니다(27 §5). 작업 객체는 `0xC74AA0`과 같게 만듭니다(✔): `+0x00` vtable `0x21EC488`, `+0x08`/`+0x10` 0, `+0x18` 소유자 = `[0x36AC888]`(작업 관리자 표), `+0x20` 상태 0, `+0x24` 0, `+0x26` 우선순위 1, `+0x27` 실행자 수 = min(`[0x304B300]`+1, 255), `+0x28` 0, `+0x30` 이름 문자열, `+0x38` 캡처 포인터, `+0x40` 본문 함수 `void(capture*, task*)`, `+0x88` 원자 카운터. 제출 `table[0](table, &task)`(스텁 `0x167D50` → `0x167E90`), 합류 `table[3](table, &task)`(스텁 `0x167D80` → 대기 본체 `0x167DD0`: SRW `DAT_14304B2E8` 아래에서 `+0x27`(실행자 수)이 0이 아니면 호출 스레드가 `0x167F30`으로 본문에 참여하고, `+0x28`이 0이 될 때까지 조건변수 `DAT_14304B2F0`에서 기다린 뒤 상태 `+0x20 = 4`, ✔ 디컴파일).
- 본문: `while ((i = next.fetch_add(1)) < n) run_pass(i)`. 덩어리 크기 1(패스 100–245개). 큰 패스가 먼저 가도록 큐를 직전 프레임의 패스별 시간으로 내림차순 정렬합니다. **패스 객체는 풀에서 프레임마다 다른 패스에 다시 배정되므로 포인터로 기억하면 틀립니다**(✔ §2.8). 키는 (`pass+0x20` 이름 문자열, `pass+0xC0` 공간 문자열, 같은 키가 한 프레임에 반복될 때의 순번)입니다. 이름 원문은 프레임 사이에 변하지 않았습니다(✔ M3a `raw_name_changes` 0). 16자리 16진수 토큰의 `#` 정규화는 불필요하지만 무해해 유지합니다. 직전 프레임에 없던 키는 가중치 0으로 뒤에 둡니다. 같은 키에 시간과 dword 수를 함께 기록해 A0 비교와 P2 분포(§7)에 씁니다.
- 엔진 worker는 TLS 실행 문맥이 있고(`0x167F30`은 없는 스레드에도 지연 생성하고 경고 한 줄), 정차·주행 모두 97% 대기였습니다(27 §6). CPU 배치(`apps/launcher/cpu_layout.py:Plan`)에서 worker는 CPU 0·1·4–7(물리 3코어)에 있으므로 실효 병렬은 3–4입니다.
- 고속도로에서는 임계 경로가 분배(구간 ÷ 실행자 수)라 실행자 수가 상한을 직접 정합니다(§2.9). 주행 중에도 엔진 worker는 스레드당 0.02–0.04코어(✔ 27 §6)라 모두 놀지만, 물리 코어가 메인 포함 4개라 실효 병렬은 4로 잡습니다(△). SMT 형제까지 실행자로 쓰는 변형은 M3b에서 재봅니다.
- 자체 스레드 풀은 M3b에서 엔진 worker가 렌더 코드의 TLS 의존으로 실패할 때만 한 번 시도합니다.

### 3.4 공유 상태 대책

1. **프레임 할당기 아레나**: `0x1E05B0`을 인라인 훅. 병렬 구간의 **worker**는 스레드 지역 {청크, 우리가 기록한 태그, 커서}에서 `0x1E05B0`과 같은 규칙(정렬, 한도 0x200000, 데이터 `chunk+0x18`)으로 bump하고, 기록한 태그가 현재 `DAT_14304D828`과 다르거나 모자라면 엔진의 `0x166B30(현재 태그 | 0xFAFAFAFA00000000)`로 2 MB를 받습니다. 메인 스레드와 구간 밖 호출은 원본으로 갑니다(전역 청크는 메인만 씀). 수명은 엔진과 같습니다(✔ §2.3): 프레임 태그 전진 `0x1E0710`이 3프레임 뒤 `0x166C50(태그)`로 같은 태그의 청크를 모두 반납하므로 우리 청크도 함께 돌아갑니다. 규칙 두 가지가 여기서 나옵니다. (a) 태그 비교는 **청크 헤더 `+0x10`이 아니라 스레드 지역에 기록한 값**으로 합니다. 반납된 청크는 그 뒤 `0x166B30`을 부르는 누구에게나(메인의 전역 프레임 청크 포함) 현재 태그로 다시 나갈 수 있어, 헤더만 보면 worker가 메인의 청크를 같이 bump하게 됩니다. (b) 태그는 1씩만 늘지 않습니다. 장치 drain `0x2DE240`이 `0x1E0710`을 3회 연속 불러 떠 있는 청크를 전부 반납하므로 "다르면 새로 받기"만 하고 "+1이면 이어 쓰기" 같은 가정을 두지 않으며, drain 뒤에는 장치가 다시 만들어질 수 있으니 프레임 래치가 `DAT_143681860`과 vtable을 매 프레임 다시 읽어 바뀌면 off로 내려갑니다. 비용은 worker당 프레임당 2 MB 청크 1개가 3프레임 더 떠 있는 것(worker 3개면 약 24 MB, `0x166B30` 프리 리스트에서 순환)입니다. 이로써 저장소 청크·바인딩 패킷·배치 출력 배열의 경합이 사라집니다.
2. **풀 락**(SRW 하나): `0x2E5040`(통째), `0x2E6AF0`, `0x2E8FE0`, `0x2E8090`, `0x2E8440`, `0x2B94B0`, `0x2BEA70`, `0x2AE640`을 인라인 훅으로 감쌉니다. `0x2E8440`은 150바이트, `0x2AE640`은 157바이트라 훅 비용이 상대적으로 큽니다. 락 보유·대기 시간과 횟수를 카운터로 남깁니다(중단 기준 3이 락 보유 합을 봄).
3. **uniform 링 2단계**(M3d, 조건부): `0x2E5040`의 2.45–2.96 ms가 락 아래 직렬이면 이득이 1단계 상한(1.6–2.5 ms, §2.8)에 묶입니다. 대안은 둘입니다. (a) `0x2E5040` 안의 `[device+0xF1490]` 적재 3곳에 미드훅을 걸어 스레드 지역 세그먼트 포인터로 바꿔 넣고, `0x2E6AF0`을 락 아래에서 호출한 뒤 결과 포인터를 스레드 지역으로 옮김. 미드훅은 uniform 범위마다 실행되므로 비용(수천 회 × 약 0.1 µs)을 재야 합니다. (b) `0x2E5040`을 C++로 재구현(디컴파일 약 250줄, 호출 `0x236930`·`0x1509820`·`0x1509140`·`0x2E6AD0`·`0x2EF660`)하고 링 단계만 스레드별 세그먼트로. (b)의 오라클은 교대 비교(§4.2)와 렌더 비교(§4.3)입니다. 세그먼트가 스레드 수만큼 늘어 2 MB GPU 버퍼 생성이 프레임당 몇 번 더 생깁니다(△ 세그먼트 재사용 여부 미확인, 열린 질문 7).
4. `[0x120]`은 worker에서 호출을 생략하고 합류점에서 한 번만 부르는 변형도 가능하지만, 지연 해제가 한 프레임 늦어져 레코드 프리 리스트가 바닥나면 `Failed to reserve new buffer record` assert입니다. 레코드 여유를 확인한 뒤에만 시도합니다.
5. snowymoon 프록시의 인라인 훅은 패스 본체(`0x1473E60`), draw 배치 안(`0x3EB290`), `[0x120]` 아래 업로드(`[0x158]` = `0x2B5F70`)에 있습니다(✔ §2.10). 2단계부터 worker가, 그리고 풀 락 안에서, 이 중계 코드를 지나게 됩니다. 스레드 안전성을 알 수 없고 AA를 꺼도 훅은 남으므로(△) **프록시 DLL을 뺀 세션에서만** 켭니다. 게이트는 DLL 유무가 아니라 코드 바이트 비교입니다(§5).

### 3.5 직렬화 대상 확정 절차

목표는 "타입 1 패스 콜백 아래에서 실행되는 모든 함수의 공유 쓰기 목록"입니다. 장치 전역을 직접 읽는 함수(27 §6, `refs-device.csv` 1,234 READ)만으로는 `0x2E5040`처럼 장치를 인자로 받는 함수를 놓칩니다.

1. **동적 클로저**(S, 게임): dxgi 프록시를 끄고 `perf <label> --profile-hz 1000 --seconds 60`(정차·주행 각 1회, 센서 켬 1회). `hotspots.py:functions`로 `0x226960` 아래에 나타난 함수 집합을 뽑습니다(지금은 217개, 끊긴 경로 포함 시 더 많음). 끊김이 없으면 `unknown_code`가 0에 가까워야 합니다.
2. **장치 인자 전파**(M, Ghidra 스크립트 `ListDeviceFlows.java` 신설): 입력은 1의 RVA 목록. 디컴파일러 호출 지점에서 인자가 `DAT_143681860` 적재 값이거나 이미 "장치"로 표시된 매개변수면 피호출자의 그 매개변수를 장치로 표시하고 고정점까지 반복합니다. 표시된 함수에서 장치 매개변수(또는 그로부터 한 단계 적재한 포인터)를 base로 하는 **store**를 오프셋과 함께 CSV로 냅니다. `ListReferences.java`의 골격을 재사용합니다.
3. **전역 쓰기**(S, `ListGlobalWrites.java`): 같은 목록에서 RIP 상대 주소로의 store와 `LOCK` 접두 유무를 냅니다. `lock add`는 제외합니다.
4. **엔진 자체 동기화 확인**: 2·3의 결과 중 SRW·`LOCK`·스핀락 아래에 있는 것(`0x166B30`, `[0x158]`·`[0x160]`의 컨텍스트 락)은 제외합니다.
5. **빈도**: 남은 후보마다 `hotspots --focus`로 ms/프레임을 붙여 락 범위(함수 통째 vs 생성 경로만)를 정합니다.
6. **동적 확인**: M3b→M3c→M3d의 단계별 락 축소에서 교대 비교(§4.2)와 렌더 비교(§4.3)가 통과해야 다음 축소로 갑니다. 정적 분석이 놓친 쓰기는 여기서 드러납니다.
7. **패스 객체 상태를 소비하는 콜백**(§2.11): blit 계열 9개 콜백이 부르는 `0x226C40`·`0x226D80`은 패스 밖 공유 상태를 쓰지 않습니다(✔ 읽은 범위). 남은 확인은 `0x21CEC0`의 음수 id 경로(`0x21D250`, 플래그에 따라 `0x21D9B0`), `0x219C50` 꼬리, `0x1519670`, 그리고 다른 타입 1 콜백(`0x1473E60` 장면, `0x151BB90`, `0x160EB80`, `0x166D2F0`, `0x1465260`)이 자기 패스 밖에 쓰는 것이 있는지입니다. 2의 스크립트에 "패스 포인터(param)를 base로 하는 store"를 따로 세는 열을 둬 패스 지역 쓰기와 공유 쓰기를 구분합니다.

산출물은 `research/ghidra/out/device-writes.csv`(Git 제외)와 §2.6 표의 갱신입니다.

### 4.2 프레임 간 비교: 교대 모드 (shadow 대체)

같은 프레임을 두 번 기록하는 shadow 비교는 쓸 수 없습니다(✔ §2.11). 대신 **프레임을 번갈아** 기록합니다. 모드 `alternate`는 프레임 래치가 프레임 번호로 직렬(`serial`, 메인 스레드)과 병렬(parallel)을 고르고(core 0.51.2부터 직렬·직렬·병렬·병렬 4프레임 주기, §11.5), 두 경로 모두 합류점의 `pass_stream.hpp:run_spliced`에 있는 `observe` 지점에서 패스 본체(레코드 0의 k부터 뒤 blob 전까지)를 `summarize`로 요약합니다.

- **요약**(기존 코드 그대로, ✔ M3a): A0 = dword 수·draw(op 1) 수·고정 길이 토큰 히스토그램(`token_length` 표; 가변 길이 op 6·7에서 멈추고 나머지는 길이만), A1 = 포인터를 가린 FNV 해시(op 1 dword 8–9, op 0xD dword 1–2, op 0x13 페이로드 바이트 1–8, ✔ 컴파일러로 확인). 비용은 dword당 한 번 훑는 것(프레임당 24.6K dword, 수십 µs)과 키당 요약 하나입니다.
- **비교**: 키(§3.3)마다 최근 네 프레임의 요약을 보관합니다. 프레임마다 (이번 프레임 vs 2프레임 전, **다른** 모드)의 A0 비교 결과를 교차 불일치로, (이번 프레임 vs 4프레임 전, **같은** 모드)의 결과를 기준선으로 셉니다. 둘 다 짝수 간격이라 엔진이 홀짝 프레임에 다르게 그리는 패스가 상쇄됩니다(§11.5; core 0.51.1까지는 1프레임 교대, 교차 1프레임·기준선 2프레임 간격). 기준선이 장면 변화 잡음(교통·애니메이션)입니다. 같은 자리 정차에서 돌리면 잡음이 작습니다.
- **판정**: 전체·키별 교차 불일치율이 기준선 + 여유(2배 또는 +1 %p 중 큰 쪽) 안이면 통과. 기준선이 0인 키에서 교차 불일치가 반복되면 그 키를 지목합니다. A1은 프레임마다 내용이 달라 기록만 합니다.
- **정확한 불변량**(프레임이 달라도 같아야 하는 것): 프레임당 키 집합(누락·추가 키 0), 타입별 패스 수(타입 3 present 1, 타입 5 Generate mips 3), 미룬 패스 수, 합류 뒤 저장소 레코드 수, 패스 포인터 중복 0. 총 dword·draw는 이웃 프레임과 잡음 안.
- 보고: 교차·기준선 불일치율, 처음 어긋난 키와 토큰 위치(`first_difference`), 모드별 프레임 수를 status에 냅니다. B 수준(바인딩 → 패킷 → uniform 바이트)은 같은 프레임이 필요해 폐기하고 §4.3이 대신합니다.

### 4.3 렌더 결과 비교

같은 프레임 비교가 없으므로 렌더 결과 비교가 1차 오라클입니다. 끔/켬(또는 직렬/병렬)을 같은 자리에서 번갈아 재고 아래 기준이 같은 범위에 들어야 합니다.

- 센서 영상·깊이: [lessons의 기준](history/lessons.md#센서-렌더-생략과-정적-물체-깜빡임) 재사용. 같은 주차 위치·10 Hz·12초에서 나무 영역 녹색 픽셀 비율(기준 13.659–13.702%)과 깊이 중앙값(34.4915–34.4934 m)이 끔/켬에서 같은 범위. 라이다는 [18](18_performance.md#줄인-작업)의 점군 비교(선택 XYZ·range·NaN·stamp)를 끔/켬 두 bag의 분포 비교로 바꿔 씁니다(다른 프레임이므로 쌍 비교는 안 됨).
- 불변량: 끔/켬에서 프레임당 draw 수(`PassCommands` 관측), 패스 수, 컴파일된 명령 버퍼 수, PresentMon GPU busy가 교통 잡음 안에서 같아야 합니다. GPU busy가 달라지면 그리는 내용이 달라진 것입니다.
- 눈 확인: 미러·HUD·그림자·파티클(연기·비)·야간 조명. 파티클은 `0x2E8090`을 지나므로 특히 봅니다.

## 5. 안전장치

구현(core 0.35.0, ✔)과 계획을 함께 적습니다. 계획과 다르게 구현한 것은 (a)–(c)로 표시했습니다.

중단 기준:

1. M3a는 통과했습니다(✔ 2026-10-15, §4.1). 남은 장시간 확인에서 orphan·크래시·영상 차이가 나면 패스 단위 미루기를 접습니다.
2. M3b-1(티켓 순서)에서 교대 비교 교차 불일치율이 기준선을 넘거나 엔진 assert·alien 경고·크래시가 나면 worker 실행 자체가 문제입니다. 자체 스레드 풀을 한 번 시도하고(TLS 의존이면), 그래도 실패면 중단합니다. M3b-2(순서 자유)에서만 불일치가 나면 기록 순서 의존이 있다는 뜻이고, 순서를 지키면 병렬이 없으므로 중단하거나 B안을 검토합니다.
3. M3c의 판정 세트는 고속도로(§6 세트 0)입니다. 1단계 상한이 0.9 ms라 이득 문턱을 두지 않고 진단 둘로 판정합니다. (가) 락 보유 합 카운터가 예측(`0x2E5040` + `[0x120]` ≈ 1.2–1.5 ms/프레임)과 맞는다. (나) 락 밖 몫이 병렬로 줄었다(합류 비용 ≤ 0.2 ms, worker CPU 상승, 기록 구간 − 락 보유 합이 직렬 때의 1/3 이하). 둘 다 참이고 2단계 예측 이득(기록 구간 − 락 보유 합 잔여 − 0.76)이 1 ms 이상이면 M3d로 갑니다. 락 보유 합이 예측의 절반 이하인데 이득도 없으면 원인이 락이 아니므로(합류 비용, worker 깨우기, 락 밖 경합) 중단합니다. 정차 세트는 상한 확인용으로 함께 재고, 센서 켬 세트가 정차보다 0.5 ms 넘게 작으면 원인을 찾은 뒤에 갑니다.
4. M3d는 고속도로 CPU busy p50 −1 ms 이상(정차 −2 ms 이상)이면 운영 후보, 아니면 중단하고 26의 일 줄이기(C1·C6)로 돌아갑니다. 1단계로 되돌릴 이유는 없습니다(고속도로에서 1단계 단독 이득은 1 ms 미만).
5. 어느 단계든 원인 모를 크래시가 한 세션에 2회 이상이면 멈추고 원인을 찾습니다.

## 8. 열린 질문

1. 렌더 통계 카운터 경합: `0x2E5FF0`·`0x2E8090`의 카운터는 `lock add`라 문제가 없습니다(✔). 남은 비원자는 `DAT_143673554`(태그, 무해)와 버퍼 레코드 참조수 u16(풀 락)입니다. uniform composer들(`0x1509140` 등)의 전역 쓰기는 P4입니다.
2. `device->vtable[0x120]`: 정체는 확인했습니다(§2.4). worker에서 호출을 생략해도 되는지는 레코드 프리 리스트 여유에 달려 있고, 락으로 감쌀 때 0.375 ms의 직렬 비용이 어디까지 이득을 깎는지는 M3c에서 잽니다.
3. 패스 간 의존(경계 표시): 기록 순서에는 영향이 없습니다(✔ §2.5). 타입 3·5 패스 뒤로 타입 1을 미뤄도 짧은 주행(34K 패스)에서 이상이 없었습니다(✔). 장시간은 △.
4. ✔ 답함(§2.8): 타입 1 패스 100–113개(브리지 끔), 메인 패스 33–41%. 절반 미만이라 B안은 1차 필수가 아니고 상한은 메인 밖 시간 2.5–3.8 ms입니다. 남은 것은 락 넘김 횟수(≈ 프레임당 draw 아이템 수)로, 1단계의 경합 비용을 정합니다.
5. 엔진 worker에서 렌더 기록 코드의 TLS 의존(M3b).
6. 합류 시 worker 깨우기 지연(세마포어)이 작은 패스보다 길 수 있습니다. 메인 스레드가 먼저 작은 패스를 집도록 정렬이 충분한지 봅니다.
7. uniform 세그먼트가 프레임마다 생성·해제되는지(P7의 남은 부분). 스레드별 세그먼트가 GPU 메모리와 생성 비용을 얼마나 더 쓰는지. 프레임 할당기 쪽 비용은 ✔ 정해졌습니다(worker당 2 MB/프레임, 3프레임 뒤 반납).
8. snowymoon 프록시 없이 운영할 수 있는지(사용자 판단, 안티앨리어싱). AA를 꺼도 훅은 남으므로(△ §2.10) DLL 제거가 필요합니다. 센서 렌더와의 공존만 따로 푸는 core 0.50.0의 구간 설정(`proxy_sensor_coexistence`)은 정적 분석 가설이며 M3c·M3d의 기록 경로는 건드리지 않습니다([조사](../research/snowymoon/sensor_coexistence.md)).
9. CPU 배치: worker 6개가 물리 3코어에 몰립니다. 메인 코어의 SMT 형제(CPU 3)를 비워 둔 결정과의 균형을 다시 볼지.
10. ✔ 리셋은 패스 반복 전(M3a: 미룰 때 레코드 0 또는 1개, k = 0 또는 4). 청크 수 1.
11. ✔ 패스 이름 원문은 프레임 사이에 바뀌지 않습니다(M3a `raw_name_changes` 0). 정규화는 불필요하나 무해해 유지.
14. 타입 1 콜백이 자기 패스 밖 공유 상태에 쓰는 곳이 있는지(§2.11, §3.5 7). blit 계열은 없음(✔ 읽은 범위).
15. `serial` 모드의 계측 비용(패스마다 QPC 두 번, 이름·공간 문자열 읽기, 정규화, 해시). 2.75 ms에 얼마가 들었는지 `off`/`serial` ABAB로 잽니다(§6).

## 9. 27과 다르게 판단한 것

- 27 §6 "id를 순서대로 모아 `[0x110]`으로 렌더 스레드에 제출": `[0x118]`(`0x2F03B0`)이 렌더 스레드 큐에 넣고, `[0x110]`(`0x2B3A80`)은 렌더 스레드 루프 `0x2F0460`이 꺼내 실행하는 함수입니다(✔). 메인 스레드가 `[0x110]`을 직접 부르는 것은 능력 0x10이 없을 때(DX11에서는 아님)뿐입니다.
- 27 §6 "렌더 통계(`render_counters_update`)도 원자 연산이 아닙니다": `0x2E5FF0`의 세 카운터는 `lock add`입니다(✔). 비원자는 일련번호와 버퍼 레코드 참조수입니다.
- 27 §6 "묶음 분할의 이유는 미확인": 경계 플래그는 `pass+0x200 == 0`이고, 그 패스는 op 4를 쓰지 않으며 컴파일러가 타깃 상태를 저장소 사이로 이어 가므로 다음 저장소와 같은 명령 버퍼에 있어야 합니다(✔). 16개 최소 묶음은 휴리스틱(△).
- 27 §6 "`0x28CE60`(저장소별 bump 할당, 64K 단위)": 단위는 0x10000 dword(256 KB)이고 청크 메모리는 **공유 프레임 할당기 `0x1E05B0`**에서 옵니다(✔). 저장소는 패스별이지만 청크의 출처는 공유라 조건 3에 걸립니다.
- 27 §6 "장애물: draw batch가 장치 버퍼 풀을 락 없이 씁니다": 맞지만 가장 뜨거운 것은 프레임 할당기이고, 그 다음이 uniform 링 커서(`0x2E5040`, 2.93 ms)입니다. `0x2E8090`·`0x2E8440`(버퍼 레코드)은 파티클 쪽이고 draw 배치 경로에서는 `[0x120]`을 통해서만 만납니다.
- 27 §6 "패스별로 다른 명령 버퍼에 컴파일한다면": 그렇지 않습니다. 16개 이상 패스가 한 D3D11 명령 버퍼로 컴파일됩니다. 다만 기록은 패스별 저장소라 병렬화에는 지장이 없습니다(✔).
- 27 §5의 "덩어리 512개 원자 배분": 그 분배는 작업 객체가 아니라 호출자가 쓴 본문(`0xC74B80` 등)의 관례입니다. 우리는 본문을 직접 쓰므로 패스 단위(덩어리 1)로 나눕니다.
- 27 §6 "패스 단위 병렬의 상한은 장면에 따라 2.5–3.8 ms": 직렬화가 없을 때의 이상값으로 그대로 씁니다. 다만 1단계(통째 락)에서는 락 직렬 바닥 때문에 1.6–2.5 ms가 상한이고, 그 값에 가까워지는 것은 2단계부터입니다(△ §2.8). 판단이 다른 것이 아니라 단계별로 나눈 것입니다.
- 27 §6 "고속도로에서 패스 단위 병렬로 줄일 수 있는 시간은 2.4–3.0 ms보다 작습니다": 맞습니다. 폴링 dword 비중으로 보면 가장 큰 패스가 18 / 15%뿐이라 상한을 정하는 것은 메인 패스가 아니라 분배이고, 이상 상한은 약 1.7 / 2.1 ms입니다(△ §2.9).
