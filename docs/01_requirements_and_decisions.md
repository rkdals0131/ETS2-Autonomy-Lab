# 요구사항과 실행 전 결정

이 프로젝트의 목적은 일반도로·교통 신호·화물 운송이 있는 ETS2에서 운전 보조를 즐기면서, 다중 카메라 기반 자율주행 연구 환경을 만드는 것입니다. 연구용 센서를 만드는 일과 주행 모델을 만드는 일을 순서대로 진행합니다.

## 사용자가 확정한 조건

| 항목 | 확정 내용 |
| --- | --- |
| 주 대상 | Euro Truck Simulator 2 |
| 운영체제 | 이후 개발·실행은 Windows |
| GPU | RTX 3060 Ti. 실제 VRAM과 드라이버는 Windows에서 확인 |
| 디스플레이 | 물리 FHD 모니터 한 대 |
| 사용자 화면 | 기본 운전석 POV |
| Phase 1 범위 | 고속도로 주행보조: ACC, 차로 유지, 사각지대 감시와 운전자 지시 차로 변경 보조 |
| 센서 | 트랙터에 전방 협각·광각과 좌우 포드 측후방 카메라 4개. 정후방 뷰 없음 |
| 인지 방향 | 뷰별 경량 모델과 객체 수준 융합. depth 기반 가상 LiDAR·객체 기반 가상 레이더는 후속 구현 |
| 장기 기능 | 시내 → 주차로 확대. 다중 카메라 BEV·E2E는 후속 연구 |
| 사용 흐름 | 운전 중 단축키로 스택 활성화·해제, 상태와 결과 시각화 |
| 시간 조건 | 정상 게임 속도, 같은 장면 상태의 카메라 묶음 |
| 제외 | 게임 감속, 프레임을 넘기며 카메라를 돌려 찍는 방식 |
| 별도 프로젝트 | AC의 서킷·도로 맵에서 센서와 상태머신·제어 연구 |

Phase 1은 운전자 감독을 전제로 하며 램프 진출입·톨게이트는 사람이 담당합니다. 자동 차로 변경은 Phase 1b입니다. [센서 구성과 상세 범위](14_phase1_highway_sensors.md)를 따릅니다. 현재 구현은 센서 수집이며 위 주행보조 기능이 완성됐다는 뜻은 아닙니다.

## 작업 기본안

아래 항목은 요구사항을 만족시키기 위한 변경 가능한 설계안입니다. 사용자에게 새로 확정받은 정책으로 취급하지 않습니다.

| 선택 | 기본안 | 선택 이유 |
| --- | --- | --- |
| 플러그인 | x64 C++와 CMake | 게임 내부와 D3D 리소스 접근 |
| 외부 실험 코드 | Windows Python 가상환경 | 영상·학습·프로토타입 제어 |
| 첫 그래픽 경로 | 설치 빌드가 지원하면 DX11 우선 조사 | 공개 추출·텍스처 후킹 코드와 연결 |
| 시각화 | Foxglove Windows 앱과 SDK | 카메라·좌표·점군·시계열을 함께 보기 |
| 기록 | MCAP 중심, 고용량 영상은 기록 비용에 따라 분리 검토 | 시간 정보와 메시지 보존 |
| IPC | 작은 상태·명령은 로컬 통신, 영상은 별도 경로 | 큰 영상 때문에 제어가 지연되지 않게 함 |
| 카메라 모델 | 고정 pinhole부터 시작 | 내·외부 파라미터와 depth 정합이 명확 |
| 확대 순서 | Phase 1 4뷰 → 시내에 필요한 측방 뷰 → 주차 센서 | 주행 기능에 필요한 방향을 우선 확보 |
| 초기 운전 범위 | 고속도로·자동차전용도로, 운전자 감독 | 장거리 주행 피로 경감이 첫 목적 |
| 대형 모델 | 이후 결정 | 게임과 모델이 GPU를 공유하므로 실제 예산 필요 |

## 지금 선택하지 않는 항목

- 모델 이름, 파라미터 규모, 학습 데이터 총량.
- 센서의 정확한 장착 좌표와 최종 FOV. 트럭 모델·운전석·트레일러 가림을 보고 정합니다.
- RTX 3060 Ti에서 달성 가능한 FPS.
- 엔진에 새 카메라를 생성하는 함수 주소와 구조체 배치.
- 기본 게임의 어느 빌드를 사용할지. 설치 가능한 빌드와 의존 플러그인 지원 범위가 필요합니다.
- 진짜 어안 투영을 만들지, 여러 뷰를 재투영할지. 먼저 pinhole 경로를 확보합니다.
- 최종 ROS 2 통합 여부. Foxglove 사용 자체에 ROS 2를 필수로 두지 않습니다.

설치 조사에서 Ryzen 7 3700X, RAM 약 23.95 GiB, Windows 11, RTX 3060 Ti 8 GiB와 현재 게임 1.61.1.1을 확인했습니다. 실제 경로와 저장 공간은 [설치 분석](10_installed_game_static_analysis.md)에 있습니다. 이것으로 다중 센서 FPS가 검증된 것은 아닙니다.

## 대안의 위치

| 방법 | 채택 여부 | 이유 |
| --- | --- | --- |
| 모니터 화면 캡처 | 초기 관측·비교에 사용 가능 | 독립적인 후방 센서를 만들지는 못함 |
| 미러 피드 추출 | 우선 조사 | 이미 다른 시점의 장면을 렌더링함 |
| 기존 미러 슬롯의 카메라 변경 | 초기 가능성 실험 | 최종 센서 수·자유도·사용자 미러 보존은 별도 해결 |
| 주차 카메라 경로 | 우선 조사 후보 | 차량 부착 카메라 경로의 공식 단서 |
| 엔진에 센서 뷰 추가 | 최종 구현 방향 | 사용자 POV와 독립적인 4~6뷰 |
| multimon | 보조 실험 | 공식 디스플레이 기능의 제한과 주 카메라 종속성 존재 |
| 큰 가상 모니터 | 필요할 때만 | 화면 공간을 늘려도 새 카메라 생성 문제가 해결되지는 않음 |
| 순차 시점 전환과 게임 감속 | 제외 | 사용자 요구와 동기화 목표에 맞지 않음 |
| 별도 게임 프로세스 여러 개 | 기본안에서 제외 | 동일 교통 장면·시간 상태 보장이 추가 과제 |
| 외부 렌더러로 맵 재구성 | 후순위 | 게임의 동적 장면과 차량을 다시 동기화해야 함 |
